# Owlshift — build plan for P0 and P1

Status: draft, 2026-09-27. What to build first, in order: the foundations (P0), then one ticket turned into a verified pull request on demand (P1). The steps after that are described in the [roadmap](roadmap.md).

## Checks to run live before writing code

Eight assumptions carry the design; each is checked with a real call before the code that depends on it, and the dated result is written down next to the decision it settles.

| # | Assumption | Depends on it | Check | Before |
| --- | --- | --- | --- | --- |
| C1 | `claude -p` runs headless on the user's own subscription login, with no API key, and honours `--model`, `--effort`, `--permission-mode` and structured output inside a worktree | The whole executor | One tiny run in a scratch repository | P0 |
| C2 | `codex exec` runs headless on a ChatGPT subscription login, gives structured output, accepts a reasoning-effort setting, confines writes to the worktree in `workspace-write`, and exits non-zero on failure | Codex reviewers | One tiny run | P5 |
| C3 | GitHub accepts pushes to a custom ref namespace, and creating an existing ref is rejected, so a claim is atomic | Claims | Two concurrent pushes to a test repository | P0 |
| C4 | Linear exposes a comment's last-edit time; an issue can be created directly in Triage with an API key; an app user works with polling only | S2 quiet window, S13, D8 | API calls on the Owlshift workspace | P2 |
| C5 | Optional reading, not a gate: Sortie's and Symphony's `WORKFLOW.md` and their adapter pitfalls | D5, Jira adapter | Read their docs and adapter code | P0 |
| C6 | `owlshift` is free where it matters: crates.io and npm were free on 2026-09-27; the GitHub name `owlshift` is taken, so the repository lives on the maintainer's personal account (`pitchopp/owlshift`), and `owlshift.dev` still needs a registrar check | D3 | Registrar check | P0 |
| C7 | Each provider's terms allow unattended headless use of a personal subscription through its own CLI; each CLI reports a reached usage limit in a detectable way (message, reset time, exit status) | Subscription-first design, S10, S17 | Read the current terms; trigger or capture a limit message for each CLI | P0 for Claude, P5 for Codex |
| C8 | Each harness CLI reports whether it is logged in through a status command, readable without Owlshift touching a credential | `owlshift doctor` (OWL-12) | Run each status command logged in, logged out and on an API key | P0 |

### Results

Checks run on 2026-09-28 (OWL-6) with Claude Code 2.1.283 and git 2.54 on macOS. Account identifiers are left out on purpose.

**C1 — passed, with one guardrail finding.** Seven tiny `claude -p` runs in a linked worktree of a scratch repository, each launched with `env -i HOME PATH USER LANG`: no `ANTHROPIC_API_KEY`, no `ANTHROPIC_BASE_URL`, no parent session variables.

- Login: `claude auth status` reports `authMethod: claude.ai` on a Max subscription; the stream's `init` event reports `apiKeySource: none`.
- `--model haiku` and `--model sonnet` reach the named model (`modelUsage`). `--effort` is applied: the same prompt used 0 thinking tokens at `low` and 2,389 at `max`.
- `--permission-mode dontAsk` denied Write and Bash (`permission_denials`, no file created); `acceptEdits` wrote the file inside the worktree. `--json-schema` returns the object in `structured_output`.
- Failure: an unknown model exits with status 1 and `is_error: true`, `api_error_status: 404`, `terminal_reason: "api_error"`, yet `subtype: "success"`. The harness adapter reads `is_error` and the exit status, never `subtype`.
- `--bare` cannot be used: according to `claude --help`, its authentication is strictly `ANTHROPIC_API_KEY` or `apiKeyHelper`, and the subscription login (OAuth, keychain) is never read.
- **Guardrail finding.** By default a headless run loads the user's own configuration: hooks, `CLAUDE.md`, plugins and every MCP server, including claude.ai connectors to Linear, Slack and Gmail. That hands the agent tracker credentials, against the rule that agents get none. Verified mitigation, in one of the seven runs: with `--setting-sources project,local --strict-mcp-config`, the `init` event lists no MCP server, no user hook fires (the default run showed hook events), and the run succeeds on the subscription login (`apiKeySource: none`). Credentials outside Claude Code, such as the `gh` login in the system keyring, stay reachable from the agent's shell: the agent environment closes that path (OWL-22, below). Since OWL-53, below, the adapter loads no settings file at all.

- **Operator allow-list (OWL-63).** Decision: a declared name reaches an agent only if the operator lists it in the personal file, `allow_gate_env = ["FEATURE_FLAGS"]`; a project's declaration never widens that list, and no personal file means no name passes. Decision (2026-09-29): the runner wraps every agent run and every gate command in an OS sandbox it builds itself — `sandbox-exec` with a generated Seatbelt profile on macOS, `bwrap` on Linux — around the harness and everything it starts (approach A, chosen by the maintainer). Because that closes the Keychain to Claude Code too, an agent run authenticates through a login of its own. Decided first as a second login of the same account, made once with `claude auth login` inside the sandbox in a folder `CLAUDE_CONFIG_DIR` names; that login cannot be made on macOS, and OWL-94 (below) replaced it with a `claude setup-token` token the runner hands the harness. - **As built.** `owlshift_platform::sandbox` turns a program and its arguments into the wrapped command, from a `Policy` of plain paths, each made real first (Seatbelt compares real paths: `/tmp` is `/private/tmp`). On macOS the profile is given inline with `-p` and every path as a `-D` parameter read with `(param …)`, checked live on 2026-09-29 with a path holding spaces, parentheses and a double quote: nothing is quoted into the profile, and no profile file exists for a command to rewrite. Its rules go from the widest to the narrowest, the last match winning. Every read rule names `file-read-data file-read-xattr`, never the wildcard, per the correction above. The order is:
  1. Everything allowed.
  2. No write but `/dev`.
  3. The home and the closed folders neither read nor written.
  4. The readable, writable and temporary folders opened again.
  5. Each folder above an opened one listable by itself, for `getcwd`.
  6. The protected paths not written.
  7. The hidden paths and the Keychain files neither read, `stat`ed nor written.
  8. The security daemons' lookups denied.

  On Linux, bwrap, found in the system folders only, runs with `--die-with-parent --unshare-pid --ro-bind / / --dev /dev --proc /proc`, a private `/tmp`, and empty `/run/user`, `/var/tmp`, home and closed folders. The policy's folders are then bound back, the shallowest first; a hidden file inside a bound folder is replaced by `/dev/null`. Arguments pass after `--` as they are.

The same rule, `named_folder`, now also judges the `PATH`'s folders, which were compared as written: `~/bin/..` or a link to the home opened the whole home. Decision (2026-09-30, OWL-94): on every platform, a confined agent run logs in to Claude Code with a long-lived token of the operator's subscription, made by `claude setup-token`.

- **Where it lives.** `owlshift init` stores it in the system keychain, service `owlshift`, account `claude-agent`, like the Linear key and the GitHub token (`init::CLAUDE_TOKEN`). The runner reads it in `owlshift do`, with the other secrets. The agent never reads the keychain, which the sandbox closes.
- **How it reaches the harness.** The Claude Code harness holds it (`ClaudeHarness::login`) and declares it in `Harness::sandbox_needs` as a `HarnessLogin`. The executor gives it to the harness command alone, right before the spawn (`HarnessLogin::apply`): first as `CLAUDE_CODE_OAUTH_TOKEN`, and since OWL-96 on a pipe the command inherits, named by `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` (below). It is never in `AgentEnv`'s variables, which the ticket had put in `from_runner`: kept out, it never reaches a gate command or the credential probes of OWL-22. Those probes still flag every Claude or Anthropic variable, and both variables are on the floor's list, so a project cannot declare them.
- **A configuration folder of the run's own.** The executor also sets `CLAUDE_CONFIG_DIR` to an empty folder, `harness-config`, inside the run's own temporary folder, which is private to the user and removed with the run. The runner makes it and binds it read and written into the sandbox: bwrap makes the temporary folder anew, empty, in its private `/tmp`, so a folder made there beforehand would not be seen (the first Linux CI run showed it). The CLI finds no other login there, as the check above ran, and nothing it writes outlives the run: transcripts, shell snapshots and settings stay with the run. A settings file one run wrote cannot reach the next. Rejected: one folder per install, `<config>/agent-login/claude`, which the ticket named. The runs of every project would share it and write into it, and a machine that made the old login could still hold a plain-text refresh token there for every agent to read. `CLAUDE_CONFIG_DIR` is no longer inherited from the runner, and `paths::claude_agent_login_dir` is gone.
- **Refusals.** A confined Claude Code run without a stored token, or with one that is blank or holds a space or a control character, is refused before anything is cloned (`NoAgentLogin`). The fix: run `claude setup-token`, then `owlshift init` and paste the token it printed; `owlshift init --replace-secrets` replaces a stored token that expired, was revoked or was pasted wrong. A Claude Code failure with API status 401 names the same fix. `init` refuses to store any secret that is not one word, as one pasted across lines is.
- **What never holds the token.** Events, briefs and error messages never hold it: the `Secret` type prints `<redacted>` in debug output, and no refusal names a value. The run's log files hold `<redacted>` where the harness printed it, even split across two writes (`RunLog`). A `result.json` or an artifact that holds it fails the run with a credential finding that names the file, never the value: what they say would reach the tracker, the pull request and the events.
- **Residual risk, recorded.** Until OWL-96, the agent could read the token: Claude Code drops `CLAUDE_CODE_OAUTH_TOKEN` from its tools' environment, but the `claude` process was started with it, and its exec block stays readable by the same user (inside the macOS sandbox through `sysctl(KERN_PROCARGS2)`, checked by OWL-96; on Linux through `/proc/<pid>/environ`). Since OWL-96 the token reaches the CLI on a pipe, and is in no exec block. What remains:
  - The guarantee rests on the CLI reading the pipe at start-up, before any tool runs, as Claude Code 2.1.284 does (checked with a made-up token, below). A process the harness started before that read, or a CLI that ignored the variable, would find the token in the pipe: Owlshift consumes nothing itself, it only never writes the token elsewhere.
  - The token stays in the `claude` process's memory. Reading it takes a debugger's access to that process (`ptrace` on Linux, `task_for_pid` on macOS), which the sandbox does not deny; the host's own rules decide (Yama's `ptrace_scope`, the binary's hardened runtime). Not checked.
  - On macOS, which has no `pipe2`, the pipe is close-on-exec a moment after it is made. It is made while no process tree can start, so no harness or gate command is forked then; a process another runner thread started with a bare spawn at that moment could inherit it. The runner starts none alongside a harness today.
  - The network stays open, so a harness or process that got the token could send it anywhere, or copy it into a file of the worktree or a commit, which no check reads. The operator revokes the token like any Claude Code login. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` closes none of this (OWL-96).
- **Tests.**
  - Unit tests: `init`'s new secret on the in-memory keychain, and the refusal of one pasted wrong; doctor's check, whether stored, absent or unreadable; the harness's refusals and its login; the log's redaction, the token split across writes included.

**OWL-96 — can the agent's shell read the token: live check.** Checked on 2026-09-30 on the maintainer's machine (macOS 26.6.2, Claude Code 2.1.284) with a made-up token, never the real one. A shell command needs a model turn, and a made-up token gets none from the real API, so `claude -p` was pointed (`ANTHROPIC_BASE_URL`) at a local fake Messages API that answered with scripted tool calls: a `Bash` probe, a `Write` of `written.txt`, and a `Bash` write. The fake API confirmed each request carried the made-up token. The probe printed presence and counts, never a value. The confined runs used Owlshift's own `AgentEnv::from_runner`, `ClaudeHarness::sandbox_needs` and `AgentEnv::confine` (the real Seatbelt profile), the adapter's write-in-worktree flags, and an empty `CLAUDE_CONFIG_DIR`.

- What `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is, read in the 2.1.284 binary: a hardening mode for runs on untrusted input, such as a GitHub Actions workflow. With it set to `1`, the CLI forces the permission mode to `default`, whatever `--permission-mode` asks, and says so on standard error: "Permission mode forced to default — CLAUDE_CODE_SUBPROCESS_ENV_SCRUB is set (allowed_non_write_users hardening)".
- The token in the tools' environment: absent in every run, scrub or not. The CLI drops `CLAUDE_CODE_OAUTH_TOKEN` from its subprocesses by itself.
- The token in a process's exec block: unconfined, `ps eww` found it in one process, the `claude` one. Confined, `ps` is refused ("operation not permitted"), but a script calling `sysctl(KERN_PROCARGS2)` read the exec blocks of about 700 processes and found the token in one, with or without the scrub.
- The scrub's cost: under `--permission-mode acceptEdits`, the `Write` call was denied ("Permission for this tool use was denied"), and the run went on without it. A write-in-worktree agent could no longer edit files.
- Handing the token over a file descriptor instead, as the CLI's `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` allows (a pipe at descriptor 3, the variable naming it; the CLI reads the pipe at start-up and drops the variable): the fake API got the token, no exec block held it (0 of about 700, confined), descriptor 3 gave the tools nothing, and the `Write` call succeeded, confined and not.
- Not checked: Linux. Docker was not running and no Linux host with a login was at hand; CI has no `claude`. What remains, on a Linux host with `bwrap`, a token from `claude setup-token` stored by `owlshift init`: `OWLSHIFT_LIVE_CLAUDE=1 cargo test -p owlshift-runner --test agent_live -- --ignored`, which runs a real confined `claude -p` on that token.

Decision (2026-09-30, OWL-96): the harness command does not set `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`. It does not keep the token from the agent, which reads it from the `claude` process's exec block, and it would deny every file edit of a write-in-worktree run. The agent environment inherits no `CLAUDE_*` variable from the runner (`INHERITED`), so an operator's own setting does not reach the harness.

Decision (2026-09-30, OWL-96, extended by the maintainer to the fix): the executor hands the token over a file descriptor, and never sets `CLAUDE_CODE_OAUTH_TOKEN`.

- **How.** `HarnessLogin::apply` calls `process::hand_over_on_descriptor`: it writes the token and a newline into a pipe before the spawn, closes the write end, moves the read end to a descriptor above 2, close-on-exec in the runner, and makes it inheritable in the child alone (a `pre_exec` hook that makes one `fcntl` call, the only `unsafe` of `owlshift-platform` on Unix). The variable `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` names it. The runner's copy closes when the command is dropped, right after the spawn. A token holding a newline, or longer than 511 bytes, is refused before anything runs; the keychain's one-word check refuses the first already, and a `claude setup-token` token is about 110 bytes. The one write of 512 bytes at most is atomic and never waits for a reader. Native Windows runs no agent (D9), and there the call fails.
- **No fallback.** An older CLI that does not know the variable finds no login, and the run fails; the token never goes back into an environment.
- **Rejected.** `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` (above). A fixed descriptor 3 through `dup2`: more `unsafe`, and the CLI reads any number. A temporary file: the token would sit on disk.
- **Tests.** Unit tests of `hand_over_on_descriptor`: the child reads exactly the token, once, and its environment does not hold it. A process the runner starts while the handed-over command still lives does not have the descriptor. A token with a newline, or too long, is refused without being shown. The confinement bench runs through `Executor::run`, under Seatbelt on macOS and under bwrap on the Linux CI job. Its harness reads the token from the descriptor, and its probe checks the rest without showing the token: `CLAUDE_CODE_OAUTH_TOKEN` unset; the raw environment not holding the token; a process started after the read getting nothing from the descriptor; and, where there is a `/proc`, exactly one process inside the sandbox whose exec block holds the token, the control it started with the token on purpose. Passed on the maintainer's macOS machine on 2026-09-30, and on the Linux CI job the same day (ubuntu-latest with the repository's bwrap AppArmor profile, `OWLSHIFT_REQUIRE_CONFINEMENT=1`, so not skipped): bwrap passes the descriptor through, and inside its sandbox only the control's exec block held the token.
- **Not checked.** A real `claude` login through the descriptor: on macOS the maintainer's command is `OWLSHIFT_LIVE_CLAUDE=1 cargo test -p owlshift-runner --test agent_live -- --ignored`, which now hands the token over the same way. On Linux, the same command on a host with `bwrap`, which no one has here.

It did so as well when the folder did not exist: the CLI makes it, so the runner makes and binds nothing more. The run's temporary folder is already written in both sandboxes.

Decision (2026-09-30, OWL-100): a confined Claude Code run keeps its temporary files in `harness-tmp`, inside the run's own temporary folder.

- **How.** The harness names the variable in `SandboxNeeds::temp_variable`: `ClaudeHarness` names `CLAUDE_CODE_TMPDIR` (`claude::TMPDIR_ENV`) when the agent is confined, and a bare run of the test bench is unchanged. The executor sets it on the harness command alone to `<run temporary folder>/harness-tmp` (`executor::HARNESS_TEMP_DIR`), after the command is confined; a gate command does not get it. The CLI makes the folder, and it is removed with the run. Nothing is opened in the sandbox: no bind, no shared temporary folder.
- **Rejected.** A third field of `HarnessLogin`: a temporary folder is not a login. The run's temporary folder itself: it works, but a folder of its own keeps the CLI's per-project folders apart from the agent's own `TMPDIR` files. Making and binding the folder like `harness-config`: not needed, since the CLI makes it.
- **Residual risk.** The variable is not documented: a release that drops it fails every confined run at start-up on macOS, loudly. With the inbox reopened by this variable, a release that drops `CLAUDE_CODE_HARBOR_KITE` too leaves the refuse flag alone to refuse messages (OWL-65).
- **Tests.** The unit test of `ClaudeHarness::sandbox_needs` checks that a confined run names the variable and a bare one does not. The bench's `a_confined_harness_keeps_its_temporary_files_clear_of_the_operators_folder`, in `tests/confinement.rs`, runs through `Executor::run` a shell-script harness that keeps its files as the CLI does, in `claude-<uid>` under `CLAUDE_CODE_TMPDIR`, and fails if the variable is unset. It writes there, the folder lies in the run's `TMPDIR`, and it cannot list the user's `/tmp/claude-<uid>`: denied on macOS, where the test makes the folder if it is absent, and absent under bwrap on Linux. Passed on the maintainer's macOS machine on 2026-09-30. `agent_live` sets the variable as the executor does. `peer_inbox.rs` still checks that the confined command carries `CLAUDE_CODE_HARBOR_KITE=0`.

**OWL-71 — launching agent commands on native Windows (decided 2026-09-29).** Native confinement (OWL-58) was split: this part prepared the launch path, and OWL-72 was to apply an AppContainer through it. Decision D9 is unchanged: native Windows runs no agent. Superseded (2026-09-29): native confinement is set aside, and the launcher was removed (OWL-89, 2026-09-30); see the decision after the OWL-72 results below. What follows is the record of what was built and checked; none of it is in the code any more.

- Premise, checked on 2026-09-29: `std::process::Command` on stable Rust cannot pass a proc-thread attribute, which is how an AppContainer is given (`SECURITY_CAPABILITIES`). A scratch crate calling `ProcThreadAttributeList::build().raw_attribute(..)` and `CommandExt::spawn_with_attributes`, checked with `cargo check --target x86_64-pc-windows-msvc` on rustc 1.98.1, fails with E0658, "use of unstable library feature `windows_process_extensions_raw_attribute`" (issue #114854).
- The fork: a `CreateProcessW` path of the runner's own, with a child type of its own, or a small program the runner starts as it starts any command, which calls `CreateProcessW` itself. Decision: the program, `owlshift-launch`. A child type of our own would replace `std::process::Child` wherever the runner takes one (the `Harness::drive` trait, the Claude Code adapter's `drive`, `drive_plain`, `watch::spawn`, the gate, `process::run_command` for the probes), and redo in Windows-only unsafe code what std does: pipes, the environment block, the program's lookup, argument quoting. The launcher keeps `sandbox::wrap -> Command`, as `sandbox-exec` and `bwrap` do; the cost is one more process per agent command and a second binary.
- As built, until its removal in OWL-89 (2026-09-30):
  - `owlshift-launch` is a second binary of `owlshift-cli`, whose `default-run = "owlshift"` keeps `cargo owl` and `bacon owl` working. Its code is `owlshift_platform::launch`, on Windows only; elsewhere the binary refuses to run.
  - Its arguments are `-- PROGRAM LINE`, `LINE` being the rest of the program's command line, verbatim. On Windows `sandbox::wrap` quotes the arguments into `LINE` as std quotes a regular argument, and `sandbox::wrap_line` takes a line as it is, for `cmd.exe`. The gate goes through `AgentEnv::confine_shell`: `confine` rebuilds a command from `get_args`, which hands back the gate's `raw_arg` as a plain argument, to be quoted again.
  - The runner starts the launcher as the root of the run's process tree, inside its Job Object (`ProcessTree::spawn`, unchanged). The launcher finds the program as std does, but for the runner's own folder and `PATH`: `.exe` is added when there is no extension, and a name with no folder is looked for in the absolute folders of the agent's `PATH`, then `SYSTEMROOT\System32` and `SYSTEMROOT`, never in the working directory. It creates the program with `CreateProcessW` and its three standard handles, closes its own copies, waits, and exits with the program's exit code; its own failures exit with 127 and `owlshift-launch: <reason>` on standard error. A job's process starts its children in the job, since `tree.rs` allows no breakaway, so stopping the tree stops the launcher, the program and all it started.
  - Batch files are refused, by `wrap_line` and again by the launcher on the path it found: `.bat` and `.cmd` in any letter case, trailing dots and spaces ignored, and a name holding `:`, a file stream such as `x.bat::$DATA`. `cmd.exe` reads a batch file's arguments again; std guards that case with its own escaping, the launcher does not. So the npm-installed Claude Code, `claude.cmd`, cannot be launched, and the native installer's `claude.exe` can.
- Nothing is granted or denied yet. A shipped build has no launcher: on Windows `wrap` still refuses with `Unsupported`, as `available` does, and `Executor::run` and `owlshift do` refuse before anything is written. Only a test sets one, with `sandbox::use_built_launcher`, compiled with the platform crate's `testkit` feature, which the runner's tests enable: a thread-local override naming the binary Cargo built, so a refusal test running beside it still sees none. `the_cli_never_turns_confinement_off` refuses the name in the CLI's sources, since a workspace build unifies the feature into `owlshift`. The work that would have lifted the refusal, finding the launcher next to the running `owlshift`, confining the program it creates and lifting `available`, is not planned; OWL-72, below, recorded how the candidate confinements behave before it was set aside.
- Checked on windows-latest on 2026-09-29 ([run 36591257645](https://github.com/pitchopp/owlshift/actions/runs/36591257645)):
  - `process::tests::a_launched_program_is_stopped_with_its_launcher_at_the_deadline`: the helper's parent was `owlshift-launch.exe`, and at a 4 s deadline the launcher, the helper and its grandchild were all gone.
  - `executor::harness::tests::a_confined_harness_command_starts_through_the_launcher`, on the harness's path, `AgentEnv::confine`: an empty argument, `a b`, `a"b`, `a\"b`, `c:\x\` and a tab came back unchanged, as did the standard input, the agent's placeholder `GH_TOKEN` and exit code 3.
  - `executor::gate`'s Windows tests, bare and confined: `echo "a  b" \"q\" "c:\x\" && exit 5` logged its line as written and failed with exit status 5, the agent environment was set, and a command past a 1 s deadline was stopped.
  - The refusals held: `native_windows_refuses_to_confine`, `a_confined_gate_command_is_refused_on_native_windows` and `a_run_on_native_windows_is_refused`.
- Limits: the Windows launcher tests need the launcher built, which `cargo test --workspace` does and a test run of one package alone does not (the test names `cargo build -p owlshift-cli --bin owlshift-launch`); `cargo owl` builds `owlshift` only, so a Windows run, once native confinement lands, will need that build too; an argument full of quotes reaches the 32,767-character limit of a command line at about half its length, since `LINE` is quoted once more on the launcher's own command line; Ctrl-C through the launcher was not checked live.

**OWL-72 — how an AppContainer behaves on windows-latest (checked 2026-09-29).** OWL-72 was re-scoped to live checks before any confinement code; two follow-ups (OWL-83, OWL-84) were to rest on them, and were canceled when native Windows was set aside (decision below). Decision D9 stands: native Windows runs no agent. A throwaway program calling the Win32 API through `windows-sys` ran in a temporary workflow on the OWL-72 branch, removed before the pull request, on windows-latest (Windows Server 2025, 10.0.26100.33438), in four rounds: [run 36603469888](https://github.com/pitchopp/owlshift/actions/runs/36603469888), [36604300313](https://github.com/pitchopp/owlshift/actions/runs/36604300313), [36604775652](https://github.com/pitchopp/owlshift/actions/runs/36604775652) and [36605235445](https://github.com/pitchopp/owlshift/actions/runs/36605235445); its source is in the pull request's commits. The secrets were fake: a gh-shaped `hosts.yml` and a sibling project's `.env` planted in the user's temporary folder, and a generic Credential Manager entry the program wrote and deleted. The container was a profile made with `CreateAppContainerProfile`, given to `CreateProcessW` as `SECURITY_CAPABILITIES` through `STARTUPINFOEXW`, as the launcher would give it.

- **Files are closed by default.** Granted nothing, the container's process read `System32` but neither the planted token nor the `.env` ("Access is denied", exit 1), itself or through a grandchild. It could not list the profile or `%APPDATA%`, nor read a file in the runner's workspace on `D:`, outside the profile. It reaches only what grants ALL APPLICATION PACKAGES (`System32`, `Program Files`) or its own SID.
- **The Credential Manager is closed.** The program and an unconfined copy of it read the entry back; the copy in the container got error 5 from `CredReadW`, with or without network capabilities, and `cmdkey /list` there listed nothing.
- **The network takes a capability; the loopback stays closed across the container's edge.** With no capability `curl` resolved no name. With `internetClient` (`S-1-15-3-1`) an HTTPS request to `example.com` got its 200; `privateNetworkClientServer` changed nothing. A listener of the host on `127.0.0.1` was not reached from the container with any set tried (none; `internetClient` and `privateNetworkClientServer`; those and `internetClientServer`), nor a listener in the container from the host; two processes in the same container did talk over the loopback. A proxy on the loopback, such as the forwarding proxy OWL-76 suggests, is out of reach: that takes a loopback exemption, which an administrator sets for the machine (`CheckNetIsolation`), not tried.
- **A granted folder needs no lowered integrity label.** The container runs at low integrity (`whoami /groups`), yet a folder granted "Modify" to its SID (`(OI)(CI)(M)`), with no label, took a new file, an append and a new folder, as a folder labelled low did. An explicit medium label with no-write-up (`S:(ML;OICI;NW;;;ME)`) on a folder inside the grant stopped the writes; an explicit no-read-up label on a file did not stop a read.
- **Speed.** On 20,000 files in 100 folders under the temporary folder, `SetNamedSecurityInfoW` added an inherited entry in 2.53 s (about 7,900 files a second), set a low label in 2.59 s, revoked the entry in 1.90 s and removed the label in 2.76 s. The probe's own build folder took 2.8 ms.

What bears on the follow-ups:

- **A plain AppContainer cannot run git.** It cannot open `NUL`: error 5 for reading, writing or both, `\\.\NUL` alike, and `cmd`'s `> NUL` fails. The device's DACL on this image is `D:(A;;0x1201bf;;;WD)(A;;FA;;;SY)(A;;FA;;;BA)(A;;0x1200a9;;;RC)`: Everyone, SYSTEM, Administrators and RESTRICTED, no ALL APPLICATION PACKAGES and no capability. Git for Windows 2.55 opens `/dev/null` at every start, so `git --version`, `status`, `add` and `commit` all died, standard input given, with `fatal: could not open '/dev/null' for reading and writing: Permission denied` (exit 128); `curl -o NUL` could not write its body (exit 23). Opening `NUL` to containers means changing that DACL as an administrator, for the whole machine.
- **Deny entries do not bind a container.** With a deny entry for its SID present on a file, or one for ALL APPLICATION PACKAGES, the container still read the file; a folder with a deny-write entry for its SID was written, emptied and renamed. A path to hide or protect inside a granted folder has to stop inheriting instead: a file whose protected DACL leaves the SID out was neither read, deleted nor renamed, and a folder whose protected DACL grants the SID read and execute only was read, but not written, appended, emptied, removed or renamed. `SetEntriesInAclW` with `REVOKE_ACCESS` removes a SID's allow entries and leaves its deny entries.
- **The launcher's program needs no grant; what it starts does.** The program `CreateProcessW` put in the container ran from the workspace, which the container cannot read. A program it started from there was refused, and ran once its folder was granted read and execute. The harness's own binary needs no grant; the tool chains it runs do.
- **A profile is needed, and deleting it leaves the grants.** `CreateProcessW` with the SID of a name no profile was made for failed with error 2. After `DeleteAppContainerProfile`, the entries naming the SID stay on every path until revoked.
- **The container joins the launcher's job and stays in its container.** Started from a process in a Job Object, its process was in that job. It could not start a process in another container, nor in its own with one more capability (error 87), and could not open the program that started it (error 5).
- **A restricted token instead.** Restricting SIDs Everyone, Users and a SID for the run, every privilege dropped but the traverse bypass, a default DACL of the user, the run's SID and SYSTEM: the profile's files, the Credential Manager and the starting program stayed closed and `NUL` opened. But git failed to start (`0xC0000142`, a DLL failed to initialise), HTTPS failed (`schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`), and the process read a file on `D:` and wrote in `C:\ProgramData` and on `D:`, where Everyone or Users may. With the logon SID among the restricting SIDs, git ran `status`, `add` and `commit` in a granted repository and the profile's files and the Credential Manager stayed closed, but the process opened the starting program and read its memory. At low integrity as well, git still ran, the memory read was refused (a query was not), writes landed only in granted folders labelled low, and HTTPS through schannel still failed.

The choices these results left were an AppContainer, once an administrator opens `NUL` to containers on the machine; a low-integrity restricted token with the logon SID, which reads whatever Everyone or Users may (as the macOS and Linux sandboxes read everything outside the home) and whose HTTPS through schannel fails; or native Windows kept refused, under WSL2 (D9).

**Decision (2026-09-29, recorded 2026-09-30, OWL-87): native Windows is set aside.** The maintainer chose the third: a confined run stays refused on native Windows, and WSL2 is the supported path (D9). The AppContainer follow-ups (OWL-83, OWL-84) and the launcher's Ctrl-C test (OWL-85) were canceled. The findings above stay as the starting point if native Windows comes back.

**The launcher is removed (decided 2026-09-30).** Whether to keep `owlshift-launch` as test-only code or delete it was the maintainer's call, and the choice is deletion: with no confinement to apply, it has no use. The removal was done on 2026-09-30 (OWL-89): the `owlshift-launch` binary and `owlshift_platform::launch` are gone, with `sandbox::wrap_line`, `sandbox::use_built_launcher`, the platform crate's `testkit` feature and the launcher's tests. On native Windows `sandbox::wrap` and `available` refuse with `Unsupported`, and so does `AgentEnv::confine_shell` for a confined gate command, directly, since `wrap` would quote the line again; the refusal tests cover both paths. A return of native Windows starts from the OWL-72 findings above and the OWL-71 record, in the history of `crates/owlshift-platform/src/launch.rs`.

**C8 — passed, with one handling rule.** Run on 2026-09-28 (OWL-12) with Claude Code 2.1.283, codex-cli 0.154.0 and git 2.54.0 on macOS. Logged-out states were produced with an empty `CLAUDE_CONFIG_DIR` or `CODEX_HOME` in a scratch directory; the API-key state with a dummy key in a scratch `CODEX_HOME`. Both commands answer in about 0.1 s, with no network wait observed.

- `claude auth status` prints JSON on stdout (`--json` is the default). Logged in: exit 0, `loggedIn: true`, `authMethod: "claude.ai"`, `subscriptionType: "max"`. Logged out: exit 1, `loggedIn: false`, `authMethod: "none"`; the `--text` form says "Not logged in. Run claude auth login to authenticate." With only `ANTHROPIC_API_KEY` set: exit 0, `authMethod: "api_key"`, `apiKeySource: "ANTHROPIC_API_KEY"`. The logged-in JSON also carries the account's e-mail address, organisation id and name: personal data, which Owlshift does not deserialize.

- `git --version` prints `git version 2.54.0 (Apple Git-157)`; the version is the third word.

## Repository & workspace layout

One repository, a Cargo workspace of six shipped crates split along the design's boundaries, so the pure core never depends on I/O, plus one test-only crate.

| Crate | Holds | Depends on |
| --- | --- | --- |
| `owlshift-core` | Ticket, pipeline, stage, gate, resource; state machine; scheduler; policy. Pure functions, no I/O | `serde` and `schemars`, for derives only (the shared vocabulary) |
| `owlshift-contracts` | Brief, `result.json`, project and personal config, events, git ref layout, format versions; JSON Schemas generated from the types | core |
| `owlshift-adapters` | Tracker (Linear, plus the Markdown test tracker), forge (GitHub), harness (Claude Code; Codex in P5), notifier; each behind a trait with declared capabilities | contracts |
| `owlshift-platform` | Service install and uninstall, process groups and Job Objects, keychain, platform directories, keep-awake | nothing |
| `owlshift-runner` | Daemon loop, executor (worktrees, spawning, isolation check), writer, local store (SQLite) | all of the above |
| `owlshift-cli` | The `owlshift` binary | runner |
| `owlshift-testkit` | Test only, never published and never a dependency of a shipped crate: the fake harness program, hermetic git and the bare-remote fixture, the scenario format and runner, and the scenario tests. It is a crate of its own because Cargo gives a binary's path only to the integration tests of its own package | core, contracts, adapters, runner (the executor it tests), platform |

Beside the crates: `roles/` (default role prompts in Markdown, versioned with the contract), `schemas/` (generated JSON Schemas), `tests/scenarios/` (S1 to S17 with their fixtures, played by the testkit), `docs/`.

**Git through the `git` CLI**, not a library: worktrees, pushes and credential helpers then behave exactly as in the user's own terminal. **Harnesses through their own CLI**, never through a model API: the user's subscription login is what runs. Library choices (async runtime, HTTP client, SQLite binding, CLI parser, keychain access) are made at implementation time against current documentation. Made so far: the HTTP client and keychain access (OWL-13, see C4 in the results).

## Contracts to write first

Six contracts are written, versioned and schema-checked before any logic, because every component and every future adapter talks through them.

1. **Brief** (runner to role): format version, role, the ticket (text from anyone but the decider quoted as data), the decider, the numbered question-and-answer thread with authors marked, the checkpoint (plan, ledger), resources and zones, the project rules injected for those zones (a rule that names no zone applies to the whole repository; OWL-61), permitted actions, the project's gate commands (from `stack.gate`, so a role never reads the project config or guesses the gate from the repository; OWL-37), the failure of the runner's own run of that gate after the previous Build `done` (`gate_failure`: the failing command, a one-line reason and the end of its output, quoted as data; OWL-16), why the runner refused the previous Build run's `result.json` in the same command (`result_refusal`; OWL-180), and where to write the result.
2. **`result.json`** (role to runner): validated against its JSON Schema, unknown fields rejected, an exit code never trusted in its place.
3. **Project and personal config**: TOML, with published JSON Schemas so editors complete and check them.
4. **Events**: timestamp, project, ticket, run, kind, data; the one stream behind logs, `why`, the UI and usage reports.
5. **Git ref layout**: `refs/owlshift/claims/<ticket>` holds the lease (holder machine, operator, expiry, format); `refs/owlshift/tickets/<ticket>` points to a commit whose tree holds the stage, plan, ledger, questions and findings.
6. **Marked comments**: a first line such as `[owlshift] QUESTIONS · round 2`, plus a machine-readable footer where the tracker can hide it; exact form checked per tracker.

The contracts live in `owlshift-contracts`; their JSON Schemas are generated into `schemas/`, and a test fails when a committed schema drifts from the types (`OWLSHIFT_UPDATE_SCHEMAS=1` rewrites them). The first cut of `result.json` below is format 1, kept as written; the reference is now [`schemas/result.schema.json`](../../schemas/result.schema.json). Refinements made while writing it (OWL-9): question ids are `Q1` to `Qn` in order, in every result, whatever ids the thread's earlier rounds used (OWL-180); `status: questions` needs at least one question; `pr` is allowed only with `status: done`; a follow-up carries `title`, `why`, `evidence`, `source` (`agent`, `reviewer` or `ci`), `done_when` and `blocked_by_parent`; `artifacts` may name `plan`, `ledger`, `findings` and `report`. A document with a newer `format` is refused with an "upgrade" error. Format 2 (OWL-23) adds the answer check's `verdicts`: one per question of the thread's latest ask (its last `questions` or `reask` entry, so after a re-ask only the re-asked questions), in question order, each with the `question` id, a `class` from the four of the answer check in [architecture.md](architecture.md) (`answered`, `partial`, `unanswered`, `counter_question`) and a `reason` that is not blank; only with `status: done`. The coverage rule needs the brief, so it is checked against it (`RunResult::validate_against`, run by the executor on every result), which also refuses verdicts from any role other than `answer_check`. Format 3 (OWL-115) adds a verdict's `reply`, the answer check's answer to a counter-question, which the runner posts as written ([architecture.md](architecture.md), "Answer check"): required on a `counter_question` verdict, refused on any other class, a string that is not blank, never `null`. A check that leaves it out fails like any invalid result, as a verdict without a reason does. The schema carries the rule as an `if`/`then`/`else` on the verdict. The schema cannot see the file system, so the runner reads each artifact without following any symbolic link (OWL-26): a link anywhere between the worktree and the file, even one pointing back inside, fails the run with an error naming the field. A hard link is the same leak with nothing to see (OWL-36): an artifact file whose link count is not exactly 1 fails the run the same way, wherever its other names are, since finding them would take a search of the whole volume; a count of 0 is a file deleted after it was opened. The count is read on the handle the artifact is then read from (`fstat` on Unix, `GetFileInformationByHandle` on Windows), so the file checked is the file read. That does not stop the count from changing between the open and the check: a process removing the inside name of a hard link to an outside file in that window leaves a count of 1. What closes that window is the executor stopping the run's whole process tree before the artifacts are read (OWL-15), so no process of the run is alive at read time. Known limits: a process that escaped the tree, and a network or FUSE mount that supports hard links but reports a count of 1. No legitimate artifact has a second name: checked on 2026-09-28 with git 2.54.0, a checkout made by `git worktree add` holds no file with more than one link outside `.git` (`find . -path ./.git -prune -o -path ./target -prune -o -type f -links +1 -print` printed nothing). It also reads at most 1 MiB of each artifact (OWL-35): an artifact seen to hold more before its end, whether huge, sparse or still growing, fails the run with an error naming the field, after reading one byte past the limit and no more. Artifacts are text a model writes, far below 1 MiB; the limit keeps a faulty or hostile role from exhausting the runner's memory or keeping it reading.

The first cut:

```json
{
  "format": 1,
  "status": "questions",
  "summary": "Plan drafted; two choices need the decider.",
  "questions": [
    {
      "id": "Q1",
      "category": "scope",
      "context": "The ticket asks for X; the code already does Y in module Z.",
      "text": "Extend Y, or build X separately?",
      "options": ["Extend Y", "Build X separately"],
      "recommendation": "Extend Y"
    }
  ],
  "decisions": [
    { "question": "Test framework", "decision": "Reuse the existing one", "basis": "Project convention" }
  ],
  "followups": [],
  "artifacts": { "plan": "plan.md", "ledger": "ledger.json" },
  "pr": null
}
```

`status` takes one of `done`, `questions`, `blocked`, `premise_false` or `failed`. When `status` is `done` after Verify, `pr` carries the branch, title and body; the runner opens the PR itself. A run stopped by a usage limit is not a `result.json` status: the runner detects it from the CLI output and records it as an interruption to resume.

## CLI surface for P0 and P1

Everything runs in the foreground; `continue` arrives in P2, `watch` in P3, the background service and its `start`, `stop` and `uninstall` commands in P7, with `pause` and `resume` for its dispatch.

| Command | Step | Behaviour |
| --- | --- | --- |
| `owlshift --version` | P0 | Version and format versions |
| `owlshift doctor [--json]` | P0 | git version, `claude` and `codex` installed, `codex` logged in (a warning until P5), the agent runs' Claude Code token stored, capabilities of the configured adapters, a Linear project's `[tracker].states` among its team's workflow states; why each problem matters and how to fix it |
| `owlshift config show` | P0 | Effective configuration and the origin of each value |
| `owlshift init` | P1 | Writes a commented `owlshift.toml` for the repository (`--tracker`, `--team`, `--gate`), then stores the tracker and forge secrets and the agent runs' Claude Code token in the system keychain (`--skip-secrets`, `--replace-secrets`) |
| `owlshift do TICKET` | P1 | Runs one ticket to a verified PR, in the foreground |
| `owlshift continue TICKET` | P2 | Picks a ticket up once its decider has answered, after the quiet window, or restarts a parked one (OWL-122, named by OWL-127) |
| `owlshift watch` | P3 | Continues each ticket whose questions wait, in the foreground, once its decider's reply counts, until Ctrl-C (OWL-152) |
| `owlshift logs [TICKET] [--last N] [--follow]` | P1 | Events, with the directory of each run's logs |

**What `doctor` checks, as built in P0 (OWL-12).**

- **Harnesses.** The ones declared under `[harnesses]` in the personal file are checked; when none are declared, both `claude` and `codex` are. Each must be on the `PATH`, and Codex logged in, following the rules of check C8. Until review roles exist (P5), a Codex that is missing, logged out or unreadable is a warning, not a failure (OWL-102): `owlshift do` does not run Codex, so the machine is ready without it, and the note under the line says so and how to get Codex ready. P5 makes it a failure again once a configured role uses Codex; the single place in doctor that decides this holds the condition. Claude Code's own login is information only (OWL-97): agent runs log in with the token the next check looks for, never with the operator's own login, so doctor still reads `claude auth status` and shows that login's state on the `claude` line, but a logged-out login, or one it cannot read, is a `·` line, not a failure, and has no fix. At an untested version, the line is a warning, as below.
- **Agent login (OWL-94).** When `claude` is required and found on the `PATH`, the `claude agent login` line says whether the token agent runs log in with is in the system keychain (service `owlshift`, account `claude-agent`). Only its presence is asked (`Keychain::contains`); the value is never returned, though the macOS Keychain reads the entry to answer and may ask to allow it, as for `do`. Absent: a failure, fixed by `claude setup-token`, then `owlshift init` (`--replace-secrets` replaces a stored one, which `do` names when a run is refused). A keychain that cannot be read: a failure, naming why. Whether the token still works shows at the first run, since `claude auth status` does not check it. With no `claude` found, its own line fails and the token is not asked, which also keeps the CLI's tests, whose `PATH` has no `claude`, away from the real keychain.
- **Harness versions.** A version outside the harness's tested list (`crates/owlshift-adapters/src/harness/tested.rs`), or one doctor cannot read, is a warning, not a failure (OWL-29). Matching is exact: a suffixed build such as `2.1.283-beta.1` is not the release `2.1.283`. A version is listed once the harness contract tests pass on output recorded with it, and the Claude contract tests fail when a recorded fixture carries a version the list lacks. The list only grows. Codex has no contract tests yet, so no Codex version is tested and doctor says so.
- **Configuration files.** The project file is `owlshift.toml` at the root of the git repository holding the current directory. The personal file's location is given in [runtime & operations](runtime-and-operations.md#install-lifecycle--uninstall).
- **Adapters.** Doctor names the configured tracker and the capabilities its adapter declares, from constants, without opening the tracker or the keychain. A required capability the build does not implement yet is a warning, not a failure: `owlshift do` needs only to read tickets and comments, and refusing a project is `init`'s job (OWL-13). Adapter traits exist from a kind's second implementation; a capability contract is frozen only once three exist (principle 8), and may change until then.
- **Tracker states (OWL-147, decided 2026-10-04).** For a Linear project only, a `tracker states` line checks that each state named under `[tracker].states` is exactly one workflow state of the `[tracker].team` team, by the rule the stage moves by (`linear::find_state`: exact name, case included, once). Every key set there is checked, one added later included. `admit = { state }` is not checked yet: admission is not built. It is doctor's one check that leaves the machine: it reads the Linear API key in the system keychain (`Keychain::read`, once, which on macOS may ask to allow the access, as for `do` and the agent login) and the team's states from Linear (`LinearTracker::team_states`, one query, read only, 50 states at most). This reverses the earlier choice to keep doctor off the tracker secret, accepted because a misnamed state otherwise shows only as a `stage_not_moved` warning event on each move. A name that matches no state, or several, is a warning, since a failed move never stops `do`; its note lists the team's states and, for a shared name, says to make it unique in Linear. What stops `do` from reading the ticket at all is a failure: no key stored (fix: `owlshift init`), a key Linear refuses (`owlshift init --replace-secrets`), a keychain doctor cannot read, a team key Linear does not know (fix `[tracker].team`). Linear out of reach, or any other error, is a warning that nothing was checked. Only state names, the team key and Linear's error text reach the report, never the key. The doctor unit tests answer through `System::linear_states`, faked; the CLI's tests run doctor outside any project, so they reach neither the keychain nor the network.
- **Data directory (OWL-109).** A `·` line in the Project section, `data directory`, prints the path where `owlshift do` keeps its event log, its dedicated checkouts and its worktrees (`owlshift_platform::paths::data_dir`), written with `~` for the home folder, and says `from OWLSHIFT_DATA_DIR` when that variable sets it. When the system has none, the line says so and to set `OWLSHIFT_DATA_DIR` to an absolute path, as `owlshift logs` does. It is information only, never a warning or a failure, and changes neither the exit status nor what blocks `do`. Doctor only reports the path: it does not open, create or list the folder. The JSON report carries the same line.
- **Exit status.** A failed check makes the exit status 1, in text and in JSON. Warnings do not: none blocks `owlshift do`.

**How `doctor` reports, as reworked in OWL-99.** A new user's first command has to say what blocks them and how to get past it without reading the code.

- **Sections.** Tools (git, the harnesses), Agent isolation (sandbox, sentinel, sentinel test, agent login), Project (project and personal configuration, tracker, tracker states on a Linear project, data directory), under a header naming the version and the operating system. One line per check: a symbol, the subject, the detail. `✓` ok, `!` warning, `✗` failure, `·` information.
- **Warnings** carry a note under their line: that they do not block `owlshift do`, and why, with what to do if anything.
- **Summary.** After a rule: when a check failed, `✗ Not ready: N problems to fix before owlshift do`, then one numbered block per failure: **Why** (what breaks and why the check exists) and **Fix** (numbered steps, each command whole on its own line with its note after it, ending with `owlshift doctor` to check). Only failures are counted: a Codex that is not ready is a warning before P5 (above), so it does not make the machine not ready. When nothing failed: ready, and the next command: `owlshift do TICKET` when the project has its `owlshift.toml`, `owlshift init` in a repository without one, `owlshift doctor` again from the project's repository when run outside one. Doctor does not look for the forge secret, nor for the tracker's but on a Linear project (the tracker states line above), since each keychain read may prompt on macOS, so the `do` line adds that `owlshift init` stores a secret `do` says is missing.
- **Every failure carries a why and at least one step**, and every warning its note: the doctor unit tests check this on every report they build, so a new failure path without them fails the test that reaches it.
- **Layout.** Colour (ANSI) only when standard output is a terminal, `NO_COLOR` is unset or empty (no-color.org), `TERM` is not `dumb`, and not on native Windows. Text wraps at the terminal's width (read with `tcgetwinsize`, the `termios` feature of rustix, no new crate), 80 columns when standard output is not a terminal, 40 at least; widths are counted in characters. A command, and a span in backticks, is never broken. A path under the home folder is written `~`, whole components only. Everything is escaped as in `logs` (`printable`) before it is wrapped, so no control character or bidirectional override from the machine reaches the terminal.
- **`--json`.** The same report for scripts and the P8 web UI: `owlshift` (the version), `ready`, `problems`, `next` (`do`, `init` or `from_repository`, `null` until ready) and `checks`, each with `status` (`ok`, `info`, `warn`, `fail`), `section` (`tools`, `agent_isolation`, `project`), `subject`, `detail`, `why` (`null` for ok and info) and `fix`, a list of `{"run": command, "note": text or null}` and `{"do": text}` steps. The closing `owlshift doctor` step is the text's own. Strings are as the checks wrote them, `~` included: escaping them for a terminal or a page is the reader's job.

**The test tracker** (published as the Markdown tracker in P9) keeps one folder per ticket in the repository: `tickets/PROJ-1/ticket.md` with a front matter and the description, and `tickets/PROJ-1/comments/` with one file per comment, named by timestamp and author. Answering a question is adding a file; everything stays diffable in git. The format, as built in P0 (OWL-11):

- `ticket.md` opens with a TOML front matter between two `+++` lines, then the description. Keys: `title`, `author`, `stage` (the visible stage: a state name as mapped under `[tracker].states`), `priority` (`urgent`, `high`, `medium`, `low` or `unset`, the default), `assignee` (optional: the decider), `labels` and `blocked_by` (ticket ids), both empty by default. An unknown key is refused. TOML keeps the project to one configuration language; the choice is revisited before the tracker is published in P9, where YAML front matter is the wider convention.
- A comment is `comments/<YYYYMMDDTHHMMSSZ>-<author>.md`: the UTC time in ISO 8601 basic format, which has no colon (Windows refuses one in a file name) and sorts in time order, then the author (ASCII letters, digits, `_` and `-`). The body is the file's content. Several comments can share a second, as on Linear, which keeps milliseconds (OWL-133). The first comment of a second has no suffix. The n-th one carries `.<n>` right after the time (`20261003T101500Z.2-owlshift.md`), with n from 2 to 1,000,000 and no leading zero. Its id is the name without `.md`. The `.` is outside the author alphabet, so an author made of digits and `-` still parses unambiguously. Posting takes the next n of that second, whoever wrote the comments already there. Comments read in order of time, then n, then file name. A comment's time is its second plus n − 1 microseconds (OWL-136, "The answer check", "When it runs"), so the times order the comments as they read, and posting past the millionth comment of a second is an error; files of one second without a suffix, written before it, share the second's time. A file is never overwritten: a poster that finds its name already taken gets an error. Two posters racing on one ticket may therefore tie on an n, and so on a time.
- Changing the visible stage rewrites the `stage` line of the front matter and nothing else, a one-line diff.
- A malformed file is refused with an error that names it.

**The test bench** (OWL-11) lives in `owlshift-testkit` and plays a ticket end to end without a model, a network or a tracker account.

- **The fake harness**, `owlshift-fake-harness --brief <brief.json> --reply <reply.toml>`, runs in the worktree like a real harness. The reply says what to do, in this order: wait (`delay_ms`); create and switch to another branch (`switch_branch`); write files (`files`) and commit them (`commit`, dated `date`, which the scenario runner sets to the virtual clock); write files in the main checkout (`main_checkout`); copy a prepared `result.json`, valid or not, to the brief's result path (`result`); print (`stdout`, `stderr`), or report a usage limit (`usage_limit`, a reset time: it prints `owlshift-fake-harness: usage limit reached · resets <time>` on stderr and writes no result); exit (`exit_code`: 0 by default, 1 with a usage limit). It is a compiled program, not a script, so it behaves the same on the three platforms. `switch_branch` and `main_checkout` break isolation on purpose.
- **A scenario** is a TOML file in `tests/scenarios/` with a fixture folder beside it (named after the file, or by its optional `fixture = "<name>"` key, a sibling folder: a scenario on another one's setup brings only its own prepared results, added to that folder under names of their own): the project repository, seeded as `main` into a local bare remote, and the prepared results. Its steps are `dispatch`, `run` (a reply for the fake harness), `comment` (a person comments), `answer` (a reply for the fake harness, run as the answer check: "The answer check" below) and `resolve` (a reply for the fake harness, run as the resolver: "The resolver" below). Any step can carry expectations on the core state (stage, waiting, round, re-asks, failed runs), the last brief (its authors, its entries in order, its latest ask, its decisions, the questions it gives the resolver), the tracker (visible stage, comments, text the last one holds or lacks) and the remote (branch pushed, file contents); a failed expectation names the scenario, the step, the expected and the found value. Time is virtual, the scenario's start plus one minute per step, so a run is reproducible to the byte. An optional `timeout_ms` sets the executor's deadline for each run and for the gate, 60 s by default; an optional `gate` replaces the fixture's `stack.gate`, so short scenarios share a fixture; an optional `runner_env` adds variables to the runner's environment the agent environment is built from, which the fixture's `stack.gate_env` picks from (OWL-44); a fixture's optional `personal.toml`, the operator's personal file, holds the `allow_gate_env` that declaration is checked against, as when the configuration is loaded (OWL-63). `a_declared_variable_reaches_the_gate` gives its gate `git --config-env=owlshift.probe=OWLSHIFT_GATE_PROBE config --get owlshift.probe`, which needs the variable the same way under sh and cmd: checked on 2026-09-29 with git 2.54.0, it prints the value when the variable is set and exits 128 with "missing environment variable" when it is not; the scenario fails the same way when the fixture stops declaring it, and does not start when the fixture's personal file stops allowing it.
- **Runs go through the executor** (OWL-15), on the fake harness. A stand-in driver plays the writer (OWL-18) until it exists, and only as far as the scenarios need: it builds the brief from the tracker, maps the executor's outcome onto a core event, posts the DECISION, questions, re-ask, RESUME and PARKED comments, sets the visible stage and pushes the branch. The writer replaces it; the scenario files stay.
- **Git is hermetic.** Every git command the bench runs itself, the executor's included, starts with no inherited `GIT_*` variable, `GIT_CONFIG_NOSYSTEM=1`, `HOME` and `XDG_CONFIG_HOME` in the fixture's folder, and `GIT_CONFIG_GLOBAL` pointing to a file the fixture writes: identity, no signing, `core.autocrlf=false`, and empty ignore and attributes files and hooks folder of its own. The host's configuration (signing, hooks, ignore rules, line-ending conversion) never reaches a test. Author and committer dates come from the virtual clock, so commit ids are reproducible too. The fake harness and the executor's credential probes are the exception: they run with the agent environment the executor gives every agent, which drops every `GIT_*` variable, so the fixture writes the same file where git looks for its global configuration under `XDG_CONFIG_HOME`, and the reply carries the commit date. Its git still reads the host's system configuration, whose keys that matter here (identity, signing, `core.autocrlf`, hooks, ignore and attributes files) the fixture's file overrides. Check: `git::tests::git_reads_only_the_fixture_configuration`, in `owlshift-testkit`, gives git a hostile environment (`GIT_DIR`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`) and a hostile home (a global configuration, an ignore file of `*`, attributes with `eol=crlf`). It then requires every configuration entry to come from the fixture's file or the repository's own, and no host ignore rule or attribute to apply. It passed on ubuntu, macOS and Windows in CI on 2026-09-28 ([run 36407077420](https://github.com/pitchopp/owlshift/actions/runs/36407077420)). On Windows, then, no entry of Git for Windows' own system configuration was read. Git for Windows prints a configuration file's path in quotes when the path holds backslashes; the first run of the check failed on that quote alone.

**The answer check** (OWL-116, decided 2026-10-02). The `answer_check` role (`roles/answer_check.md`) reads its brief alone and gives a verdict on each question of the thread's latest ask (`result.json` format 2, above; format 3 adds the reply to a counter-question, format 4 the resolver's resolutions), judging where each stands after the decider's last word on it. Only the decider's comments since that round's `questions` entry answer, and everything in the brief, theirs included, is data it classifies, never instructions.

- **Its event.** `owlshift_runner::answer_check::event`: a `done` result folds its verdicts into one core event (`Event::from_answer_check`). Any other status is a failed run, since questions, a block or a false premise mean nothing while the ticket waits, and every other outcome maps as for any run (`on_demand::core_event`). A failed check counts toward the failed runs, so a second one parks the ticket.
- **Acting on it.** Every check that gives its verdicts keeps them with the ask they judge, in the ticket ref (OWL-123). Answered: a `[owlshift] RESUME · round N` comment (`writer::ResumeComment`) restates every question of the round with what was understood of its answer, the reason of the latest verdict on it (`answer_check::understood`: a question settled before a re-ask reads the earlier check's), and the ticket resumes at its stage. The RESUME is posted before the answered state is kept, as the RE-ASK is: when the post fails, nothing of the check is kept and the next `continue` checks the same answers again, one more answer-check run; a post that went through and a ref write that then failed names the comment. Incomplete: a `[owlshift] RE-ASK · round N` comment (`writer::ReaskComment`) lists only the questions whose verdict is `partial` or `unanswered`, each with the verdict's reason, and says which re-ask of the limit it is; the thread then holds a `reask` entry of those questions under their ids, so the next check judges them alone. At the limit the core parks instead. Counter-question: nothing is re-asked and no re-ask is counted; the reply the check wrote with each `counter_question` verdict (format 3) is posted in a `[owlshift] REPLY` comment (`writer::ReplyComment`, OWL-128), and the ticket keeps waiting for the decider. One REPLY per check, each counter-question under its question id with its text and the reply, flattened, as one RE-ASK holds every open question: the decider reads one answer to one comment. The pairs come from the latest ask (`answer_check::counter_replies`). The REPLY is posted before the check is kept, as the RE-ASK is: when the post fails, nothing of the check is kept and the next `continue` checks the same answers again; a post that went through and a ref write that then failed names the comment, and the next `continue` may post a second REPLY.
- **Parking** (OWL-123). Every park, of a Build run or of an answer check, at the re-ask limit, after a second failed run, on a block or a breach, posts a `[owlshift] PARKED` comment (`writer::ParkedComment`): the reason; the last failure or what a blocked run said, flattened; at the re-ask limit, the round's questions still open with the verdicts' reasons; and what restarts the ticket. That is `owlshift continue TICKET` when a ticket ref keeps its state, after answering the open questions at the re-ask limit, and `owlshift do TICKET` when no round was ever asked, so nothing was kept and `do` runs it again. After a breach the comment keeps what the run changed off the ticket, since it describes the runner's machine, and says a person checks that machine first, Owlshift refusing the project there until the quarantine is cleared, then runs `continue`, or `do` if the project's checkout was deleted (which loses the ticket ref). The comment is posted after the parked state is kept, and also when keeping it failed, as when a run that broke isolation moved the ticket ref: the ticket stopped either way. A post that failed leaves the park as it is, and `do` or `continue` says so (`Stop::Parked`'s `unposted`).
- **When it runs.** Once answers arrive: a decider comment newer than the latest ask, or than the comments the last check that gave its verdicts read (`answer_check::new_answer`; OWL-122 widened OWL-116's "the last check that found a counter-question" to every check with verdicts, so an answer already judged is never judged again on its own, after a restart included). Newer is the comment's last edit against the ask comment's time, both the tracker's, never this machine's clock, and a comment is the decider's as the brief marks it. A failed, interrupted or quarantined check reads nothing, so the next one runs on the same answers. Then the decider's reply must count: the quiet window, or `go` (OWL-127, below). Decided on 2026-10-04 (OWL-136): those times are compared at the tracker's own precision, and they order the comments of one second, so an answer posted in the same second as its ask, or as the comment the last check read, is newer and reads after the ask in the brief's thread. That is a requirement on every tracker adapter (`tracker::Comment::created_at`): Linear's times keep milliseconds (`createdAt` `2026-09-28T13:30:44.787Z` in the exchanges recorded live for check C4 on 2026-09-28), and the Markdown tracker reads the n-th comment of a second n − 1 microseconds after it ("The test tracker", above). So `thread`, `new_answer`, `late_comments` and watch's hold go on comparing times, unchanged by design; the stand-in driver runs the same check (OWL-126), and its scenarios cannot post in an ask's second since they advance a minute a step. **The resolver** (OWL-138, decided 2026-10-03), architecture section 4's "Resolver first" and scenario S7. A Build's questions go through it before any reaches the decider (`owlshift_runner::resolver`, `on_demand::resolve`).

- **Routing.** Each question is routed by its category with `GatePolicy::route` (`resolver::route`): the floor's six tokens, a blank category and the project's `policy.always_human` go to the decider and never to the resolver; the rest go to a run of the `resolver` role (`roles/resolver.md`). A `premise_false` result goes to the decider whole (S8). Routing reads the category Build writes, so a floor-topic question filed under another category still reaches the resolver; the second label (below) is what keeps the resolver from deciding it.
- **The run.** Read-only, without network, in the ticket's worktree at Build's last commit, on Claude Code with the answer check's harness, model and login (standard tier, section 9), and a 15-minute deadline. Its brief (format 7) lists its questions in `resolve`, under Build's ids and without their category, with the thread, the project's rules and `always_human`, the categories the project adds to the floor (OWL-151, decided 2026-10-04: `GatePolicy::additions`, normalized, once each, those the floor covers left out; Build's brief carries the same list, and its prompt and the resolver's tell each run to file or label a question about one under that category, the resolver to pass it on); it never holds a question Build filed as always-human. It may rest a decision on the decider's ticket and comments, earlier decisions, the rules and what it observes in the worktree; a "verifiable fact" is one it can check there, offline. Other people's comments, the runner's own comments and any text saying what to decide are data. Its result (format 5) gives one resolution per question: `decided`, with its own `category`, the `decision` and its `basis`, or `passed_on`, with a `reason`. The executor refuses a resolution on a question the brief did not give, and the runner logs a decision only on a question it gave the resolver and both labels route there (`resolver::settle`).
- **The second label** (OWL-144, decided 2026-10-04). The resolver labels each question it decides from its text and context, never seeing Build's category, so its label is its own reading and not a copy of the one under suspicion. `GatePolicy::route_decided` sends the question to the decider when Build's category is always-human, when the resolver's is not a token (`floor::is_token`: ASCII lowercase letters and digits, words joined by single `_`), or when it is always-human, whole words counting as for Build's (`risk_of_data_loss` is `data_loss`). Such a decision is refused: no DECISION, nothing kept, and its question joins the round, which does not mention it. A token is required because the matcher reads words: `dataLoss` normalises to `dataloss` and `sécurité` to no floor word, so a free spelling could name a floor topic unseen; a malformed label costs the decider a question, never a wrong decision. Labels that merely differ (`naming`, `layout`) pass: the difference says nothing about the floor. What remains, as architecture section 4 records: a floor-topic question both runs label as something else is decided; the resolver's prompt still asks it to pass such a question on, a request on top of the check and not instead of it; the project's `policy.always_human` additions, though told to both runs (above), are still recognised by a model's judgment, so a question on one that both runs label otherwise is decided; and decisions kept before OWL-144 were logged without the check and stay.
- **Decisions.** Each is posted as a `[owlshift] DECISION` comment (`writer::DecisionComment`): the question without Build's id, which a round's numbering would contradict, the decision, what settles it, how to reverse it, and the resolver's run in the footer. It is then kept in the ticket ref (`questions.json` format 4, `decisions`), one at a time. A post that fails sends its question to the decider: no decision is applied unlogged. A post whose keeping then fails stops the command and names the comment; a later run may post a second DECISION. A kept decision makes the ticket ref even when no round opens, an exception to "makes no ticket ref until a round opens" (`owlshift do` above): `continue` then runs Build at Build, and `do` starts from Ready keeping the decisions. Each kept decision takes the place of its comment in every later brief's thread as a `decision` entry, built from the ref alone: a comment that only looks like a DECISION, whoever wrote it, stays a comment read as Owlshift's, never a decision. Build follows a `decision` as the answer to its question, and a decider comment that says otherwise overrides it, wherever it sits in the thread (`roles/build.md`). The delivery report lists every kept decision among the decisions taken without a human. Deleting the dedicated checkout loses the kept decisions with the asks: their comments stay on the ticket as the runner's plain comments.
- **What is left.** Always-human questions, passed-on ones and those whose DECISION was not posted go to the decider as the round, in Build's order, renumbered Q1..Qn as a round must be; the QUESTIONS comment says how many others were decided. The core's `Questions` is applied only then: the ticket stays at Build through the resolver. When nothing is left, Build runs again in the same command, with no stop and no counter moved, and without the quiet window of `continue` (OWL-127), which holds a round's answers only: no reply is awaited. After `MAX_RESOLVED_PASSES` (3, `owlshift_core::state`) such runs in a row in one command, the next run's questions all go to the decider, which architecture section 4 records as the bound on "Resolver first".
- **Fallback.** No other harness can take over yet (P6, and a deviation from section 9's fallbacks): a resolver at its usage limit, a failed one, one without a valid result or past its deadline sends every question to the decider in a normal round, which says why. A resolver that breaks isolation is quarantined and parks the ticket; its restart runs Build again from its checkpoint, which asks again.
- **Events.** A `gate` event for each routing that reaches the resolver or its bound: `resolver` (`done`, `usage_limit`, `failed` or `pass_limit`), `raised_by` and `run`, and the question ids `given`, `decided`, `to_decider` and, after a run, `passed_on`, `refused` (decisions the second label refused) and `unposted`, the last two also in `to_decider`. A `tracker_write` for each DECISION names its `question`, and the round's `gate` event names Build's ids of the questions it asks (`raised_as`).
- **Deviation from scenario S7.** "Replying to that comment reverses it and starts a correction run": in P2 nothing watches the ticket, so a reversal takes effect at the next run on it (Build after the round's answers, or a new `do`), which reads the decider's comment over the decision. The automatic correction run comes with P3's watch.
- **Who runs it.** `do` and `continue`, and in the scenarios the stand-in driver's `resolve` step, with the same pieces and without the bound, which is per command. `crates/owlshift-testkit/tests/on_demand.rs` covers a decision and a round of the rest through to a delivery, a run whose questions are all decided going on without a stop and continued after a usage limit, a resolver at its usage limit, a refused DECISION, the bound and a breach, and a decision the resolver labels `data_loss` refused beside one that stands (OWL-144); `tests/scenarios/resolver.toml` plays a decision beside a project-added always-human category, then a run decided whole.

On the P2 exit gate, OWL-174 listed three open points "to be decided on the ticket before building"; its Build run decided all three, on bases such as "an example is most useful when it documents the options", and the delivery report listed them among the decisions taken without a human. The prompt let Build "decide what can be discovered", a looser bar than the resolver's, and a Build decision met neither the routing by category nor the second label, so the floor never applied.

- **The role.** `roles/build.md`: how the work is built is Build's (code structure, names, tests), and the pull request's body says what a reviewer should know. A choice of what the work delivers (its content, behaviour, interface or wording) that the ticket, the thread, the rules or the repository do not plainly settle, and every point the ticket leaves open, is a question, filed under `scope` when its answer changes what the ticket delivers. Following the decider's word, a `decision` entry or a rule is not a decision, and is listed nowhere.
- **The runner.** `RunResult::validate_against` refuses a Build `result.json` that lists `decisions`, whatever its status (`result.json` format 6; the field stays in the contract, which no role fills today). The refusal is a failed run, so nothing of it is accepted or delivered, while its commits stay on the branch; the next Build run of the command is told why (`result_refusal`, "A refused result" below): ask each choice as a question, and leave them open even though the work is committed. A retry that lists decisions again, or a `blocked` run that lists any, is one more failed run, and a second one parks the ticket. The resolver is then the only one that decides without the decider, and the delivery report's decisions are its kept ones and the runner's note of late comments given to a run (OWL-139).
- **What remains.** The runner sees only what a run reports: a choice a run makes without recording or asking it, a retry that drops its refused decisions instead of asking them included, goes unseen, and the reviewer reads the diff. Telling a choice of what the work delivers from one of how it is built stays a model's judgment. A run that would have recorded a choice now stops to ask it, at the cost of a resolver run and a Build run that asks.
- **Rejected.** The prompt alone: nothing outside the run checks it, and OWL-174's run ignored the ticket's own instruction. The resolver reviewing Build's recorded decisions before delivery: a resolver mode to confirm a choice already built, a step between the gate and delivery, a resolver run on every delivery with decisions, and the points asked after the build. A category on each Build decision, floor-labelled ones refused: the label is the run's own, with a reason to choose another.
- **Tests.** `tests/scenarios/open_points.toml` is the acceptance: a decider's ticket lists two open points; a Build run that decides them and is `done` is refused before the gate, with nothing posted; its retry, told why, asks both; the resolver decides where the README lists the example, and whether the example shows every key reaches the decider as round 1, under `scope`. `decisions_against_the_brief` (`crates/owlshift-contracts/tests/contracts.rs`) refuses a Build result with a decision under every status and passes one without.

**The Claude Code harness adapter** (OWL-14), in `owlshift-adapters::harness::claude`, runs one role with `claude -p` on the user's own login, following the OWL-14 results above.

- **Split with the executor.** `command` builds the invocation for a request (working directory, model, effort, permissions, result path, an optional JSON Schema, an optional dollar cap passed as `--max-budget-usd`, from the personal file's `budget_usd`: a dollar cap on each run of a harness, not on a day's total, whatever the billing, [runtime and operations](runtime-and-operations.md#configuration)); the executor spawns it in its own process group or Job Object and hands the child to `drive`, which writes the prompt on standard input, streams every output line to a callback (the executor's run log) and returns the run. The executor stops a run by stopping the process group; `drive` returns at most two seconds after the child exits, even when a process it started holds the output open.
- **Permissions.** Read-only is `dontAsk` plus an allow rule for the result file alone; write in worktree is `acceptEdits` plus Bash; no network removes the web tools; a browser is refused. A result path that would be a pattern in a rule (anything but ASCII letters, digits, `.`, `_`, `-` and `/`, or a `.` segment) is refused. C1's guardrail flags are always passed, and no settings file applies, the worktree's own `.claude/settings*.json` included (OWL-53); the agent environment (OWL-22 in the results above) covers what lies outside Claude Code. `Run::mcp_servers` names the servers of the `init` event.
- **Outcome.** Completed needs exit status 0 and a final record with `is_error: false`. Otherwise a usage limit still in force at the end of the stream (a `rate_limit_event` with status `rejected`, or an assistant message with `error: "rate_limit"`, not lifted by a later `allowed` report) makes the run a usage limit, with the reset time and window of the rejection when there was one, never read from the message text. Anything else is a failure: no final record, no `is_error` flag, a signal, the prompt not delivered, or an error with its API status, terminal reason and error kind. Completed means the harness finished; the role's `result.json` is still validated by the executor.
- **Usage.** Tokens, cost estimate, duration and turns come from the final record, per model too; a run without one has unknown usage, not zero. The last rate-limit report gives the window, its reset time and the five-hour and seven-day utilisation. `apiKeySource: none` means no API key: the run logged in, with the subscription token unless a gateway or provider variable reached it, which the agent environment prevents (OWL-120); any other value fails the run.
- **Tests.** Contract tests replay the scrubbed recordings in `crates/owlshift-adapters/tests/fixtures/claude/` in CI; the usage-limit one is constructed from C7's shapes until a real limit is recorded. A tiny real run is an ignored test, run by hand with `OWLSHIFT_LIVE_CLAUDE=1`.

**The executor** (OWL-15), in `owlshift-runner::executor`, turns one role into one run: `Executor::run` takes a `RunSpec` (main checkout, worktree, branch, base, run directory, brief) and a `Harness`.

- **Worktree and brief.** The ticket's worktree is created on its branch from the base, resolved to a commit first, or reused when it is the root of a linked worktree of the main checkout's repository (the same common git directory, and a top level of its own, not the main checkout's; paths compared once resolved), on that branch, at the commit the branch has there. Anything else refuses the run: a worktree on another branch, a separate clone on the right branch and commit, the main checkout itself. The branch name must be one git takes as is (`check-ref-format --branch`, no leading `-`). The run's own files live in `.owlshift/run/` in the worktree, kept out of git by a `.gitignore` of `*` in that folder, which touches nothing the worktrees share (`info/exclude` is shared): the brief, whose `result_path` the executor sets to `.owlshift/run/result.json`, the result, and the build role's plan and ledger. An earlier agent could write there, so nothing is written through a link: `.owlshift` and `.owlshift/run` must be real directories, each file is removed and then created anew, and the previous result is removed. The caller's run directory, outside the worktree, gets `stdout.log`, `stderr.log` and a copy of the brief.
- **The base** (OWL-51, decided 2026-09-29). The isolation check leaves the remote-tracking refs out (below), so a run can move `origin/main`, or make it or `origin/HEAD` point elsewhere, unseen. The next run does not start there: its caller fetches, then passes `RunSpec.base` as a commit resolved after that fetch, as `owlshift do` does (`project::sync_checkout`, see "The project's rules" under OWL-20). The check is not extended to `origin`'s default branch instead: the runner's own fetches for other runs write remote-tracking refs during a run (see "What P6 holds to"), so a moved ref could not be blamed on the run, and the next fetch resets it anyway. One shape survives the fetch: a remote-tracking branch made symbolic, pointing at another branch of origin, which git follows; `sync_checkout` refuses a default branch in that shape. Checked on 2026-09-29 with git 2.54 on a clone of a local bare repository: `fetch --prune` put back a moved and a deleted `refs/remotes/origin/main` and pruned a planted `refs/remotes/origin/evil`, `remote set-head origin --auto` pointed `origin/HEAD` back at `origin/main` from it, but a `refs/remotes/origin/main` made symbolic to `refs/remotes/origin/topic` stayed symbolic, and `rev-parse` then gave `topic`'s commit. The executor takes `RunSpec.base` as a full commit id or as a remote-tracking name looked up as exactly `refs/remotes/<name>` (`show-ref --verify`), then peeled to a commit; an abbreviated id, a local branch name and a revision expression are refused (OWL-66). Checked on 2026-09-29 with git 2.54: `rev-parse origin/main` gave a planted `refs/heads/origin/main`; `rev-parse refs/remotes/origin/main`, with that ref absent, gave a planted `refs/heads/refs/remotes/origin/main`; `show-ref --verify` refused the absent ref and `origin/main~1`; a full commit id resolved to itself despite a branch of that name.
- **Before the spawn.** `AgentEnv::check` runs in the worktree for the forge hosts, and a finding refuses the run. The caller builds the `AgentEnv` with the project's declared variables (`stack.gate_env`, OWL-44) and the operator's `allow_gate_env` (OWL-63), and names the forge hosts (OWL-20). Whatever fails up to the spawn (worktree, run files, credentials, the first snapshot, the command) is an error of `run`: nothing ran, no run is counted.
- **Spawn and stop.** A `Harness` builds its command and reads its own output; the executor sets the working directory, replaces the whole environment with the agent's, pipes the three streams and spawns the command as the root of a `ProcessTree`. A watchdog thread stops the tree at the executor's deadline, a failed run; the tree is stopped again after every run, before the result is read, so nothing the run left running changes what is checked. `ClaudeHarness` uses the adapter's `command` and `drive`, with the role's prompt followed by one line naming the brief file; an MCP server in its `init` event fails the run. `drive_plain` serves a harness without a driver of its own, such as the fake harness. The executor's own git commands run through `owlshift_platform::process::run_command`, also as the root of a process tree, stopped after 120 s, with their whole output: the probes' 64 KiB cap would cut a large repository's status and blind the isolation check (OWL-48). The watchdog stays for the runs whose output is streamed to a log, the harness and the gate's commands.
- **Outcome**, in this order: an isolation violation quarantines the run, whatever else happened, and the core parks the ticket; then the deadline, an MCP server loaded, a usage limit (an interruption, with its reset time) and a harness failure. Otherwise the result decides: `Finished` needs the harness to report completion and a valid `result.json`, read without following a link and at most 1 MiB, validated against its contract, with `pr.branch` equal to the run's branch and every artifact readable (OWL-26, OWL-35). A harness failure with a valid result is still a failure, and so is an exit status 0 without one.
- **Isolation**, after every run. The main checkout: its HEAD commit and branch, and every entry of `git status --porcelain=v2 --untracked-files=all --ignored=matching` with the content hash of each file it lists (tracked and staged changes, untracked files, ignored ones such as `.env`; an ignored directory counts by its presence). The repository's shared `config`, `config.worktree`, `hooks/` and `info/`, where a planted hook would later run code in the user's checkout. Every ref but the run's branch and the remote-tracking refs: tags, other branches, `refs/stash`. And the worktree: still on its branch, at a commit that descends from the one the run started from, or, for a rebase, from its new base. A check that cannot run counts as a violation. Nothing is written: `--no-optional-locks`, and `hash-object` without `-w`. Before any git runs, two checks read the file system alone (OWL-59): the worktree's `.git` link (see "The worktree's `.git` link" under OWL-20 below), and the shared git files against the snapshot, from the common directory resolved before the run. A violation there ends the check with no git run, so a command a run planted in the shared configuration, such as a clean filter that `git status` of the checkout would run, never runs with the runner's environment. Every command of the runner's git, the executor's and `owlshift do`'s alike, runs with `-c core.hooksPath=<a folder that does not exist> -c core.fsmonitor=false`: no hook and no file-system monitor runs, `worktree add`'s `post-checkout` included. The rest of the runner's environment is kept, since the person's own configuration, such as `safe.directory` or what the fetch authenticates with, must still apply (decided 2026-09-29). Two ways past those checks are closed (OWL-50, decided 2026-09-29), both checked live that day with git 2.54.0. A nested repository in the main checkout, with a clean filter in its own `config`, a `* filter=<it>` attribute and a changed file, and its gitlink staged in the checkout's index (or committed), made the hardened `git status` start git in it and run the filter three times; the main checkout's status now runs with `--ignore-submodules=dirty`, which starts no git in a submodule and still lists a gitlink added or moved, where `all` hides the gitlink too and `untracked` still runs the filter. The monitor stays off in a nested git either way: `-c core.fsmonitor=false` reaches it through `GIT_CONFIG_PARAMETERS`. A `commondir` file written in the main checkout's git directory made git there read another repository's configuration, and run its filter; `commondir` is now one of the shared git files, so it stops the check before any git. The check still runs with the runner's environment, not through `Git::as_agent` as the gate's checks do: the agent environment strips credential variables, not the runner's files, which a program that did run would reach anyway; and the snapshot, taken before the run, would need the same environment for ignored files (`core.excludesFile` found through `HOME` or `XDG_CONFIG_HOME`) to compare equal. What that git can still run is what the checked configuration already named, such as a filter driver configured before the run (see the limits below); this settles the check's part of the follow-up under OWL-16.
- **Its limits.** The check assumes nobody else changes the main checkout during a run: a person editing or committing there looks like a breach. `owlshift do` (OWL-20) therefore hangs worktrees off a checkout nobody edits, a clone under Owlshift's data directory, so that a person keeps working in theirs (S12; see "`owlshift do`" below). It does not see changes outside the repository, a file inside an ignored directory, an edit inside a submodule's work tree (OWL-50; the checkout never populates one), an edit hidden by an index flag (`assume-unchanged`, `skip-worktree`), or a process that left the tree with `setsid`; confining an agent is the operating system's job (OWL-41). Its checks before any git trust the configuration they compare to be the whole of it: a file an `include.path` of the snapshot's configuration names, or a change past the first MiB of a shared file, goes unseen, and a filter driver configured before the run still runs on the checkout's changed files, with whatever script it names; the dedicated clone (OWL-20) has none of these.
- **Rebase runs and parallel runs** (OWL-49, decided 2026-09-28). The check takes two inputs the executor does not pass yet: the rebase role (P3) passes the first, the scheduler (P6) the second. A run alone still calls `Snapshot::take` and `Snapshot::check`, whose rules are unchanged.
  - *Rebase.* `Snapshot::take_rebase` names the new base, resolved to a commit when the snapshot is taken: remote-tracking refs are outside the ref check, so a name resolved after the run could be moved by the agent onto any history. After the run the branch must descend from its start, as for every run, or from that base. The start stays acceptable because a rebase that meets a conflict it cannot resolve aborts and escalates, leaving the branch as it was. Whether the run's commits were replayed is not checked: resolving a conflict changes a patch, a commit already upstream is dropped, a reword changes an id, so any such rule would quarantine good rebases. The replayed content is judged like any run's commits, by the gate, the verify stage and the review. Everything else is checked as for any run: `git rebase --update-refs` moves the branches stacked on the run's and is quarantined, so the rebase role runs without it.
  - *Parallel runs.* `Snapshot::check_among` asks the scheduler twice, just before and just after it reads the refs, for the other runs in flight at any time since the snapshot (`Concurrent`): the branches of runs still running, and those of runs that ended, each with the commit its own check verified (`Checked::tip`). A branch running in either answer is left out, its own run's check guarding it, and so is one that only the second answer knows or whose tip changed between the two. A branch that had already ended in the first answer must still be at its tip. The second answer keeps a run that starts during the check from being flagged; the first keeps a run that commits and ends after its branch was read, but before the second answer, from being held to a tip the read could not see. Tags, the stash, every other branch (a parked ticket's included), the shared git files and the main checkout are checked as for a run alone, and a breach there quarantines every run whose check sees it: the check cannot tell which run did it.
  - *What P6 holds to.* The scheduler registers a run before creating its branch. When a run's check returns, the scheduler moves that branch to the ended runs with the check's tip, and nothing touches it until every run that overlapped it has been checked. A run's branch is held to its tip only by the checks that start after its own check returned; the ones already reading leave it out. A run whose check returned no tip is quarantined and stays out of both sets, so any change to its branch is flagged. Branches are created from a commit, as the executor does: made from a remote-tracking name, a branch gets `branch.<name>` entries in the shared configuration. Worktrees stay outside the main checkout, where a new one would show in its status. The runner's own git work for other runs during a run writes only their branches and remote-tracking refs: a fetch that follows tags would write `refs/tags/`.
  - *Its limit.* A run that appends a commit to another running run's branch, without breaking that run's history rule, goes unseen: while both run, that change cannot be told apart from the other run's own work.
- **Checked live on 2026-09-28** with Claude Code 2.1.283, `haiku` at effort `low`, the adapter's flags, under `env -i HOME PATH USER LANG TMPDIR`. With either permission mapping (read-only: `dontAsk` plus `Edit(./.owlshift/run/result.json)`; write in worktree: `acceptEdits` plus Bash), a role read the brief at `.owlshift/run/brief.json`, which git reports as ignored, and wrote `.owlshift/run/result.json`: exit status 0, no permission denial, `apiKeySource: none`, no MCP server. Then `crates/owlshift-testkit/tests/executor_live.rs`, run by hand with `OWLSHIFT_LIVE_CLAUDE=1` from inside a Claude Code session on the maintainer's machine, took a tiny read-only role through the executor: no credential finding, isolation held, `Finished` with the expected summary, in 9 s. C7's open item, the exit status at a real usage limit, stays open: no limit was reached.
- **Tests.** The scenarios run on the executor and the fake harness: the smoke scenario (a usage limit, a crash, questions, a valid build committed and pushed, an invalid result, a valid verify), and three short ones on its fixture in `crates/owlshift-testkit/tests/scenarios.rs`: a file written in the main checkout and a branch switch, both quarantined and parked despite a valid result, and a run stopped at a one-second deadline. `tests/isolation.rs` finds every kind of violation on one repository, after a run's own work (a commit, its ignored files, a fetched ref) passes. It passes a rebase onto the new base and an aborted one, and quarantines a rewrite below both the start and the base with the remote-tracking ref moved, and a rebase with `--update-refs` (git 2.54 locally, then CI's). Two concurrent runs pass, one ending first, while during a check a third starts and a fourth ends at a commit the check's read did not see; the same check told of no other run, an ended run's branch moved, a parked ticket's branch and a tag are still found; `tests/executor.rs` checks the refusals before the spawn: a credential in the repository's configuration, a worktree on another branch, a separate clone and the main checkout given as the worktree, run files reached through a link.

**The project gate** (OWL-16), in `owlshift-runner::executor::gate`. The build role runs `stack.gate` and says so in its result, but a claim is never proof: after every Build run that ends `done` and breaks no isolation, the executor runs the gate itself.

- **How.** Each command of the brief's `gate`, in order, from the worktree root, through the platform's shell: `sh -c` on Unix, `cmd /d /s /c` on Windows with the line passed verbatim. It runs with the agent environment (OWL-22), never the runner's, with no input, as the root of a process tree; the first failure stops the gate. An empty gate runs nothing and passes, which the delivery report states as "the project declares no gate command"; the build role still stops with `blocked` on one, so only a role that ignored that rule or a test bench gets there.
- **On the delivered commit.** The worktree must be clean before the gate (uncommitted changes fail it without running a command), clean after it, and at the same HEAD: a passing gate vouches for the commit the run delivers, which the report records. These checks run git with the agent environment and `core.fsmonitor` off, so a helper the run planted in the repository's configuration never runs with the runner's environment, and their status with every configured filter driver switched off (OWL-73, under "Follow-ups"). The result and its artifacts are read before the gate, so gate code cannot change what the runner acts on.
- **Output and deadline.** The commands' standard output and standard error go interleaved, and whole unless abandoned, to `gate.log` in the caller's run directory; a failure keeps the last 16 KiB, cut on a character boundary. The commands share one deadline, `Executor::gate_timeout` (`DEFAULT_GATE_TIMEOUT`, 30 minutes, until a caller has a reason for another): each gets what is left, none starts once it is spent, and a command running at the deadline is stopped with its tree. The tree is also stopped when its root exits, so a process left holding the output does not hold the gate; the output of one that left the tree is waited for until the deadline, at least 2 s, then abandoned, and the gate fails with the output read until then (OWL-54), which is also what the log has of it. What it writes later is still read, so the process is not stopped by a closed pipe, but dropped: the drain writes the log under a lock that spans each write, and the gate empties it under that lock when it abandons the output, so nothing lands after the command's status line (OWL-69). The checks around the commands keep the executor's own 120 s git deadline.
- **Verdict.** Isolation is checked again after the gate, since the gate ran code the run wrote: a breach quarantines the run, whatever the gate said. Otherwise a red gate makes the run `Failure::Gate`, which the core counts as a failed run (`RunFailed`): the ticket stays at Build, nothing is pushed, and the existing breaker gives one fix run before parking it. The caller puts the failure in the next Build brief (`gate_failure`), where the build role reads its output as data; a passing gate clears it, and `RunReport::gate` carries the passing commands and commit for the delivery report. The failure is kept in memory by the caller until ticket refs persist a checkpoint.
- **Tests.** Unit tests in `gate.rs` run real commands on the three CI platforms: order and first failure, the tail of a long output, the deadline, a process left holding the output, the tail taken while the output is still open, an abandoned drain's log emptied only once its write in progress landed and written no more (OWL-69), the agent environment, and on Windows a line with inner quotes; on Unix, a process that left the tree and holds the output fails the gate with the output read before, and nothing it writes after the gate returned reaches the log, which ends with the lines of a command run next on it (OWL-69), and attributes naming a driver of the repository's configuration and one of the user's run neither in the gate's git, before or after the commands, while a plain `git status` runs both (OWL-73). The scenario `tests/scenarios/gate.toml` is the acceptance: the gate fails after a first Build `done`, the next brief carries the failure, and it passes after the fix run. Short scenarios on its fixture cover a gate refused on uncommitted changes, a gate that commits, and a gate that breaks isolation and fails, which is quarantined.
- **Follow-ups.** A gate-specific attempt counter, if one fix run proves too few. The isolation check's own `git status` still runs with the runner's environment, now only once the link and the shared git files are found untouched (OWL-59). The gate's own checks around its commands run git in the worktree with the agent environment, no hook and no monitor, outside the sandbox; OWL-64 makes the executor's file-system checks (the link, the shared git files) before that git, before the commands and again after them, and a violation stops the gate there and quarantines the run, so a clean filter the gate's code configured never runs; the gate's status ignores submodules, so a planted gitlink starts no git in an unchecked repository. One limit remains: a process that escaped the gate's tree could change those files after the check.
  - *Configured filter drivers* (OWL-73, decided 2026-09-29). The worktree's attributes, written by the run, choose the filter driver a file goes through, and a driver already configured (a global or system git-lfs, one in the repository's own configuration, such as a script in the worktree) would run in the gate's status outside the sandbox, on content the run chose. Just before each of the gate's two status calls, the gate lists every driver git would find (`git config -z --get-regexp '^filter\.'`, with the same environment and hardening as the status) and switches each off on that status: `-c filter.<name>.clean=`, `smudge=`, `process=` and `required=false`. This departs from the ticket's two options. Running the gate's git without the global and system configuration leaves the repository's own drivers running and loses the global `core.excludesFile`, so the gate would fail on files the user ignores. Recording the drivers in the snapshot and failing closed when attributes name one would fail every gate of a repository that uses git-lfs, whose committed attributes name it; `merge.*.driver` never runs in a status. Two costs: a file a driver filters is read raw, so once its timestamps change (touched, or racily clean after a checkout or a commit) it reads as modified and the gate fails, which a repository using git-lfs should expect, the failure naming the drivers switched off; and a driver whose name a `-c` argument cannot carry (holding `=`, empty, not UTF-8) fails every gate, as does a listing git could not give. Checked on 2026-09-29 with git 2.54.0, a throwaway global configuration and a marker per driver: the gate's status and `rev-parse` ran no `diff.*.textconv`, `diff.*.command` or `merge.*.driver`, while `git diff` ran the diff command; the empty values stopped a clean driver and a `process` driver, whereas keeping `required=true` made the status die ("clean filter 'X' failed"); `-c filter.a=b.clean=` split at the first `=` and the `a=b` driver still ran; the listing gave every scope's keys, a name's case kept. A possible follow-up covers every program git could start at once: running the gate's own git inside the sandbox, where a driver still runs, but confined.

**A refused result** (OWL-180, decided 2026-10-07). On the P2 exit gate (OWL-175, below), a Build run asking after a round with a re-ask went on from the thread's numbering and asked `Q4`; the runner refused its `result.json` ("question Q4 is out of order: expected Q1"), its retry, told nothing, did the same, and the second failed run parked the ticket.

- **The role.** `roles/build.md` says that every run that asks numbers its questions from `Q1`, whatever ids the thread's earlier rounds and re-asks used.
- **The retry is told why.** A Build run whose `result.json` is refused (`Failure::InvalidResult`) is a failed run, as before, and the next Build run of the same command gets the reason in its brief (`result_refusal`, brief format 7; `result.json` stays format 5), as a red gate's next run gets `gate_failure`. `on_demand::result_refusal` reads it from the run's outcome for `OnDemand::build` and for the scenarios' stand-in driver alike: any other outcome leaves the next brief without it, so it reaches one run only, and never the answer check or the resolver. The reason is the runner's message, cut to 2 KiB (`MAX_RESULT_REFUSAL_BYTES`) with its beginning kept, since it can quote a whole string of the refused result; what it quotes is data. A result holding the harness's login is a credential failure, checked before the contract (`executor::read_result`), so the reason never quotes it.
- **What it did not change.** The failed-run breaker: a refused run counted, so after another failed run at the same stage the refusal parked the ticket with no retry left to tell; OWL-183, below, keeps it from spending that last attempt. The reason lives in the command's memory, like `gate_failure`: a park, a usage limit or the end of the command drops it. The answer check and the resolver are retried across commands, so carrying their refusals would need the ticket ref; not done.
- **Rejected: the runner renumbering the questions itself.** The numbering carries nothing but order, but renumbering would loosen a strict contract for one shape only, while the brief's reason serves every refusal a run can fix by itself (an unknown field, `pr` without `done`, a wrong `pr.branch`). And a run's own text can cite its ids, in a question's `context` or a decision's `basis`, which a silent renumbering would leave pointing at another question.
- **Tests.** `tests/scenarios/numbering.toml` is the acceptance: after a round with a re-ask, a run asking `Q3` is refused with nothing posted, and its retry, told why, opens round 2 with `Q1`. `a_refused_result_is_told_to_the_next_build_run_only` (`tests/on_demand.rs`) checks the real loop: the refusal reaches the next Build brief only, not the resolver's nor the Build run after, and `run_started` records it.

**A refused result at the last attempt** (OWL-183, decided 2026-10-07). With OWL-180 alone, a refused Build result was one more failed run: when another run of the stage had already failed, it was the second and parked the ticket, and its reason reached no run. A failed answer check counts toward the stage it returns to, so a round whose check failed once, followed by a resumed Build run that numbers on from the thread as OWL-175's did, parked with that fix unused.

- **The rule.** A Build run whose `result.json` is refused, and whose brief carried no `result_refusal`, counts as a failed run, except that it never brings the count to the breaker's limit: at the stage's last attempt, the ticket stays at Build with its count, nothing is posted, and the next Build run of the command gets that attempt, told why. A Build run that was told and fails, however, counts as any failed run, so at the last attempt it parks. Below the last attempt nothing changes: the first refusal of a ticket with no failed run counts, and its told retry is the last attempt.
- **Where.** The core event `Event::ResultRefused`, valid at Build only, since only Build's brief carries a refusal's reason: it counts as `RunFailed` below the last attempt and leaves the state as it is at it, so `state.json` keeps its format and its invariants. The runner chooses it: `on_demand::stage_event` maps a Build run's `Failure::InvalidResult` to it when the run's brief carried no `result_refusal`, and every other outcome as `core_event` does, for `OnDemand::build` and the stand-in driver alike. It covers every refusal `result_refusal` tells, the contract's and a result that is a link or past 1 MiB alike.
- **The bound.** Two refusals in a row never both go free: the second run was told. Each freed refusal is followed by a told run that parks, stops (a round for the decider, a usage limit), delivers, or goes on through a resolver's settled pass or a late-comment integration run; neither count is reset in a command (`MAX_RESOLVED_PASSES`, one integration per delivery), so a command frees a handful of refusals at most, each at the cost of one Build run. Across commands the reason is dropped, as OWL-180 says, so a `continue` after a usage limit can free a refusal again: each such command is a person's gesture, or follows the decider's answer. The PARKED comment says "a run failed again, with no attempt left", true whether or not a freed refusal came before.
- **Rejected.** Counting as before and documenting the park: OWL-180's fix would never reach the case it was built for. A per-stage flag in `state.json` (format 3), set once a refusal was freed: the reason it pairs with lives in the command's memory, so the flag would outlive what it is for. A refusal that never counts: two in a row, and then more, would loop on paid runs. The rule in the runner alone, skipping the core event: the breakers live in the core machine, and the stand-in driver would need a copy. Freeing the contract's refusals only, not a link or a size: it would split `Failure::InvalidResult` for no case seen.
- **Tests.** `tests/scenarios/last_attempt.toml` is the acceptance: a crashed answer check counts at Build, the resumed Build run asks `Q2` and is refused with nothing posted or parked, and its retry, told why, opens round 2 with `Q1`. `a_refused_result_never_spends_the_last_attempt` (`tests/on_demand.rs`) checks the real loop and the bound: after a run with no result, a refused run does not park, and its told retry, refused again, does. `a_refused_result_counts_but_never_spends_the_last_attempt` (`owlshift-core`) and the transition table pin the event.

**The GitHub forge adapter** (OWL-17), in `owlshift-adapters::forge`, pushes the ticket's branch, opens its pull request and reads its complete check set. It has no merge, close or approve operation.

- **What it relies on,** checked read-only on `pitchopp/owlshift` on 2026-09-28 with `gh api`. GraphQL's `statusCheckRollup.contexts` on the head commit lists the check runs of every app and the commit statuses (`CheckRun | StatusContext`) in one paginated connection with `totalCount` and `isRequired(pullRequestNumber:)`; paged two at a time, pull request #16 gave four contexts over two pages, the same four check runs as REST `commits/<sha>/check-runs`. `mergeable` is `MERGEABLE`, `CONFLICTING` or `UNKNOWN`; `mergeStateStatus` is `DIRTY`, `UNKNOWN`, `BLOCKED`, `BEHIND`, `UNSTABLE`, `HAS_HOOKS` or `CLEAN`. The check run statuses, conclusions and commit status states are the schema's enums, read by introspection. An unknown pull request answers HTTP 200 with an error of type `NOT_FOUND`; a rejected token answers HTTP 401 with a REST-shaped body, "Bad credentials". The repository is private on a free plan: reading branch protection or rulesets answers 403, and the branch is not protected, so no check there is required.
- **API and credential.** GitHub's GraphQL API, since one query gives every check, whether required, and the merge state; REST needs three endpoints paginated separately. The token lives in the system keychain (service `owlshift`, account `github`): a fine-grained token with pull requests (write), checks, commit statuses and metadata (read), or the output of `gh auth token`. Owlshift does not read `gh`'s own login. The push goes through the `git` CLI and the user's own git credentials.
- **Push.** `git push --porcelain <remote> <commit>:refs/heads/<branch>` pushes exactly the verified commit, never a force. The outcome comes from the exit status and the ref's porcelain flag (C3): created, fast-forward, up to date, or rejected; no flag for the branch is a failure, reported with the end of git's standard error, any credential in a URL removed. Tested against a local bare remote with the bench's hermetic git.
- **Complete.** Every context of the pull request's head commit, read to the last page. The list is refused rather than returned partial when a page does not advance, the count differs from `totalCount`, or the head moves while reading; and the head must be the commit the runner pushed.
- **Verdict.** Not open when the pull request is closed or merged; red when a check failed or the pull request conflicts; pending when a check is not finished (a check run not `COMPLETED`, a status `PENDING` or `EXPECTED`) or mergeability is `UNKNOWN`; no checks when there are none; green otherwise. A check passes on `SUCCESS`, `NEUTRAL` or `SKIPPED`; any other conclusion or state, including one GitHub adds later, is a failure that a human sees. Every check counts, required or not. `mergeStateStatus` is reported, not judged: `BLOCKED` and `BEHIND` depend on reviews and branch protection that Owlshift cannot satisfy by itself.
- **Known limit.** A required check that has not reported yet has no context, so it cannot be listed; `mergeStateStatus` then reads `BLOCKED`. Reading the required checks themselves needs admin rights or, on a private repository, a paid plan.
- **Opening.** `find_open_pull_request` looks for an open pull request from the branch of this repository into the base, so a resumed delivery does not open a second one; `open_pull_request` passes the runner's title and body verbatim. Draft pull requests are optional: a private repository on a free plan has none.
- **Tests.** Fixtures recorded read-only on `pitchopp/owlshift`, in `crates/owlshift-adapters/tests/fixtures/github/`; the answer to `createPullRequest` is made up in the schema's shape and flagged, since recording it would open a pull request. An ignored live test pushes, opens, finds and reads a pull request on a disposable repository named by `OWLSHIFT_LIVE_GITHUB`, then closes it and deletes the branch.

**The delivery report** (OWL-18), in `owlshift-runner::writer`, is the Writer's first write: a `[owlshift] DELIVERY` comment on the ticket once its pull request is open.

- **Content.** The pull request and its head commit; the complete check set (OWL-17) with its verdict, every check and the forge's merge state; the project gate, as a value OWL-16 fills (until then, "not run by Owlshift"); the decisions taken without a human; what remains for a human, derived from the rest: review and merge, unfinished or failing checks, a conflict, proposed follow-ups that nothing files yet. A check set that could not be read, or that belongs to another commit than the head, is said so; the report still goes out.
- **Writing.** The Writer asks the floor before posting. When the ticket's newest delivery report already has exactly the same body, it returns that comment instead of posting, so a retried delivery does not post twice; a newer state is a new report. Text from a model or the forge is flattened to one line, and a check link is kept only for a plain `https://` URL, so neither can forge the header or the footer nor break the layout.

Linear stored the body verbatim, the HTML-comment footer included, so `MarkedComment::parse` read it back with its footer, and the retry posted nothing. Whether Linear's editor shows the footer was not checked. This validates the ticket's acceptance before `owlshift do` exists; OWL-20 wires the Writer into it.

**`owlshift do`, `init` and `logs`** (OWL-20), in `owlshift-runner::{on_demand, project, events, init}`; the CLI only opens what they need.

- **Which checkout.** This settles the point OWL-15 left open (decided 2026-09-29). Worktrees hang off a dedicated clone of the project's `origin` under Owlshift's data directory, never the person's checkout, so a person editing or committing there does not look like a breach. The layout is `<data>/projects/github.com/<owner>/<repo>/`:
  - `checkout`: the clone, the runs' main checkout;
  - `worktrees/<ticket>`;
  - `runs/<ticket>/<run>` with `brief.json`, `stdout.log`, `stderr.log`, `gate.log`;
  - `lock`;
  - `unverified`.

  Names are lower-cased, and a Windows device name gets a trailing `_`. The first `do` clones; later ones set the clone's `origin` to the person's, `fetch --prune`, then `remote set-head origin --auto`, so a project that changed its default branch gets its new base; a failure of that call stops `do` rather than keep a stale base. The base is `origin/HEAD`, which a clone records; the pull request's base is that branch. Checked on 2026-09-29: git 2.54 sets `refs/remotes/origin/HEAD` to `origin/main` when cloning a local bare repository, and GitHub advertises the symref (`git ls-remote --symref origin HEAD` on this repository answered `ref: refs/heads/main`).
- **Refusals before anything runs.** A machine where agents cannot be confined (no `bwrap`, or native Windows), or no usable Claude Code token for agent runs in the keychain: what the executor would refuse at the spawn (OWL-41, OWL-94) is refused before anything is cloned, with the fix (`claude setup-token`, then `owlshift init`). On Linear, a ticket of another team than `tracker.team`: `owlshift do LOC-12` in an OWL project would otherwise build and report on another team's ticket. An `origin` that is not on github.com, or whose http(s) URL carries a user or a token (the URL is never repeated). A ticket with no decider (OWL-124, "Who answers which ask" above): before anything is cloned when it has no assignee and declares no zone, otherwise once the fetch gives the base whose `owlshift.toml` names the zone owners. Another `do` on the same project: an OS file lock (`File::try_lock`), released even by a crash. A missing keychain entry. A forge that refuses the token: one read of the pull request is made before the run, so a bad token fails in seconds, not after an hour of Build. The runner's own git drops the variables that point git at another repository (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and the like), and keeps the person's authentication ones.
- **The run.**
  - The brief: the ticket, its thread, the gate and the project's rules (below). A comment is `owlshift` when it parses as a marked comment, which only ever demotes; `decider` when the decider's account wrote it (since OWL-124, the decider in force at its place in the thread: "Who answers which ask" above); `other` otherwise. The ticket's author is the account that created it (OWL-62: Linear's `Issue.creator`, the Markdown front matter's `author`): `decider` when it is the current decider's account, matched by identifier, so the description reads as instructions; `other` otherwise, and when the tracker names no account, so it reads as a request. On Linear, though, the author is never `decider` (OWL-74): Linear answers alike for an issue the decider typed and one created through their API key by a script or an agent, so the adapter never reports the creator as an account, and every Linear ticket reads as a request. Two limits are accepted, not worked around: an edit of the description by someone else after its creation is not seen, since the tracker names the creator only; and on Linear, a comment posted through the decider's own API key (by a script or an agent holding it) is the decider's. When the worktree holds `.owlshift/run/plan.md` and `ledger.json`, `checkpoint` points to them, so a fix run or a new `do` resumes from the plan.
  - The harness: Build runs on Claude Code with the `standard` tier's model, or the CLI's default, `network: false`, a 2-hour deadline and the gate's 30 minutes. The agent environment is `AgentEnv::from_runner` with the project's `stack.gate_env` (OWL-44) and the personal `allow_gate_env` (OWL-63), confined, with Claude Code on the token for agent runs, read from the keychain with the other secrets (OWL-94). The credential check covers `github.com`.
  - The loop follows the core machine on a `trivial` pipeline cut at Build. A failed run, a red gate included, gets one more run with `gate_failure` in its brief; a second failure parks, save a refused result of a run not told of one, which never spends the last attempt (OWL-183). `on_demand::stage_event` maps a run's outcome onto a core event for `do` and the scenario driver alike.
- **The project's rules** (OWL-61, decided 2026-09-29), in `owlshift-runner::rules`. Conventions such as DCO sign-off must reach the build role as instructions from the runner, not only through what the harness loads by itself from the worktree.
  - Source: the files `stack.rules` names (OWL-67, below), by default the `AGENTS.md` at the root of the repository, the cross-harness convention (Codex reads it natively; this repository's `CLAUDE.md` only imports it). `CLAUDE.md` is not read by default: it is Claude Code's own loading mechanism, and injecting it verbatim would pass an `@` import, not a rule.
  - Rule files (OWL-67, decided 2026-09-29). A project names them in `owlshift.toml`, next to `stack.gate_env`: `rules = ["AGENTS.md", ".claude/rules/testing.md"]`, paths from the repository's root with `/` between folders. Without the key, the rules are OWL-61's: the root `AGENTS.md`, and none when the base commit has no such file. With it, each named file gives one rule, in the order named, and a named file the base commit lacks refuses `do`, naming it: a rule dropped unseen is a changed instruction too. A blank named file still gives no rule, as it holds no instruction, and its path is then absent from the `dispatch` event. `rules = []` gives no rule. Each file is read as below, at most 32 files are named, and 64 KiB is the limit of all the rules together: the sum of the sizes git lists for them, checked before any is read, the refusal naming each file and its size. The brief's rules thus stay bounded however many files are named.
    - Where the list comes from: the `owlshift.toml` that `do` loads, the person's own checkout, the file `stack.gate` comes from, whose commands the runner already runs. An agent reaches that file only through a reviewed merge. The files' text, which becomes instructions, is read at the base commit (Trust, below).
    - Files only. A folder or a glob is not taken: the files of `.claude/rules/` are scoped to paths by their `paths:` front matter, which Owlshift would otherwise inject for the whole repository; a project names such a file only if it applies everywhere, and path-scoped rules come with zones (P2). The list stays in `owlshift.toml`, so what reaches an agent as an instruction is changed there, in review. An `@` import in a named file is passed as text, not followed: a project names the imported file instead.
    - No section is left out. A named file is taken whole, like any rule, since a cut rule is a changed instruction and a Markdown heading is no reliable boundary (a fenced block holds `#` lines too). Text meant only for interactive sessions, such as this repository's tracker section, goes in a file the project does not name.
    - The paths are checked when the file is loaded (`ProjectConfig::validate`): a path that is empty, starts with `/`, holds `\`, a NUL or another control character, or an empty, `.` or `..` part (so a trailing `/` too), a path named twice, compared as written, or more than 32 paths makes `owlshift.toml` invalid with `stack.rules: ` and the reason. At the base commit, a named path under a symbolic link or inside a submodule has no entry and is refused as missing; a folder is refused as not a regular file. Each file takes its own `git ls-tree`, never one for all: checked on 2026-09-29 with git 2.54, `git ls-tree HEAD -- docs docs/deep` lists `docs/deep` alone, so a folder named with one of its own paths would read as missing; `sub/deep/x.md`, with `sub` a symbolic link to `docs`, and `agents.md` for `AGENTS.md` under `core.ignorecase=true` list nothing.
  - Trust: the files are read at the base commit, never in the worktree. The ticket's branch is written by agents, so reading it there would let a run promote its own text to instructions for the next. The base is resolved once, by `sync_checkout` after the fetch, through its full name (`refs/remotes/origin/<branch>^{commit}`), so a local branch named `origin/<branch>` cannot shadow it, and a remote-tracking ref a run moved is reset by that fetch first; the ticket's new branch starts from that same commit (OWL-51). The rules therefore carry what the forge's default branch holds, the trust the project already gives its own merged code, and are read once per `do`: the fix run gets the same rules, a later `do` those of the base then.
  - Reading: `git ls-tree -z -l` at that commit gives the entry, then `git cat-file blob` its content, with no filter, text conversion or hook. No entry means no rule for the default `AGENTS.md`, and a refusal for a named file. The entry must be a regular file (mode `100644` or `100755`) of at most 64 KiB, in UTF-8; a leading byte-order mark is dropped and a blank file gives no rule. Anything else (a symbolic link, a folder, a submodule, a larger file, other bytes, a git failure) refuses `do` before the run, naming the file: a rule is never cut, since a cut rule is a changed instruction.
  - In the brief: one rule per file, `source` its path as named, `applies_to` empty, which means the whole repository; zones are the ones the ticket's `zone:` labels declare until intake declares them (OWL-129, above), and path-scoped rules come with intake. The `dispatch` event names the rules' sources.
  - With the harness: since OWL-53, Claude Code loads no `CLAUDE.md`, rule or settings file from the worktree. Whatever a harness loads by itself from the worktree comes from the ticket's branch, so the build role reads it as data; the brief is the source that counts. The role's limits prevail over any rule: this repository's `AGENTS.md` also tells an interactive session how to reach the tracker, which the build role refuses and the sandbox closes anyway.
- **Rules per role** (OWL-185, decided 2026-10-07). A project adds rules to one role without touching Owlshift's prompt for it. Its conventions for building, such as a frontend style or how migrations are written, need not reach the resolver, nor later design, verify or fix; and the override in `.owlshift/roles/` replaces a prompt whole, and with it the limits, the result contract and the routing of questions every run relies on.
  - Configuration: `[roles.<role>]` in `owlshift.toml`, with one key so far, `rules`, a list of files read as `stack.rules` reads its own (paths, files only, `@` imports passed as text, each file taken whole): `[roles.build] rules = ["docs/skills/frontend/SKILL.md"]`. A role is named as its prompt file is (`build`, `resolver`), so the table and the override in `.owlshift/roles/` name the same thing. Only a role whose brief carries rules takes the table: `build` and `resolver` now, each later role as it is built. `answer_check` is refused: it classifies the decider's answers from the brief alone, and an instruction there could only sway a verdict. An unknown role is refused too, since a misspelt table would drop its rules unseen. Either makes `owlshift.toml` invalid with `roles.<role>.rules: ` and the reason. An older Owlshift refuses the unknown table, so a project that uses it raises its `requires` to the first version that reads it.
  - In the brief: the role's rules follow those of `stack.rules`, one rule per file in the order named, each with its `source`, so the role reads them as it reads the others; its prompt is unchanged and its limits prevail over any rule. `stack.rules` keeps its default, the root `AGENTS.md` when the key is left out, beside a role's rules. A path in both lists, compared as written and the default counting as `["AGENTS.md"]`, is refused, since the file would be given twice. The limits hold per brief: 32 files and 64 KiB for `stack.rules` and the role's together, checked before any is read, the refusal naming each file and its size. The files are read at the base commit like every rule (Trust, above), and the `dispatch` event names every source.
  - Skills: a project that writes its instructions as skills names their `SKILL.md`, which Owlshift reads as one more rule: taken whole, front matter included, the files it points to not followed, and its `description` never used to choose when it applies, since a named file reaches every run of its role. A skill that applies only to part of the repository waits for path-scoped rules, which come with zones at intake (P6). Claude Code's own skill loading stays off (OWL-53): a skill in the worktree comes from the ticket's branch, and Codex has no skills, while the brief serves both harnesses.
  - Rejected: a catalogue the agent loads skills from on demand, by their `description`, as Claude Code does. It spends less of the brief's room, but needs a tool on both harnesses that reads only files of the base commit, and leaves to a model whether a project's instruction applies; it can come later beside this key. A text appended to the prompt from `owlshift.toml`, which would put instructions in the configuration rather than in files the rules already know how to read and review.
  - What stays open: Claude Code 2.1.284's `init` lists the user's own skills even under `--setting-sources ""` (OWL-77, above); whether a confined run, whose home is unreadable, can invoke one was not checked.
- **The worktree's `.git` link.** An agent owns every file of its worktree, `.git` included: pointed at a git directory of its own, or with its administrative folder's `commondir` pointed there, git in the worktree reads that directory's hooks and configuration, which the rest of the isolation check never sees. So `.git` must be a plain file naming a folder of `<checkout>/.git/worktrees`, whose `commondir` leads back to `<checkout>/.git` and which holds no `config.worktree`; anything else is a breach. Both files are read as git reads them, the whole file less its trailing line breaks, so a trailing space names the same folder for the check as for git, and a file past 4 KiB is refused. The executor checks the link itself (`executor::check_worktree_link`, OWL-59): first in the isolation check, after the run and again after the gate, before any git runs, a breach quarantining the run; and before a kept worktree is reused, before any git runs in it, a breach refusing the run. `do` also checks a kept worktree before the run, under the project's lock, so that a breach marks the project. And the runner never runs git with the person's credentials in a worktree: the push leaves from the checkout, where the worktree's commits are, with `--no-verify`; like every command of the runner's git, it runs no hook and no file-system monitor.
- **The unverified marker.** Before each spawn, `unverified` is written. It is removed once the run's isolation check, the `.git` link included, passed, and rewritten with the violations on a quarantine. While it exists, `do` refuses the project and says how to recover: delete `checkout` and `worktrees` for a fresh clone, or delete the marker. Without it, something a breaking run left in the clone (a hook, a configuration entry) would become the next snapshot's norm and run in the runner's own git. A crash or a Ctrl-C in the middle of a run leaves the marker too.
- **Delivery,** after a Build `done` whose gate passed. It goes through the Writer, which asks the floor before each write:
  - `push_branch` pushes the gated commit (`PushBranch`) from the checkout, with the adapter's `push_command` run by the runner's git;
  - `open_pull_request` opens the pull request, or returns the one already open (`OpenPullRequest`);
  - the pull request's head must then be the pushed commit, read up to five times two seconds apart, since GitHub moves it shortly after a push. A branch someone else moved fails the delivery, and no report is posted;
  - the check set is read once, and the delivery report is posted with the gate's commands.

  The report goes out right after the pull request opens, with the checks as read then; waiting for CI is P3's watch. `blocked` is printed, not posted; since OWL-122, `questions` are posted ("The answer check", above). The visible stage moves to review once the pull request is open (OWL-137, "The answer check", above). Exit status 0 for a delivery, 1 otherwise.
- **Events.** Until the local store exists, events go to one JSON Lines file, `<data>/events.jsonl`, shared by every project, one contract `Event` per line (`Event::render_line`).
  - What is recorded: `dispatch`, `run_started` (with the run directory), `run_ended` (outcome, status, summary or reason, gate verdict and commit, exit code, duration, model, harness version), `usage`, `gate` for a question round, `decision` for a park, `tracker_write` for the push, the pull request and the report, and `warning` (OWL-134) for something left out of a run without stopping it: a malformed `zone:` label the brief dropped, with its `label` and `reason`, one event per label and per run (a Build retry is a run, so it repeats them).
  - Appends: a separate `events.lock` serializes them across processes, so a reader never waits on the log (a lock on Windows would block reads), and a line torn by a crash gets its line break before the next event.
  - Printing: `do` prints each event as it records it. `owlshift logs` prints them all, `logs TICKET` one ticket's, and `--follow` then prints new complete lines until Ctrl-C.
  - Terminal safety: every printed line is made safe first. A value with a space, a quote or a control character is printed JSON-quoted, and control characters and bidirectional overrides are escaped, so a model, a tracker or a file name cannot drive the terminal.
- **`init`.**
  - The project file: written from a commented template and the flags, checked to parse before it is written, and never overwritten. An existing file's tracker decides which secrets are needed.
  - The secrets: the Linear key for a Linear tracker, and the GitHub token and the agent runs' Claude Code token always (OWL-94: `do` runs Claude Code), asked for only on a terminal with hidden input (`rpassword` 7.5). The token's help names `claude setup-token`. Stored ones are kept unless `--replace-secrets`. A secret that is not one word, holding a space or a control character, is not stored, and `init` exits 1. On a non-terminal, `init` names each missing secret and how to provide it, and exits 1: a machine set up before OWL-94 now lacks the token until `init` runs once more on a terminal. Then, for a Linear tracker, the Linear app's client ID and secret (OWL-157), optional and together (`init::store_app_credentials`): an empty client ID skips the app, a client ID without its secret or either one not one word stores neither and exits 1, a stored pair is kept unless `--replace-secrets`, and half a pair left in the keychain exits 1.
  - Not in P1: stack detection (P9), a check that the tracker answers, daemon registration (P7), and the harness login check, which is `owlshift doctor`'s.
- **This repository** has its own `owlshift.toml`, written by `init`: Linear team OWL, and CI's three commands as its gate. A CLI test holds the gate to `.github/workflows/ci.yml`.
- **Not run live here.** No real `do` was run: the three-ticket exit gate below is the maintainer's. The hidden prompt was not tried on any platform, and the shape of the `createPullRequest` answer still comes from OWL-17's made-up fixture.
- **Known limits, and the follow-ups they call for.**
  - The runner's git commands keep the executor's 120 s deadline (`executor/git.rs`), which can cut the first clone of a very large repository (OWL-60).
  - `logs` shows where each run's logs are, not their content.
  - Worktrees are not removed after a merge.
  - On macOS the data directory's path holds a space (`Application Support`), which some project tooling mishandles.
- **Tests.**
  - `owlshift-testkit/tests/on_demand.rs` plays `do` on the Markdown tracker, the fake harness, a bare remote and the real GitHub adapter over a fake transport. The agent runs bare (`without_confinement`), as the scenarios' isolation tests do: a breaking agent must reach what the sandbox closes, and confinement has its own tests. One confined `do` checks that a machine or a harness that cannot run a confined agent is refused before anything is cloned. The runs take a lock of their own, one at a time: a child forked by another thread shares every open file until it execs, a just-released project lock included.
