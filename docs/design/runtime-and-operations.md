# Owlshift — runtime & operations

Status: draft, 2026-09-27. Owlshift ships as one native binary that runs as a light background service on each machine, with a CLI and a local web UI on top; Docker is for servers and optional sandboxing only.

## How it runs

One process per machine, `owlshift daemon`, started by the operating system's service manager, serves every adopted project; it runs no model itself.

**Every cycle** (about 60 seconds, configurable):

1. One query per tracker for tickets changed since the last cursor, one per forge for PR and check changes.
2. A comparison with the local store: an answer posted, a ticket ready, a blocker cleared, a PR merged or red.
3. Nothing to do: it waits for the next cycle, using no CPU and zero tokens. Its memory footprint is expected in the tens of megabytes, to be measured.

**When there is work:**

1. It creates a worktree and writes the brief.
2. It spawns the harness CLI (`claude -p …` or `codex exec …`) as a child process, inside a process group on macOS and Linux and a Job Object on Windows, so the whole process tree can be stopped. The mechanism is `owlshift_platform::process::ProcessTree`, which the doctor's probes already use at their deadline (OWL-31). On Windows the child is created suspended, placed in the job, then resumed, so it cannot start a process outside the job: stable Rust gives no other way, since `ChildExt::main_thread_handle` and the proc-thread attribute list are unstable (checked on rustc 1.98.1, 2026-09-28). On native Windows a confined agent command is refused, native confinement being set aside (D9, [build plan](build-plan.md#results)), so there the Job Object holds the doctor's probes. On Unix a descendant that calls `setsid` or `setpgid` leaves the group and is not stopped. Being in a group of its own also puts the child out of reach of the terminal's Ctrl-C, so the `owlshift` CLI calls `process::stop_trees_on_signal` (OWL-43): on SIGINT, SIGQUIT, SIGTERM or SIGHUP it stops every live tree, then ends as the signal would have ended it. On Windows the child shares the console and gets Ctrl-C itself, which is not enough. This was checked on windows-latest on 2026-09-29 (OWL-47, [run 36602854369](https://github.com/pitchopp/owlshift/actions/runs/36602854369), the test at commit 971ce22): `owlshift doctor` got a console Ctrl-C while its git probe hung with a child, and ended 21 ms later with `STATUS_CONTROL_C_EXIT`. A probe that kept Ctrl-C's default action died of it within 21 ms, with its child. A probe that ignored Ctrl-C, and the child it started, which inherits that, were still running 5 s later in all seven runs. So on Windows `stop_trees_on_signal` installs a console handler: on Ctrl-C or Ctrl-Break it terminates every live tree's Job Object, then ends the process as Ctrl-C does. Ctrl-Break takes the same path, not checked live; closing the console is left to the system, which ends every process attached to it.

   A hard kill of Owlshift itself (SIGKILL, a crash, the system ending it for want of memory) runs no handler. Decided on 2026-09-29 (OWL-86): on Linux and macOS the CLI also calls `process::stop_trees_when_killed`, first thing in `main`. It starts a sentinel, `/bin/sh` running a short loop in a process group of its own, and tells it, through a pipe only Owlshift holds, of each tree as it becomes live and as its handle is dropped or the signal handler stops it. When Owlshift ends, however it ends, the system closes the pipe, and the sentinel kills the process group of every tree still live, as `ProcessTree::kill` does. So a tree still live when Owlshift ends is stopped whatever the end, a normal exit included; a tree whose handle was dropped is left running, as `ProcessTree` promises. The sentinel is a best effort, not a guardrail: if it cannot start, Owlshift prints a warning and runs on without it; once it is killed it protects nothing more, nor once it is stopped and a line to it was lost (OWL-93, below), and Owlshift never waits on it; a kill in the gap between a tree's start and the moment the sentinel is told of it, well under a millisecond, and a descendant that left the tree's group escape it. Checked on 2026-09-29: the loop, run under dash and under macOS's `/bin/sh` with an empty environment, killed an announced group and spared a withdrawn one (macOS 26.6); a SIGKILL on the process group `owlshift doctor` leads, while its probe hung with a child, left both running before the change (macOS 26.6), and with the sentinel both were gone within 5 s of Owlshift's end, the bound the test checks, on macOS 26.6 and on ubuntu-latest (dash as `/bin/sh`) and macos-latest ([run 36620251554](https://github.com/pitchopp/owlshift/actions/runs/36620251554), the tests at commit afb304e), where a hard kill of a process owning two trees also stopped the live one and spared the one whose handle was dropped. Rejected: Linux's `PR_SET_PDEATHSIG`, which reaches only the root, not the processes it starts, and fires when the thread that spawned the root ends (per prctl(2), not checked live); a subreaper, which adopts orphans while it lives and does nothing once it is killed. Both are Linux only, where one sentinel serves both systems. Native Windows is out of scope for this guarantee: a hard kill of `owlshift.exe` leaves its trees running there.

   A sentinel that is gone is reported, not replaced. Decided on 2026-09-30 (OWL-88): Owlshift keeps the sentinel's process handle and reads, without waiting, whether it still runs (`process::sentinel_status`: running, ended and how, or never started); one that ended is reaped then. `owlshift doctor` reports its own sentinel on a `sentinel` line, as a warning when it ended or could not start, never as a failure, and `owlshift do` prints a warning at the end of a run during which it ended; a start failure is already warned of when the command begins. Neither refuses to work, since the sentinel is a best effort, not a guardrail. It is not restarted: on macOS a new pipe is made close-on-exec only after it is created, so a process another thread starts at that moment, not every one of which goes through the live trees' lock, could inherit its write end and hide Owlshift's end from the new sentinel; and whatever killed it, a person or a clean-up tool, would be fought without anyone knowing. A sentinel that is stopped but not ended is not seen by that wait (OWL-91, below, adds one that sees it): it still runs, and the writes to it, non-blocking, start failing only once its pipe is full, when Owlshift kills it (OWL-93, below). Checked on 2026-09-30 on macOS 26.6.2 with rustc 1.98.1, on a `/bin/sh` loop reading a non-blocking pipe in a group of its own: a non-blocking wait saw it running, and after a SIGKILL saw it ended by signal 9; a write to its pipe then failed with EPIPE, and the writer lived on, since Rust ignores SIGPIPE before `main`; stopped with SIGSTOP, it was still seen running, and the writes failed with EAGAIN after 69,608 bytes. The test that kills the sentinel of a running `owlshift doctor` and finds the warning, with doctor ending normally after writing to the dead sentinel's pipe, runs on ubuntu-latest and macos-latest.

   A sentinel that is stopped is reported too. Decided on 2026-09-30 (OWL-91): when the non-blocking wait says the sentinel runs, a second one, `waitid` with `WSTOPPED | WNOHANG | WNOWAIT`, asks whether it is stopped. It takes nothing: the stop can be seen again, and an end, not asked for, is still reaped by the first. `process::sentinel_status` then says stopped, `owlshift doctor` warns on its `sentinel` line, never fails, and `owlshift do` warns at the end of a run if its sentinel is stopped then. It is worth it because doctor called a stopped sentinel running, and until OWL-93 one protected nothing: it reads nothing, and when Owlshift's end leaves its process group orphaned, its new parent, init or launchd, being outside the session, the system sends that group SIGHUP then SIGCONT, as POSIX requires of an exit that orphans a group with a stopped member, so it died of the SIGHUP before it read the end of its input. It is also rare: only an explicit stop, by a person or a tool, reaches it, since in a group of its own it gets no Ctrl-Z, and it touches no terminal, so it gets no SIGTTIN or SIGTTOU. Rejected: a flag set when a write fails with EAGAIN, which comes only after 69,608 bytes, thousands of lines, so never within a doctor run; `waitpid` with `WUNTRACED`, which reports a stop only once and reaps a sentinel that ended behind `Child`'s back; reading the process state from `/proc` or `proc_pidinfo`, one way per system where the wait serves both; a probe the sentinel answers, which needs a channel back from it. Ignoring SIGHUP in the script, left open here, came with OWL-93, below, and a guard against lost lines. Checked on 2026-09-30 on macOS 26.6.2 with rustc 1.98.1 and rustix 1.1.5, on a `/bin/sh` loop in a group of its own: the second wait returned nothing while it ran; after SIGSTOP it returned stopped by signal 17, again on a second call and after a `Child::try_wait`, which still said it runs; after SIGCONT it returned nothing, after another SIGSTOP stopped; after SIGKILL nothing, and `try_wait` then reaped it, killed by signal 9. With the sentinel of a running `owlshift doctor` stopped, a SIGKILL on doctor's process group left the sentinel gone and the probe and its child running; with `trap '' HUP` added to the script, the same sequence left none of the three. A SIGTSTP on doctor's group, as Ctrl-Z sends to the foreground group, stopped doctor and not the sentinel. The tests that stop a sentinel, see it stopped, then running once continued, and find doctor's warning for a stopped sentinel passed on ubuntu-latest (dash as `/bin/sh`) and macos-latest ([run 36692895180](https://github.com/pitchopp/owlshift/actions/runs/36692895180), the tests at commit c5995c1); on Linux the orphaned group's SIGHUP then rested on the kernel's implementation of that rule, which OWL-93 checks.

   A sentinel that is stopped still stops the live trees at Owlshift's end. Decided on 2026-09-30 (OWL-93): the sentinel's script first ignores SIGHUP (`trap '' HUP`), so when Owlshift's end orphans its group while it is stopped, and the system sends the group SIGHUP then SIGCONT, it lives on, reads the end of its input and kills the groups still live. The guard comes with the trap, in the same change. A stopped sentinel reads nothing, so Owlshift's lines pile up in its pipe, and once the pipe is full a line is lost, the writes being non-blocking; a sentinel that lost a `-` line would, once continued, kill a tree whose handle was dropped. So when a write to the sentinel fails with EAGAIN, Owlshift kills it with SIGKILL, by its pid, which stays its own until it is reaped, and writes to it no more. The kill comes in the same call as the failed write, under the live trees' lock, before the drop or the stop that sent the line returns: a hard kill of Owlshift before then finds that tree still live, which the sentinel may stop, and after then the sentinel is gone. Killed, it stops nothing, the safe side: the trees then live are no longer protected, as with any sentinel that ended, and `process::sentinel_status` says it ended, `killed by Owlshift once its input was full, a line to it lost`, which doctor and `owlshift do` print as any end. A write that fails otherwise, as with EPIPE once the sentinel is gone, is ignored as before. Only a stopped or long-starved sentinel fills its pipe: a tree costs two lines of about 8 bytes, the pipe holds 64 KiB on Linux (per pipe(7)) and 69,608 bytes on macOS, some 4,000 trees' worth, and the loop reads tens of thousands of lines a second. The script then closes its output, which only a test reads, to wait until the sentinel ignores SIGHUP before stopping it; Owlshift itself does not wait, so a sentinel stopped in its first milliseconds, before the trap, still dies of the SIGHUP. Where Owlshift's end leaves the sentinel to a subreaper of its own session, on Linux, its group is not orphaned and a stopped sentinel stays stopped (per the kernel's `kill_orphaned_pgrp`, not checked live). Doctor's and `do`'s warnings for a stopped sentinel say so since OWL-95, on 2026-09-30: it is continued at Owlshift's end, a hard kill included, and then stops the processes Owlshift started, except when its input filled first, so that the guard killed it and it stops nothing, its status then saying it ended; when it was stopped before the trap; or, on Linux, when Owlshift's end leaves it to a subreaper in the same session. `do`'s warning leaves out the first, since it prints only for a sentinel still stopped at the run's end, and one the guard killed during the run is reported as ended. Rejected: polling the pipe for room before each line, to kill the sentinel before a line is lost, which only moves the same window before the write, and on macOS said there was no room after 15,880 bytes while writes still succeeded, the pipe growing; a flag written on EAGAIN to a second pipe the sentinel reads at the end, which protects no more, needs a descriptor passed beyond the standard ones, and a new status for a sentinel alive but told to stop nothing; sequence numbers in the lines, which show a gap only when a later line gets through, never lines lost at the end, as when the sentinel stays stopped; reporting the sentinel as unreliable without killing it, which leaves it to act on the stale list. Checked on 2026-09-30 on macOS 26.6.2 with rustc 1.98.1. The loop, with the trap, read 19,980 lines, 10,000 trees with 20 live at a time, in 0.60 s, and closed its output 3.6 ms after it started. A test's process owned a live tree and a tree whose handle it dropped, stopped its sentinel, then was killed with SIGKILL: without the trap the live tree still ran 5 s later; with it, the live tree was gone and the dropped one spared. The same, with the sentinel sent 256 KiB of lines while stopped and the tree's handle dropped after them: with the trap and without the guard, the continued sentinel killed the dropped tree; with both, it was spared; and a sentinel stopped then sent as many lines was killed as its pipe filled, which its status said. A `/bin/sh` that writes a file when it gets SIGHUP, stopped in a group of its own, was neither hung up nor continued while its parent lived, and wrote the file then ended once its parent was killed with SIGKILL. These tests passed on ubuntu-latest (dash as `/bin/sh`) and macos-latest ([run 36717037792](https://github.com/pitchopp/owlshift/actions/runs/36717037792), the tests at commit a69fb40), so on Linux too the orphaned group's SIGHUP then SIGCONT is observed, not assumed.

   A sentinel that runs is also tried. Decided on 2026-09-30 (OWL-90): on Linux and macOS, `owlshift doctor` checks that this host's `/bin/sh` does what the sentinel needs (`process::probe_sentinel`), and reports it on a `sentinel test` line. The check starts a process group of its own: a leader and a member that joins its group, both waiting on a pipe the probe holds. It then starts a second, throwaway sentinel running the same script and tells it of that group, then closes the sentinel's input. The line is `ok` when both processes die of SIGKILL within 5 s (`SENTINEL_PROBE_TIMEOUT`, kept below the 10 s deadline of each doctor probe). Otherwise it is a warning that says why, never a failure. The line is independent of the `sentinel` line, and a failed test changes nothing: the real sentinel still runs and gives its best effort. The probe never tells the real sentinel of its group, and it sends signals itself only by pid, to children it has not reaped. It reaps the throwaway sentinel before the group's members, so the group's id stays reserved as long as anything could still signal it. Everything it started is reaped before it returns, on every way out. A kill of `owlshift doctor` during the probe also leaves nothing behind: the pipes' write ends die with it, so the members and the throwaway sentinel reach the end of their input and end. Doctor runs its checks on one thread, so no process started at the same moment can inherit the throwaway sentinel's input on macOS and hide its end. Checked on 2026-09-30: on macOS 26.6.2 `owlshift doctor` printed `a test sentinel stopped a test process group 12 ms after its input ended`. The probe was tested on ubuntu-latest (dash as `/bin/sh`) and macos-latest ([run 36646224731](https://github.com/pitchopp/owlshift/actions/runs/36646224731), the tests at commit 2ccc9ba). In a helper process of one thread it returned `Works` and left no child, running or unreaped. With a script that reads to the end and kills nothing, it returned a warning after its 300 ms bound and again left no child.
3. It streams the harness output to a per-run log file and waits.
4. It validates `result.json`, checks isolation, and hands the result to the Writer.

**Harness authentication.** A Codex run inherits the user's normal Codex login (`HOME` and `CODEX_HOME` are among the variables an agent inherits), so it is billed as that login is: to the user's ChatGPT subscription, or to the API for a login made with an API key (`codex login --with-api-key`), which Codex keeps in its own configuration and `owlshift doctor` reports as such. A Claude Code agent run does not use the user's own Claude Code login or configuration: no user settings file, no configuration folder of the user's and no `ANTHROPIC_*` or `CLAUDE_*` variable is inherited from the user's environment, and it logs in with the token of the user's subscription that `owlshift init` keeps (OWL-94), so an API-billing setup in the user's Claude Code does not apply. Neither a project nor the operator can put such a variable back: a name starting with `ANTHROPIC_` or `CLAUDE_`, or `CLAUDECODE`, is refused as a gate variable, declared or allowed, so no gateway (`ANTHROPIC_BASE_URL`, which would receive the subscription token), Bedrock, Vertex or Foundry routing reaches a run (OWL-120). Owlshift never asks for, stores or passes a model API key, and `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `AWS_BEARER_TOKEN_BEDROCK` sit on the credential floor. A Claude Code agent run is therefore billed to the subscription through that token. What Owlshift does not control is the machine's managed settings, set by an administrator and outranking every flag: their `env` entry or `apiKeyHelper` can still hand a run an API key or route it elsewhere. A run that reports an API key (an `apiKeySource` other than `none`) fails and its work is refused, though what it spent is spent; routing set there reports `none` and goes undetected, and so would an API key under a Claude Code release that stops reporting `apiKeySource`. The operator's own proxy and certificate settings, which agents inherit, are trusted likewise. A Codex run on an API-key login is the one API-billed case Owlshift expects.

**Codex routing (OWL-125, OWL-130).** A Codex agent run keeps the login of the user's Codex and uses Codex's own servers: neither a project nor the operator can pass it a variable of Codex's own, since every name starting with `CODEX_` or `OPENAI_` is refused as a gate variable, declared or allowed. Among them, checked with Codex 0.154.0, `CODEX_REFRESH_TOKEN_URL_OVERRIDE` would send the login's refresh token to the host it names, `CODEX_EXEC_SERVER_URL` would hand the run's commands to a remote server, and `CODEX_API_KEY` would replace the login, which also puts it on the credential floor. `CODEX_HOME` is the one inherited, so the login must live in Codex's own configuration: a login set only through `CODEX_API_KEY` in the user's shell does not reach an agent run. `NODE_OPTIONS` is refused too, since Codex installed with npm starts as a Node launcher that would load the code it names and could set those variables before it starts Codex; a gate that needs it sets it in its own command. The adapter passes `--ignore-user-config` on every launch (OWL-130), so the user's `config.toml` does not apply to an agent run: not its providers, which can name any variable as a key or header, nor its MCP servers or telemetry exporters, nor its trusted projects, whose own `.codex/config.toml` would otherwise start MCP servers, programs included, as the run begins. Checked with Codex 0.154.0, a repository cannot name the provider or its base URL even when trusted, and no configuration key names an exec server. What Owlshift does not control is `$CODEX_HOME/.env`, which Codex reads whatever the flag and which can set the proxy a run uses, and the ChatGPT apps server a ChatGPT login opens. These rules apply from the Codex harness adapter on; no Codex agent run exists before it.

**Around it:**

- **Single instance.** A lock allows one daemon per machine; a newer binary asks the running one to drain and exit.
- **Control channel.** A Unix socket (macOS, Linux) or a named pipe (Windows) serves the CLI, the web UI and later the app.
- **Usage limits.** When a CLI reports that the subscription's usage limit is reached, the daemon records the reset time it reports, pauses that harness until then, and routes roles to their fallback. The interrupted run resumes from its checkpoint after the reset.
- **Sleep.** A sleeping machine freezes the daemon; on wake it catches up. A run cut off mid-way loses nothing: its lease expires and the ticket resumes from the last pushed checkpoint.
- **Keep awake, optional.** While a run is active, a power assertion (the mechanism behind `caffeinate` on macOS) prevents idle sleep; released when runs end.
- **Webhooks** are an optional speed-up on a server with a public address; polling always works.

## Platforms

Native binary on every developer machine; Windows goes through WSL2 first; Docker is for servers and optional sandboxing, never the desktop default.

| Platform | Support | Background service | Notes |
| --- | --- | --- | --- |
| macOS | First class from P0 | A user LaunchAgent, label `dev.owlshift.daemon` | Minimum macOS version to set (D12) |
| Linux | First class from P0: CI and servers | A systemd unit (user on desktops, system on servers) | Also the Docker image base |
| Windows | Through WSL2 from P1, running as Linux | systemd inside WSL, or a logon task that starts it | Native Windows later, on demand |

**Why WSL2 first on Windows.** The risk is not Owlshift's own code but what it launches: project tooling (Makefiles, bash scripts) rarely runs on native Windows, and native support of each harness CLI and its sandbox must be checked one by one. Native Windows adds Job Objects for process trees, paths over 260 characters in worktrees, files locked while open, and antivirus slowing git.

**Why not Docker on desktops.**

- Docker Desktop runs a permanent Linux VM that reserves gigabytes of memory, against tens of megabytes for the daemon, and must be running for Owlshift to work.
- Worktrees, git operations and dependency installs are markedly slower through the VM's shared folders.
- Harness CLIs are logged in to the user's subscription on the host (on macOS, in the Keychain); a container would need copied tokens.
- Many projects already use Docker: an agent in a container would need Docker-in-Docker or the host's Docker socket, which is root-equivalent access.
- No notifications, tray icon, keep-awake or real browser from a container.
- Docker Desktop requires a paid subscription in companies above 250 employees or USD 10 million revenue, a brake for an open-source tool.

**Where Docker fits.**

1. **Server mode:** an official image and a compose file for a Linux server, where there is no VM overhead. Codex is logged in inside the server once, and the Claude Code token is made with `claude setup-token` and stored by `owlshift init`, as on any machine.
2. **Optional sandbox per project:** each run in a disposable container, a layer of defence on top of the harnesses' own sandboxes, worth it for public repositories.

## Install, lifecycle & uninstall

Four commands cover the whole life of an install, and uninstalling removes exactly what was installed, because background services that outlive their binary are the classic failure of this kind of tool.

```bash
brew install owlshift        # or cargo install, or the Linux install script
owlshift init                # in each repository to adopt
owlshift start --at-login    # plain `start` runs for this session only
owlshift uninstall --purge   # --purge also removes history and worktrees
```

Prerequisites: git, and at least one harness CLI installed (`claude`, `codex`). Codex is logged in on the user's own subscription, which Owlshift reuses. Claude Code only has to be installed: agent runs log in with the token of the user's subscription that `owlshift init` keeps, made with `claude setup-token`; the user's own Claude Code login is not used.

**Against lingering services:**

1. **Start at login is opt-in.** `start` alone runs for the session; `start --at-login` installs the service and says so.
2. **An install manifest** lists every service file, data directory, worktree and keychain entry Owlshift creates; `uninstall` removes exactly that list. `--purge` never touches repositories or tickets.
3. **A self-healing launcher.** The service starts a thin launcher that first checks the binary still exists; if not, it removes its own service definition and exits instead of failing in a loop.
4. **Visible and findable.** A stable label (`launchctl list | grep owlshift`), shown in macOS Login Items; `owlshift doctor` lists any leftover and offers to clean it.
5. **One instance.** A lock prevents two daemons, including an old and a new version, from running at once.

**Where files live.** Platform-standard directories: Application Support on macOS, the XDG directories on Linux. The personal configuration file is `owlshift/config.toml` in the user's configuration directory: `~/Library/Application Support` on macOS, `$XDG_CONFIG_HOME` or `~/.config` on Linux, `%APPDATA%` on Windows (OWL-12). `OWLSHIFT_CONFIG_DIR`, when set to a non-empty absolute path, overrides that directory: `<value>/config.toml` is read instead of the platform default, replacing `<config_dir>/owlshift` rather than the platform's parent config directory. A relative or empty value is treated as unset. This exists so tests and tooling can redirect the personal configuration file deterministically on every platform: on Windows, the `dirs` crate resolves the configuration directory through the OS known-folder API, which no other environment variable redirects, so `OWLSHIFT_CONFIG_DIR` is the only way to isolate a test from a real personal file there (OWL-30). Worktrees live under Owlshift's data directory, one per project and ticket, never inside the user's checkout. The data directory is `owlshift` in the user's local data directory: `~/Library/Application Support` on macOS, `$XDG_DATA_HOME` or `~/.local/share` on Linux, `%LOCALAPPDATA%` on Windows. `OWLSHIFT_DATA_DIR`, set to an absolute path, replaces it, by the same rule as `OWLSHIFT_CONFIG_DIR`. It holds, per project, the dedicated clone the worktrees hang off, the worktrees and the run logs, and, until the local store exists, the event log `events.jsonl` (OWL-20, [build plan](build-plan.md#cli-surface-for-p0-and-p1)). Tracker and forge secrets live in the system keychain: macOS Keychain, Secret Service on Linux, Credential Manager on Windows. Model credentials stay with each harness CLI.

**Deadlines of the runner's git.** Every git command the runner runs for itself stops, with its whole process tree, after 120 s (`GIT_TIMEOUT`), except the first clone of a project: `owlshift do` clones the project into the data directory once, and a large repository can take longer than 120 s to arrive, so that one command has its own deadline of 30 minutes (`CLONE_TIMEOUT`, OWL-60), still stopping the whole tree. A clone that hits it fails with the deadline in the message and its partial folder is removed, retried for up to 10 s because a stopped git's files can stay locked for a moment on Windows. The clone is also marked `unfinished-clone` in the project's directory until it succeeds, so a partial folder that could not be removed, or that a crash or a Ctrl-C left, is removed by the next `owlshift do` before it clones anew, and never taken for the project's checkout; if it still cannot be removed, `do` refuses and names the folder (OWL-80). The fetch of a later `do` keeps the 120 s: it is incremental, it runs before every ticket, and a stalled network should stop it fast; if a real project's fetch proves to need more, it is a one-line change to give it the clone's deadline.

With the Tauri app (P11), start at login should go through the operating system's app login-item mechanism, so deleting the app removes it; to verify when the app is built.

## Updates & versions

One update path per install method, a restart that never loses work, and a version number on every format that outlives a binary.

**The binary.**

- Installed by a package manager: `brew upgrade owlshift`. Installed by hand: `owlshift self-update`, which downloads a signed release and verifies its checksum. `self-update` refuses on a package-managed install and points to the package manager, so the two never fight.
- The service points to a stable path (`/opt/homebrew/bin/owlshift`), never to a versioned directory, so an upgrade cannot break it.
- Graceful restart: stop dispatching, let running roles finish or checkpoint, exit; the service manager starts the new binary. Safe because state lives in the tracker, git and SQLite.
- Rollback: the previous version stays installable (`brew install owlshift@0.4`), and the local store is backed up before each migration.
- Semantic versioning; releases are tagged, signed and carry a changelog.

**Formats that outlive a binary.**

| Format | Protection |
| --- | --- |
| Project file | `requires = ">=0.4"`: a teammate with an older binary gets a clear error |
| Local store (SQLite) | Migrated at start, backed up first |
| Claims, artifacts, marked comments | Carry a format version; a runner refuses a ticket written by a newer incompatible version and says "upgrade" |
| Brief and `result.json` | Versioned contract between the runner and every role prompt |

**Harness CLIs update themselves, silently.** A flag can disappear between two days (`codex review` stopped accepting `-m`), and so can the wording of a usage-limit message. So every run records the harness version; `owlshift doctor` flags a version never tested; a nightly CI job runs the harness contract tests against the latest CLI releases, so a breaking change is caught upstream of users.

## Configuration

Configuration is plain text in two files plus the keychain; every screen that edits it later writes to those same files, which stay the reviewable record.

**`owlshift init`** detects the stack (`package.json`, `pyproject.toml`, `Makefile`, `Cargo.toml`…), connects the tracker (OAuth where offered, else a token), stores tracker and forge secrets in the system keychain, writes a commented project file, and registers the project with the daemon. It checks that Codex is logged in and that Claude Code agent runs have their token (below); it never asks for a model API key. In P1 (OWL-20), `init` writes the commented project file from its flags and stores the tracker and forge secrets, asking for them on a terminal only. Stack detection (P9), a check that the tracker answers and the registration with the daemon (P7) come later, and the harness logins are `owlshift doctor`'s to check. `init` also stores the token Claude Code agent runs log in with (OWL-94): agent runs are confined and cannot reach the Keychain, so the operator makes a long-lived token of the same subscription with `claude setup-token` and pastes it into `init`, which keeps it in the system keychain; `--replace-secrets` replaces one that expired or was revoked. `owlshift do` refuses to start without it, before it clones anything, and says how to make it, as `owlshift doctor` does. For a Linear project, `init` also asks for the client ID and secret of the Linear OAuth app Owlshift writes as (decision D8, OWL-157), optional and stored together, which a workspace admin creates in Linear's API settings with client credentials on: leaving the client ID empty keeps Owlshift writing through the API key, whose holder Linear does not notify. With the app stored, each `do`, `continue` or `watch` requests the app's token before any work, refuses if the app cannot be used rather than write through the key, and revokes the token when it ends; a `watch` stopped with Ctrl-C leaves its token to expire after Linear's 30 days. To go back to the key, delete both keychain entries (`linear-app-client-id` and `linear-app-client-secret` under service `owlshift`).

| Layer | Where | Holds |
| --- | --- | --- |
| Floor | Built into the binary | What no configuration can loosen ([architecture](architecture.md), section 8) |
| Project file `owlshift.toml` | Committed in the repository | Tracker and state mapping, admission gesture, gate commands, resources and zones, pipeline and plan approval, rules added per role, role prompt overrides in `.owlshift/roles/`, tiers mapped to models, policy additions, caps |
| Personal file | The user's config directory, never committed | Identity on tracker and forge, installed harnesses and their fallbacks, concurrent runs, usage caps, an optional dollar cap per run, keep-awake, notifications |
| Ticket labels | The tracker | One ticket's variant, tier, or exclusion |

Precedence: the floor wins, then the project, then the personal file, which may lower caps and budgets but never loosen project policy. `owlshift config show` prints the effective value of every key and the file it comes from.

**Notifications.** Decided on 2026-10-01 (OWL-24). `[notifications]` says how this machine tells its operator that they have become the blocker, at the moments [S6](scenarios.md#s6-the-human-is-the-bottleneck) lists: a question, a re-ask, a parked ticket, every harness at its usage limit; never for progress or a green check. Its one key so far, `desktop`, shows a notification through the operating system's own notification service; it is on unless set to `false`. It is how P2 tells a person that a question waits when Owlshift has no agent identity of its own on the tracker (the Linear app user of decision D8, built in OWL-157 and optional: with it, Linear notifies the decider of Owlshift's comments and its questions mention them), and it stays on beside one; someone the tracker already notifies can turn it off. Since OWL-170, a QUESTIONS, RE-ASK or REPLY comment posted without its mention of the decider, because the tracker has mentions but could not give this one (on Linear, the decider's profile link could not be read, or is not a plain `https://linear.app/` link), is recorded as a `warning` event (`what` `mention_dropped`, with the comment's kind and id, the decider's account and why), which the command's output prints like every event and `owlshift logs` shows, so the operator knows Linear may not have told the decider and can reach them another way; the comment, the state kept and the desktop notification are unchanged, a tracker with no mentions, such as the Markdown tracker, records nothing, and `owlshift doctor` says nothing of it, since a mention is read at each post and its failure belongs to that post. Shown on this machine, it reaches its operator only: a decider elsewhere is reached through the tracker. A machine with no desktop session, such as a server, shows nothing, and no run or command fails for it. It is a table rather than a single switch because the webhook and the daily digest of P7 get their keys here when they are built; a webhook's address is a secret, so it will live in the keychain, not in this file. Since OWL-140, `owlshift do` and `owlshift continue` act on it: once their outcome is printed, they show one line when it makes a person the blocker, namely questions posted as a round (or found unpostable, or a false premise), a re-ask, a reply on the ticket to the decider's counter-question (the decider must answer again), a parked ticket, or the run stopped at its harness's usage limit. Since OWL-149, the same moments notify when the comment reached the ticket but keeping Owlshift's own state in the ticket's ref then failed (the questions of a round or the decision a false premise calls for, a re-ask, a reply, a PARKED comment that was posted): the line says the state was not kept, since the next run may post that comment again. Since OWL-159, a park whose state was not kept and whose PARKED comment could not be posted notifies too, whether or not its stage moved: the run parked the ticket, which waits for a person whatever reached it, as a park whose comment could not be posted but whose state was kept already does; the line says that both failed. Nothing else notifies: no delivery, no wait on an answer already asked for, no refusal, even one whose message says a decision or a resume reached the ticket before keeping its state failed (neither asks anything of anyone); the terminal says what to do. "Every harness at its usage limit" is, until P6 brings fallbacks and the scheduler, a run stopped at the usage limit of its one harness, notified each time a command stops there; P6 notifies once per limit, as [S10](scenarios.md#s10-circuit-breakers-and-usage-limits) says. The line holds the ticket's identifier, what waits, and the ticket's link when the tracker gives one: Linear's `Issue.url`, checked live on 2026-10-03 (`{ issue(id: "OWL-140") { identifier url } }` answered `https://linear.app/owlshift/issue/OWL-140/<slug of the title>`); a link that cannot be read, or is not a plain `https` link, is left out and the line still goes. On macOS the line is shown by `/usr/bin/osascript` running `display notification`, the title and the line passed as the script's arguments so no quote in them changes the script; on Linux by `notify-send`, only when `WAYLAND_DISPLAY` or `DISPLAY` is set, otherwise nothing is shown and nothing is said; native Windows refuses `do` and `continue`, since native confinement is set aside (D9), so it shows none. Checked live on 2026-10-03 on macOS 26.6.2: that `osascript` call exited 0, and the operator could not confirm that the notification appeared on screen, so its display was not confirmed then. Confirmed on 2026-10-07 during the P2 exit gate (OWL-142), same macOS, observed by the maintainer: the notifications of `do` and `continue` showed, as Script Editor's, each with the ticket and its link; a click opens Script Editor, and Owlshift's own icon and a click that opens the ticket wait for the P11 menu-bar app (OWL-181). macOS shows such notifications as Script Editor's, and if Script Editor's notifications are turned off, `osascript` still exits 0 and nothing shows, which Owlshift cannot see. Checked live on 2026-10-08 on Linux, not on a desktop session: a Debian 12 container (Docker on macOS, linux/aarch64) with Xvfb as `DISPLAY`, a private D-Bus session, dunst 1.9.0 as the notification daemon and libnotify-bin 0.8.1 (`notify-send` 0.8.1), where Owlshift's own `DesktopNotifier` (`for_this_machine`, built from this crate) was called with a line shaped like those above. `dbus-monitor` saw one `Notify` method call on `org.freedesktop.Notifications` from `notify-send`, its summary `Owlshift` and its body the line passed, whole, and dunst then held it as displayed (`dunstctl count displayed` 1, then 1 in its history once closed); with `DISPLAY` and `WAYLAND_DISPLAY` both unset, `for_this_machine` returned no notifier and the bus saw nothing. A real desktop's daemon (GNOME, KDE) was not run, so how it renders the line is unchecked. A notification that cannot be shown, a missing `notify-send`, a non-zero exit or no answer within ten seconds, is recorded as a `warning` event (`what` `notification_not_shown`) and changes neither the outcome nor the exit code. Rejected: the `notify-rust` crate (4.18.1, MIT OR Apache-2.0, read on crates.io on 2026-10-03), whose Linux side pulls in a D-Bus stack, where the system's own commands need no dependency.

**Zone owners.** Decided on 2026-10-02 (OWL-33). `[zones."<path>"]` names the `owner` of a code zone, who decides the tickets without an assignee that touch it, by the rule of [architecture](architecture.md), section 4. A zone is a folder from the repository's root, `/` between its parts and at most one `/` at the end; no part may be empty, `.` or `..`, and the whole repository cannot be owned, so a ticket with neither an assignee nor an owned zone has no decider. Paths compare part by part, ignoring ASCII case, as zones do when they collide, so `Billing` and `billing/` name the same zone and cannot both be listed. An owner is a tracker account's identifier as the tracker reports it (a Linear user's id, the name on the Markdown tracker), written exactly: identifiers compare as written, case included, never by display name, and one with a space at either end is refused. A handle for each person is the identity map's, in P10. A project that lists zones raises its `requires` to the first Owlshift that reads them, so an older one says to upgrade. Since OWL-124, `owlshift do` and `owlshift continue` act on it (below); zones are declared at intake from P6.

**Zones a ticket declares, until intake.** Decided on 2026-10-02 (OWL-124), as a stopgap until intake declares zones (P6), which then decides how its declaration and these labels combine. A ticket declares a zone with a label `zone:<folder>`, such as `zone:backend/billing`: the prefix in any ASCII case, then a folder by the rules of an owned zone above, spaces around it dropped. Labels exist on every tracker, so no adapter changes, and an agent cannot set one, since agents hold no tracker credentials. They are trusted as ticket metadata: whoever may edit the ticket's labels chooses which zones it touches, and so, for a ticket without an assignee, which of the owners `owlshift.toml` names decides it, but never anyone the file does not name; Owlshift does not record who set a label. Labels settle the decider only of a ticket without an assignee. Since OWL-129 the brief's `zones` lists the zones the labels declare, for a ticket with an assignee too, since it tells the agent where the ticket works; path-scoped rules still come with intake. A malformed `zone:` label refuses a ticket without an assignee, naming the label: a dropped declaration would change who decides unseen. With an assignee it changes no decider, so the brief leaves such a label out of the list. The owners are read from `owlshift.toml` as the base commit holds it, after the fetch, never from the person's checkout or a worktree (architecture, section 4), with the base's own `requires` checked, at most 64 KiB, and none when the base has no such file; a file the runner cannot read or parse refuses the command, naming `owlshift.toml on origin/<branch>`. A ticket with no decider is refused with the reason: before anything is cloned when it declares no zone, after the fetch otherwise. A zone owner is known by its account identifier only, which messages and the brief's `decider` then show (a Linear user's id) until the identity map of P10. Checked live on 2026-10-02 (OWL-129): Linear's API accepts a label named `zone:backend/billing`, with `:` and `/`, and returns it as written; the read-back through the Linear adapter is still pending ([build plan](build-plan.md#cli-surface-for-p0-and-p1), "Live check of Linear's label name"). The adapter reads label names as they are.

**Usage caps.** Decided on 2026-10-01 (OWL-24). A usage cap keeps part of a subscription for its owner, across every project this machine serves ([S16](scenarios.md#s16-several-projects-on-one-machine)). It is set per harness, `usage_cap_percent` under `[harnesses.<name>]`, a whole number from 1 to 100, and counts in the subscription's own terms ([architecture](architecture.md), section 9): the share used of each usage window the harness reports, its owner's use outside Owlshift included. While the latest share Owlshift has seen for any window of a harness is at or above its cap, and that window has not reset since, no new run starts on that harness: it counts as at its usage limit, and what [S10](scenarios.md#s10-circuit-breakers-and-usage-limits) says of one applies, fallback and notification included. A run already started is not stopped, so a window can end above its cap; and since a share is only known from a run's report, a cap holds nothing on a harness whose runs report none. Without a cap, only the provider's limit applies. One share covers every window of a harness; a cap per window can come later beside this key without changing it. Rejected: a cap on tokens or on runs, which Owlshift could count itself but which does not match a subscription's limit, since the provider decides what a window holds and a token of one model does not weigh what a token of another does. In the runs checked for C7 ([build plan](build-plan.md#results)), Claude Code reported a five-hour and a seven-day window in its `rate_limit_event`, each with its share and reset time; the adapter keeps both shares but only the reset time of the window a report is about, so P6 adds every window's share and reset time. What Codex reports is checked with C7's Codex part in P5. P6's scheduler enforces the cap, and decides where the latest share seen is kept across a restart; until then the key is read and checked, and nothing acts on it.

**Dollar budget.** Decided on 2026-10-01 (OWL-117). `budget_usd`, under `[harnesses.<name>]`, is a dollar cap on each run of a harness, not on a day's total, whatever the billing. It stops one runaway run; bounding what runs take of a subscription over time is the usage cap's job, above. Owlshift passes it to Claude Code as `--max-budget-usd` whatever the billing, since it cannot know the billing before a run and agent runs log in with a subscription token anyway (OWL-94). Checked on 2026-10-01 with Claude Code 2.1.284, twice: `claude -p --model haiku --max-budget-usd 0.001 --tools ""` on a subscription login (`apiKeySource` `none`, cost basis `list`) ran one turn, ended at $0.19 and $0.29 of list-price cost, and exited 1 with `subtype` `error_max_budget_usd` and `terminal_reason` `budget_exhausted`. So the cap holds for one invocation, holds on a subscription against the list-price estimate, and a run can end above it. The adapter reads that exit as a failed run, unless a usage limit is still in force at the end of the stream, so two budget stops park the ticket as [S10](scenarios.md#s10-circuit-breakers-and-usage-limits) says: a ticket that needs more than its cap twice is going in circles. Codex has no such option (`codex exec --help`, codex-cli 0.154.0), so nothing enforces a Codex `budget_usd`. Rejected: a daily total, which needs Owlshift to keep run costs across restarts and to choose a day boundary; a daily key can come later beside this one. `owlshift do`, the one command that runs agents so far, passes the Claude key on every run.

## Observability & the local web UI

Every action is a recorded event, readable from the CLI from P1 and from a local web UI from P8; the tray app of P11 wraps that same UI instead of rebuilding it.

**Events and logs.** Each scan, decision, dispatch, run start and end, usage, gate, tracker write and warning (something left out without stopping a run) is a structured event in the local store. Each run's full harness output is captured to its own log file. On the ticket, comments give the human-readable trace. Until the local store exists, the events of `owlshift do` go to `events.jsonl` in the data directory, one JSON line each, and `owlshift logs` reads that file. It shows each run's log directory, not the logs themselves (OWL-20).

| Command | Answers |
| --- | --- |
| `owlshift status` | What runs, what waits for me, usage today and when each harness's limit resets |
| `owlshift logs --follow` | The live event stream |
| `owlshift logs PROJ-123` | Everything about one ticket, runs included |
| `owlshift why PROJ-123` | Why a ticket is not starting: a blocker, a held zone, a cap, a harness at its limit |
| `owlshift continue PROJ-123` | Pick one ticket up once its decider has answered, after the quiet window (P2, OWL-127) |
| `owlshift pause`, `resume` | Stop or restart dispatch for every ticket; running roles finish |
| `owlshift retry`, `cancel` | Act on one run |
| `owlshift doctor` | Capabilities, harness versions and logins, leftovers |

`why` is the most useful of them: a scheduler that cannot explain a wait looks broken.

**The local web UI (P8)** is served by the daemon on `127.0.0.1` only, protected by a per-install token so no website open in the browser can drive it. It is identical on every platform and reachable on a server through an SSH tunnel.

- **Overview:** tickets ready, running, waiting for a human, in review, and what blocks what.
- **Ticket:** the stage timeline, each run with its live log, usage and result, the questions and answers.
- **Orchestrator:** scans, decisions, errors, adapter health (tracker reachable, harness logged in, usage limit reached), usage per harness.
- **Config:** the effective configuration with the origin of each value and validation errors; an edit writes to the file.
- **Controls:** pause, resume, retry or cancel a run, release a claim.

**The tray app (P11)** is a Tauri shell around the same UI, adding the menu-bar icon, native notifications and the login item.

**Telemetry:** none sent anywhere. An OpenTelemetry export can be switched on by a team for its own collector.

## Testing strategy

Almost everything is tested without network or tokens; the parts that touch the operating system or a live service are thin and tested on every platform.

| Layer | How | When |
| --- | --- | --- |
| Core logic: scheduler, state machine, policy, answer routing | Unit tests on pure functions | Every commit |
| Scenarios S1 to S17 | End to end on the Markdown tracker, a local bare git remote and a **fake harness** (a small test program that writes a prepared `result.json`, with optional delays, failures and usage-limit messages; see the [build plan](build-plan.md#cli-surface-for-p0-and-p1)) | Every commit, in seconds |
| Tracker and forge adapters | Recorded HTTP fixtures, plus a conformance suite every adapter must pass | Every commit |
| Live services | A sandbox tracker workspace and a test GitHub repository | Nightly |
| Harness CLIs | Contract tests with a tiny real prompt against the latest CLI releases, on the maintainer's subscription | Nightly |
| Operating-system integration | Service install and uninstall leave nothing behind (checked against the manifest); a process tree is fully stopped; an expired lease is taken over | Every commit, on macOS, Linux and Windows runners |
| Real use | Owlshift's own backlog from P1, Locary's from P5 | Continuous |

The fake harness is the keystone: it makes the needs-input loop, re-asks, crashes and usage-limit fallbacks reproducible without consuming a subscription.

## Prior art

Owlshift combines three well-established patterns rather than inventing one: poll far and run locally like a CI runner, serve a local web UI like Syncthing, and pair a daemon with a CLI and a tray app like Tailscale or Ollama.

| Tool | What it shares with Owlshift |
| --- | --- |
| GitHub Actions self-hosted runner | Polls a remote service and runs jobs locally; `svc.sh install` and `svc.sh uninstall` manage a launchd, systemd or Windows service |
| GitLab Runner | The same model: `gitlab-runner install`, `start`, `stop`, `uninstall` |
| Tailscale | A daemon (`tailscaled`), a CLI talking to it through a local API, a menu-bar app |
| Ollama | A local server on `localhost:11434`, a CLI over HTTP, a menu-bar app that starts it |
| Syncthing | One Go binary, a web UI on `localhost:8384` protected by an API key, tray apps wrapping that UI |
| Vibe Kanban, Sortie | Category peers: a local web UI; a single binary with SQLite |
| GitButler | A Rust and Tauri desktop developer tool |

The known weak spot of the pattern, services left behind after uninstall, shows up with `brew services` and with a runner folder deleted before `svc.sh uninstall`; the lifecycle section above is designed against it. These descriptions come from each tool's public documentation and were not re-checked for this draft.
