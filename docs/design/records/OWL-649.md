# OWL-649 · Trace every GitHub App token refresh and find how a rotation was lost

Settles: [architecture](../architecture.md) section 8, "The GitHub App's tokens" (*Its events*, *The dark wake*, *The read-back*, *A lost answer*); section 5, "Dark wake" (*The GitHub App's refresh*); [runtime and operations](../runtime-and-operations.md), "Dark wake" (*The GitHub App's refresh*).

## The incident (2026-11-23 and 2026-11-24)

One project on the GitHub App, served by the daemon, lost its sign-in: the refresh token in the keychain was spent and the rotated pair never written back. From the ticket (2026-11-25) and the maintainer's reading of the daemon's log, the event log and `pmset -g log` on 2026-11-26:

- 2026-11-23T23:41:40Z: the last write of the project's keychain entry (its modification date), during a maintenance wake of about 45 s. The access token it held expired 8 hours later, at 2026-11-24T07:41Z.
- 07:41Z to 08:53Z: the Mac lid-closed on battery, with dark wakes of about 2 s every 16 minutes or so, and maintenance wakes of about 45 s. The project's tracker is GitHub Issues, read with the App's token at every pass of the watch, dark wakes included; no error line was written for it.
- 2026-11-24T08:53:10Z: the first refusal, under the 0.2.0 watch, 2 s after the full wake: "the ready column could not be read … GitHub refused the GitHub App's refresh token (incorrect_client_credentials)".
- 16:29:32Z: the 0.3.0 upgrade drained that watch (`stop: drain`, exit 0). The new watch failed at 16:29:35Z with the same refusal, and 122 times after it: the token was already dead. The project stayed paused for 18 hours, until it was removed from Owlshift.
- Nothing in the event log recorded a refresh or a keychain write, and the keychain entry is gone since, so no item that shadowed it can be looked for.

## The most likely cause, not proven

A refresh sent in a dark wake, and the Mac asleep again before GitHub's answer came. GitHub rotated the pair and its answer was lost. `AppToken::renew` takes no answer for no refusal: it clears the spent mark it set before the request (`github_token.rs`, the arm of any error but a refusal), so the next call sends the same refresh token. That token was spent, and GitHub refuses a refresh token already used with `incorrect_client_credentials` ([check C13](../build-plan.md#results), 2026-10-19), which is the refresh-failure rule's `SignInAgain`, the pause the project stayed in.

Why it fits the timeline: the access token expired at 07:41Z inside a lid-closed stretch of dark wakes; the watch read GitHub at every pass, so a read in one of those wakes sent the refresh; a dark wake lasts about 2 s, which a request with its TLS handshake and GitHub's answer can outlast; and the first refusal came at the first read of the full wake. Not proven: no event recorded the refresh, and the entry is gone.

- **Reproduced** by `github_token::tests::an_answer_lost_after_github_rotated_is_refused_at_the_next_refresh`, on `github_token::testing::Rotating`, a GitHub that accepts only the refresh token it issued last and refuses any other with `incorrect_client_credentials`, as C13 found. Its first answer is lost after it rotated: the first call is `Unreachable` with the keychain unchanged; the second sends the same refresh token and is refused in the incident's words; the two `sending` events hold the same `stored_expires_at`.
- **Closed** for dark wakes by the hold (architecture section 8, *The dark wake*), tested by `a_dark_wake_sends_no_refresh_until_the_full_wake`, `a_dark_wake_still_uses_a_peers_pair_and_tells_each_hold` and `an_unknown_wake_holds_nothing` (github_token.rs), and on the production path by `forge::tests::a_dark_wake_holds_the_refresh_on_the_production_path`.
- **Rejected:** a power assertion around the refresh and its write. caffeinate(8) on macOS 26.6.2, read on 2026-11-26: `-i` creates "an assertion to prevent the system from idle sleeping", and `-s` an assertion to prevent the system from sleeping that "is valid only when system is running on AC power". A lid closed on battery sleeps whatever is held (architecture section 5, "Keep awake"), which was this incident's case, and no assertion keeps the network up.
- **Its reach:** the hold rests on OWL-485's reading of the graphics bit, which was never sampled on a headless Mac. A Mac whose bit stays clear at every reading would never refresh: once the access token's 8 hours have passed, each GitHub call of the project fails with the hold's words, and nothing bounds the hold or lifts it (architecture section 5, "Dark wake", *The GitHub App's refresh*). Not observed, and not checked by this ticket, which had no headless Mac. [Troubleshooting](../../troubleshooting.md) ("A dark wake, on macOS", *A hold that never lifts*) tells it from a hold that ends: `ioreg -r -n IOPMrootDomain` shows `"System Capabilities"` without the graphics bit while the screen is on.

## The other paths

Each path the ticket names, and each one the reading of the code found, with its status: ruled out, guarded, or open.

- **A second process of the same data directory refreshing outside the account lock** (`init`'s check, `doctor`, the UI, a watch's steps): ruled out. `DeviceFlow::refresh` has one caller, `AppToken::renew`, which takes the account lock first. Every production token is built by `AppAccess::token` with the access's lock, `ProjectDirs::account_lock_file`, from `Secrets::read` (`do`, `continue`, watch and its steps, `release`), the UI's `reply_key` and `init` (`app_access`); a test of each checks the lock (`do_cmd::app_access`, `tracker::github::tests::a_replys_access_is_the_projects`, `init_cmd::tests::inits_access_is_the_projects_when_it_has_one`). `doctor` never refreshes: `forge::token_at` refuses a token past its expiry.
- **A drain or an upgrade during a refresh:** ruled out for this incident by the timeline, since the first refusal came at 08:53Z and the drain at 16:29Z. In the code, a watch looks at its stop between actions (`watch/stop.rs`), and the account lock's guard lives until `renew` returns.
- **0.2.0 against 0.3.0:** ruled out. Between v0.2.0 and this ticket's base, `github_token.rs` changed by one line (`account_lock` returns `project::FileLock`), and `forge/github_app.rs` and the platform's `keychain.rs` not at all. `project.rs`, which holds `FileLock`, `try_lock_file` and `lock_file_within`, changed in OWL-646: a `FileLock` unlocks its file before it closes it, which releases the lock earlier only for copies of the file a child forked while it was held; `renew`'s guard is still held until `renew` returns, under a drain as otherwise, and the children it runs under the lock (`security` for the keychain on macOS, and since this ticket the wake probe's `ioreg`) get no copy of the lock's file, which the standard library opens close-on-exec. The loss happened under 0.2.0, before 0.3.0 ran.
- **A keychain write that fails:** guarded before this ticket (tried `STORE_TRIES` times, then `SignInAgain`, "the rotation is lost"), now traced: each try is a `keychain_write` event, the last failed one with `rotation_lost`.
- **A write that looks done and did not land** (another item of the same service and account given first, or a store that exits 0 without writing): possible, not shown; now guarded by the read-back (architecture section 8, *The read-back*), tested by `a_write_the_keychain_does_not_give_back_is_a_lost_rotation`, `a_write_whose_read_back_fails_counts_as_done` and `github_sign_in::tests::a_sign_in_the_keychain_does_not_give_back_failed`. This ticket's design run checked on 2026-11-25 on macOS 26.6.2 that `security -i` exits with the status's low byte, 44 for a failed lookup (errSecItemNotFound, -25300), so an exit of 0 alone does not prove a write; and `add-generic-password -U` names no keychain. The entry is gone, so this incident cannot be checked for it.
- **Two data directories sharing one keychain entry but not one lock:** open. The account lock is under the data directory (`ProjectDirs::account_lock_file`), the keychain entry the machine's (the platform's `keychain.rs`), so a process run with another `OWLSHIFT_DATA_DIR` refreshes beside the served one. Nothing shows it played a part. Whether a reused refresh token also revokes the newer pair is unverified, so whether that second refresh only fails, or loses the pair, is not known. Proposed as a follow-up.
- **A signal, a checked stop's bound or the daemon's SIGKILL of its UI between GitHub's answer and the write:** open. Not this incident, which no stop reached before the loss; proposed as a follow-up, which the maintainer moved out of this ticket on 2026-11-26.
- **A refresh begun in a full wake and cut by a sleep, a SIGKILL, a crash or a power loss:** open. No client can recover an answer lost after GitHub rotated. Now traced (below).
- **GitHub's side** (a revoked authorization, a cap on tokens) **and another client ID:** not looked at; the maintainer's look of 2026-11-26 did not cover GitHub's security log or the personal file.

## What GitHub documents (read on 2026-11-26)

"Once you use a refresh token, that refresh token and the old user access token will no longer work" ([Refreshing user access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/refreshing-user-access-tokens)). The page says nothing of a refresh token used twice, of what that does to the newer pair, or of the error it answers; C13 observed `incorrect_client_credentials` and `bad_refresh_token`.

## As built (2026-11-26)

**Events** (`github_token::TokenEvents`). Project events of the data directory's log, of no ticket and no run, in the existing kinds, so no event contract changes. Each holds `github_app`, `outcome`, `project` (`owner/repo`, which the event's own project field also holds but `owlshift logs` does not print, and which one data directory's log of several projects needs to tell whose token it was), `pid`, `command` (the process's first argument when it is a plain lowercase word, else `owlshift`) and `version`; a warning adds `what` = `github_app_token` and `why`. Expiries are RFC 3339; no event holds a token, which every test of the log checks.

- `github_app` = `refresh`, with `trigger` (`expired` or `http_401`), `held_expires_at` (the pair the process holds) and, once the keychain is read under the lock, `stored_expires_at`: `sending` (decision, with `wake` = `full` or `unknown`), then `rotated` (decision, with the new pair's `expires_at` and `refresh_expires_at`, before the write), `refused`, `no_answer` or `failed` (warnings). A call that sends none records `stored_pair_used` (decision) or `not_sent` with its `reason`: `dark_wake` (a decision), `lock_held`, `lock_failed`, `not_stored`, `unreadable`, `keychain_unreadable`, `no_refresh_token`, `refused_before` or `past_its_life` (warnings). A token source records a reason once while it repeats, and again once it hands out a token or sends a refresh, so a watch whose token died adds one event rather than one per request.
- `github_app` = `keychain_write`, with `by`: `refresh` (each try, with `try`, `tries`, `read_back` and, on the last failed try, `rotation_lost`), `sign_in` (`init`'s store of a new sign-in), `removal` (`init --github-token`) or `uninstall` (as the project the account names, lowercase). Outcomes `stored`, `removed`, `none_stored` (decisions) or `failed` (a warning).
- `AppAccess` carries the log, the lock and the wake probe in private fields, and `AppAccess::token` is the one way a token is built outside the token module's tests. With every default probe set to read a dark wake, the runner's and the CLI's suites passed in full on 2026-11-26 (1159 tests), so no test reads the machine it runs on.

An example `sending` line as `owlshift logs` prints it, the times and pid made up:

```
2026-11-24T07:41:52Z - decision command=watch github_app=refresh held_expires_at=2026-11-24T07:41:40Z outcome=sending pid=4242 project=owner/repo stored_expires_at=2026-11-24T07:41:40Z trigger=expired version=0.3.0 wake=full
```

**The hold.** `renew` reads `owlshift_platform::wake::read` as its last check before the request, under the account lock and after the keychain's read. In a dark wake it sends nothing and fails as `Unreachable` with `github_token::DARK_WAKE_HOLD`, which `forge::refusal` makes a wait for the network; [troubleshooting](../../troubleshooting.md) quotes those words, and a test checks it does.

**The read-back.** `github_token::store_checked`, used by each try of the refresh's write and by the sign-in's store.

**The login agent.** `forge::github::login_agent` keeps the 30 s global timeout and adds `timeout_resolve` and `timeout_connect`, 10 s each. ureq 3.4.2's source, read on 2026-11-26: a phase's timeout names the earliest configured deadline (`Timings::next_timeout`, timings.rs), so a stalled resolve or connect, TLS handshake included, is `Timeout::Resolve` or `Timeout::Connect` rather than `Timeout::Global`; and a connect that fails for one address gives an `Io` error of kind `ConnectionRefused`, `HostUnreachable`, `NetworkUnreachable` or `AddrNotAvailable` (`is_addr_specific_error`, transport/tcp.rs). A request with no answer then says "no connection was made, nothing was sent" for those, and "no answer came, and the request may have reached it" for any other error, a TLS one included.

**What the next loss looks like in the log.** A `sending` with no outcome from the same pid: the process ended, or slept for good, mid-request. A `rotated` with no `keychain_write` after it: the process ended between GitHub's answer and the write. A `no_answer` saying the request may have reached GitHub, followed by a `refused` with the same `stored_expires_at`: an answer lost after GitHub rotated, this incident's most likely shape.
