# OWL-650 · Explain a refused GitHub sign-in so a user fixes it without the source

Settles: [architecture](../architecture.md) section 5, "Restarts", "Pause", "The digest", "`owlshift status`", and section 8, "The refresh-failure rule"; [runtime and operations](../runtime-and-operations.md), "Notifications".

## As built (2026-11-25)

**The notice.** A GitHub App token that only a new sign-in mends (GitHub refused its refresh, its rotation was lost, its refresh token is past its life, its keychain entry does not read or is gone) is a `forge::Error` of kind `SignInAgain`. `forge::refusal` turns it into `Refusal::sign_in_to_github`, which is lasting. `Refusal::in_checkout` rewords it for a person once the command knows its folder: `forge::sign_in_notice(repo, checkout, resumes)` becomes the message, and the technical words (`forge::sign_in_again`: the keychain service and account, GitHub's error) become its `detail`. The notice was decided on the ticket (Q1): "Owlshift can no longer reach GitHub for <repo>, so none of its tickets move. Sign in again: `cd '<checkout>'` then `owlshift init`. It shows a code to enter on github.com; your owlshift.toml, your other stored keys and your tickets are kept. Owlshift picks the project up again within a minute." The folder is quoted by `owlshift_platform::service::sh_quote`. `owlshift init` keeps an existing project file ("exists: kept as it is"), keeps the secrets already stored, and replaces a refused app token with a new device sign-in.

**Where the folder comes from.** In `do_cmd::run_with`, the tracker and forge opener's result is mapped through `in_checkout` inside its closure, so it holds both when the opener is called directly and when `watch::offline::open` calls it. For the daemon's watch (`watch --drain --served`), the folder is the checkout registered in `projects.json`, and the last sentence is kept. For `do`, `continue` or `watch` typed in a terminal, the folder is the project file's own, and the last sentence is dropped, since nothing restarts that command. `do_cmd::refusal_lines` prints the detail first and the notice last. The daemon keeps the last stderr line as the pause reason, so the reason is the notice and the technical line stays in daemon.log.

**The daemon waits quietly.** `daemon::child::Supervised` has a hold mode (`hold`, `release`, `Ended::write_held`). A paused slot's retry at each pass starts its watch held and says no "Started the watch" line. When the watch ends unservable for the reason the pause already holds, its lines are dropped. Any other end writes them first, and the lift writes them before "is served again". `pause` says `Paused <repo>, waiting for you: <reason>.` only when the pause starts or its reason changes. It notifies once per pause: `Owlshift: <repo> waits for you: <reason>`.

The plan's review raised that a new reason was not written to the pause file, so status, the digest and doctor would have kept showing the first one. The daemon now writes its own pause file again when the reason changes. A person's pause is still never replaced.

**Every surface shows the same reason.**

- `owlshift status`: the watch line reads `waiting for you since <pause time>` for the daemon's pause, whatever a retry recorded last. The pause line gives the reason once, without "the daemon tries it again at each of its passes", in both voices. `owlshift status --waits` reads `waiting for you since <time>, so nothing is dispatched and no step starts: <reason>`.
- The web UI: app.js gains `waitsForYou` and `pauseText`. They are used by the side bar, the overview's project head, the graph and a ticket's waits card. The Orchestrator's control row reads `waiting for you since <time>: <reason>`.
- The digest: `<repo> waits for you: <reason>` for the daemon's pause, with the reason whole, `<repo> paused (<why>)` for a person's, and `<repo> paused` for a file that does not read.
- `owlshift doctor`: a new `service pause` line fails while the daemon's pause stands, with the reason as its detail. For the sign-in notice of the folder `doctor::sign_in_folder` finds, the line's fix is `owlshift init` in that folder; for any other reason, it is a step to do. `forge::token_at` now returns `TokenTryError::SignIn` for an entry that does not read or an access token past its expiry with no refresh token alive. The forge access line fails with the notice and the same command for it, and gives the technical words in its why. `TokenTryError::Expired` is an access token past its expiry whose refresh token is alive, which doctor does not renew (GA4). It names the same command in plain words. Neither gives the keychain's fix. The merge on green and check re-runs lines point at the forge access line.

`owlshift init`'s help now says it keeps an existing owlshift.toml and the secrets already stored, and signs in to GitHub again (decided on the ticket, Q3). [docs/reference/cli.md](../../reference/cli.md) is regenerated from it.

**Every daemon pause waits for you** (decided on the ticket, Q4), whatever its reason. Each of them is a refusal no restart mends. Only the GitHub sign-in's reason is reworded here.

**What differs from the plan, or is left open.**

- "Within a minute" is not exact. The daemon tries a paused project again at its next pass, so within a minute of the fix. It lifts the pause only once that watch has run one pass more, so tickets move after up to two minutes. The notice keeps the decided sentence. Doctor's why line says both delays.
- A registered checkout whose working tree lacks owlshift.toml would make `owlshift init` offer to write one. The notice's "your owlshift.toml … is kept" then does not hold. `Served::locate` already refuses a checkout that is gone.
- After GitHub refuses a refresh it did not record as past its life (a revoked authorization), doctor, which reads the token without a refresh, sees only an expired access token. It then gives the `Expired` words, not the notice. The command and the folder are the same, and the `service pause` line holds the notice while the daemon's pause stands.

## Other pauses on credentials and secrets

Decided on the ticket (Q2): listed here, each with the fix a reworded message should give, for a person to file in Triage, one ticket each. Each one already shows as waiting for you in status, the UI, the digest, doctor and the notification. Only its own wording is left.

1. **No GitHub token stored.** Made by `forge::no_token` (crates/owlshift-runner/src/forge.rs), through `forge::github`. Today it reads: "no GitHub token in the system keychain: run `owlshift init` in a terminal, or store one under service …, account …". Fix to give: what it stops, then `cd '<checkout>'` and `owlshift init`, which signs in to GitHub and keeps owlshift.toml.
2. **The keychain unreadable.** Made by `Secrets::read` in crates/owlshift-cli/src/do_cmd.rs: the keychain does not open, or an entry does not read, which is a `KeychainError` in its own words. Fix to give: unlock the login keychain (or the Secret Service on Linux) and allow Owlshift to read it, without `owlshift init`, which would store nothing new. Say that the service tries again by itself.
3. **No Linear API key.** Made by `tracker::linear` (crates/owlshift-runner/src/tracker.rs, "no Linear API key in the system keychain: run `owlshift init` …") and by the Linear app's `AppError::NoKey`. Fix to give: `cd '<checkout>'` then `owlshift init`, which asks for the key, keeps owlshift.toml and the other stored keys, and says where to make the key in Linear.
4. **The Linear app's pair unreadable or refused.** Made by `tracker::AppError` (crates/owlshift-runner/src/tracker.rs): `Keychain` (the pair does not read), `Incomplete` (only half of the pair stored) and `Tracker` (Linear refused the app). Fix to give: in plain words, either `owlshift init --replace-secrets` in the checkout to store the pair again, or the two keychain entries to delete to write through the API key. Name what each choice keeps.
