# OWL-640 · Keep two runners of a team from filing two repairs for one broken base on GitHub Issues

Settles: [architecture](../architecture.md) section 5, "Not twice" and "The repair ticket", on GitHub Issues. It corrects the first residual of [OWL-622's record](OWL-622.md) and the GitHub `proposed` of OWL-536's record in [the build plan](../build-plan.md), "P9 · Open-source readiness".

## As built (2026-11-23)

- *The search.* `GitHubTracker::find_proposals` (`tracker/github/drain.rs`), which `Tracker::proposed` calls, still reads the issues labelled `agent:proposed`, open or closed. It now also reads the open issues of each stage label `[tracker.states]` names, one list per label through `open_labelled`. The same exact match applies to every list: the title in any case, or the marker in the body. Pull requests are left out, and each issue is counted once.
  - A repair carries the ready stage's label from its filing and some stage label until it closes, so a colleague's runner, searching before it files, finds it and files nothing (`a_second_runner_finds_the_first_ones_repair_and_files_nothing`).
  - The same lists find a proposal that a person promoted from `agent:proposed` to a stage. This narrows OWL-536's "may be filed twice" (`proposals_are_found_by_title_or_marker_open_or_closed`).
- *The cost.* `proposed` makes one to six list reads instead of one, all on the core budget the drain already uses. Each read is conditional (`rest_text_cached`), so an unchanged page costs a 304. The stage lists hold Owlshift's own queue. A stage label holding a comma is skipped, since GitHub's list cannot ask for it; before, it would have made the whole search fail.
- *The replay.* The drain's fixture (`tests/fixtures/github-tracker/drain.json`) gains the four stage lists after the proposals' list. The ready stage's list is emptied, and `drain_recorder` amends it the same way, since the sandbox keeps unrelated issues there.

## Live checks (2026-11-23)

All four checks ran with `gh api`, through the maintainer's login, on the private sandbox repository. Each test issue was deleted afterwards with GraphQL's `deleteIssue`.

- *L1.* An issue was filed with `agent:ready`. One second later, the open list of that label, asked with the `ETag` it answered before the filing, answered 304: stale. The unfiltered open list did not hold the issue either. The search API did not find it 2 s after the filing and found it at the next probe, 8 s after.
- *L3.* Three filings, each followed by continuous polling. The label list first showed the new issue after 7.5, 8.4 and 7.3 s; `search/issues` after 6.6, 7.3 and 6.3 s. GitHub's issue lists are not read-after-write. The search API's index lag is therefore no reason to prefer a list: a list lags as much.
- *L4.* An issue with no label was found by `search/issues` with its exact title as a phrase, backticks included, and with its marker line as a phrase. The marker of another commit matched nothing. The search budget is its own: `X-RateLimit-Resource: search`, 30 a minute.

These settle the choice between three ways to search.

- *Chosen: the stage lists.* They use the same endpoint and budget as the drain, and their size is bounded.
- *Rejected: the search API.* It finds a repair whatever its labels, and a closed one. But each `proposed` would spend two calls of a 30-a-minute budget, and a spent budget holds every tracker call, since the forge keeps a single hold for the tracker (OWL-554).
- *Rejected: the unfiltered open list.* It pages through every open issue and pull request at each search, and it fails past 10,000 items, so proposals would never be filed on a large repository.

## Accepted residuals

- *Two filings within about 8 seconds.* Both runners file, as L3 measured: no list or search sees the first filing that soon. On a search that fails, the runner's repair filing (`on_demand/base_hold.rs`) files anyway. A claim between runners would close both; the follow-up is proposed in Triage.
- *Repairs and proposals the search misses.* It does not read an open repair or proposal whose stage labels a person removed, nor a closed repair; Linear's search finds a canceled one.
- *A failed list read.* Any one of the six lists that fails, for example on a rate limit or a 5xx, fails the search. The repair is then filed regardless, as above, and the owed proposals wait for the next pass.
