# OWL-662 · Park a ticket whose Build leaves nothing to deliver, and bound delivery retries

Settles: [architecture](../architecture.md) section 5, "Verify", "Nothing to deliver"; section 5, "The bound", "Failures inside a pass".

## Why (2026-11-26)

On LOC-2233 (Locary) Owlshift looped from 00:10Z until a person stepped in: 80 resumes, about 15 USD. Pull request #1791 had already made the ticket's change on `develop`, so the Build made no commit, its gate passed on the base itself, and GitHub refused the pull request: `UNPROCESSABLE: No commits between develop and owlshift/loc-2233`. `deliver` returned `Stop::Delivery`, which counted nowhere, and watch resumed the ticket at Verify about every ten minutes, with one Claude and one Codex review each time.

## As built (2026-11-27)

- **The core.** `Event::NothingToDeliver`, valid only at Verify, parks the ticket at Build with `ParkReason::NothingToDeliver` (`owlshift_core::state`). Its failed runs are cleared as entering Build clears them, and its Verify passes are kept within their loop. A restart (`Event::Restarted`) brings it back to Build, so `continue` runs the Build again, on a ticket a person may have changed.
- **The read.** `OnDemand::nothing_to_deliver`: `git merge-base --is-ancestor <gated commit> <base>` in the dedicated checkout (`base_hold`'s `is_ancestor`, now shared). The decision stays in the core; only the read is the runner's.
  - In `build()`, once the Build's gate passed and the late comments were read again, before the kept Build is stored for Verify: against the base this command fetched. A review loop is left out; its Build that commits nothing already ends the loop (OWL-307).
  - In `deliver`, right after the base's head is read for the push (`base_at_push`) and before the neutral image or the push: against that head, then against the fetched base. The neutral image never rewrites a commit on the base, so the gated commit is what would be pushed.
- **The park.** `OnDemand::park_nothing_to_deliver` drops the kept Build and its last fix, the delivery's held mark (`held.verified`, OWL-403), and a delivery record no pull request was kept for (an earlier refused attempt's `pushing` and `delivered_at`), all in the park's one write. The PARKED comment says "the base already holds this ticket's change". It names the base and its short commit, quotes the Build's summary, and says to close the ticket when the base's change is what it asked for, or else to change it and restart it. The runner never moves the ticket to done.
- **The bound.** `deliver_verified` sends every `Stop::Delivery` of a first delivery to `OnDemand::delivery_failed`. While the ticket ref keeps Verify, it applies `RunFailed` to that kept state. Below the bound it keeps the count and returns the stop, its reason ending "counted as a failed run, so a delivery that fails again parks the ticket". At the bound it parks with `FailedRuns` and the delivery's reason. A ref that already keeps Watch is left to watch's bounds. A count the ref cannot keep is said in the stop.
- **Tests.**
  - Core: `state::tests::nothing_to_deliver_parks_at_build_and_a_delivery_clears_the_failed_runs`, and the transition table rows.
  - Writer: the PARKED comment's text.
  - Bench (`verify_scenarios`):
    - `a_build_that_leaves_nothing_to_deliver_parks_before_verify`, with `continue` building again;
    - `a_base_that_takes_the_build_during_verify_leaves_nothing_to_deliver`;
    - `a_pull_request_the_forge_keeps_refusing_parks_after_one_more_try`, against the bench forge's new `refuse_create`, which answers as GitHub answered LOC-2233.

## Built otherwise than the ticket's wording

- **The count is shared with Verify's other failures.** A Verify seat that failed once, followed by one failed delivery, parks the ticket. This follows section 5's "Failures inside a pass": one count per stage.
- **Counted at `deliver_verified`, not on every `Stop::Delivery`.** The two other sources of that stop before Verify are the comments read again before delivery and a gate commit the report lacks. Both happen at Build, on a read of the tracker or the run's report, and are not failed deliveries. They stay uncounted, so that a tracker blip twice in a row does not park a ticket.
- **No fetch for the deliver-time read.** When the checkout lacks the base's head read for the push, the read falls back on the base the command fetched. Whatever it misses is a refused pull request, now bounded.
- **The base the Build-time read uses is the one fetched when the command started.** A Build can run for tens of minutes. A base that moves meanwhile is read again at the push.
- **The bound is two Verify passes and two delivery attempts.** A delivery retried after a failure still runs its Verify pass again on the kept Build (OWL-304: "a pass run again in place of its record"). This ticket bounds that to one retry; it does not remove the pass.

## Left out: a branch with commits but no diff

A Build whose commits change nothing against the base (the base made the same change in other commits) is not parked. GitHub opens that pull request, so it does not loop, and its empty diff is visible in review. Parking it as well would need a tree comparison against a moving base, and a person may still want the pull request: for example, commits that only reorder history, or a base that later reverts its own change.
