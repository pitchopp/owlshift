# OWL-638 · Detect Swift in owlshift init now that confined runs on macOS have their own temporary folder

Settles: [runtime and operations](../runtime-and-operations.md), "More stacks (OWL-624, OWL-627, OWL-628, OWL-629)", the Swift row of its table of run caches (`pubspec.yaml`, `Package.swift`). Corrects [OWL-628](OWL-628.md), whose Swift row of R1 and whose `swift` function comment said SwiftPM needs no run cache, and follows [OWL-637](OWL-637.md), which gave confined runs on macOS their own temporary folder.

## As built (2026-11-23)

Swift stays a note. `stack::swift` (`owlshift-core`) writes no setup, gate or run cache for a `Package.swift`; its note now says what the check showed: the three lines `swift package --disable-sandbox resolve`, `swift build --disable-sandbox` and `swift test --disable-sandbox` need `run_caches.CLANG_MODULE_CACHE_PATH = "clang-modules"` set by hand, the setup and the build passed with it on macOS, `swift test` of a swift-testing target did not, Linux was not checked. Held by `stack::tests::dart_and_swift_roots_get_a_note_only`, which now looks for the variable's name in the Swift note, and `init::tests::an_elixir_and_deno_root_is_written_and_loads`, unchanged. Dart and Flutter are unchanged.

## Live check R1, macOS (2026-11-23)

Script: [`owl-628.sh`](../live-checks/owl-628.sh), row `swift`, run with `KEEP=1`; the `[stack]` written by a local, uncommitted patch of `stack::swift` (a branch of `main`) that writes the three lines above, in a first run with nothing else, in a second with `STACK_EDIT` adding `run_caches.CLANG_MODULE_CACHE_PATH = "clang-modules"` above `gate = [`). Fixture: the harness's (`Files` 4.2.0 from GitHub, one swift-testing test), served by a local bare remote. macOS 26.6.2 (25G83), Apple silicon; Swift 6.4 (swiftlang-6.4.0.34.1) of the Command Line Tools, without Xcode.

| `[stack]` | `owlshift gate`, confined |
| --- | --- |
| The three lines, no run cache | red in 11 s at the setup: the manifest's swiftc cannot write `~/.cache/clang/ModuleCache/…/SwiftShims-….pcm` ("Operation not permitted"), then "failed to build module 'Swift'; this SDK is not supported by the compiler", which is the same failure, not a toolchain mismatch |
| With `CLANG_MODULE_CACHE_PATH` as a run cache (98 MB) | setup green; `swift build` green (1066 s cold on a loaded machine, 52 s with the cache filled); `swift test` red: `external macro implementation type 'TestingMacros.TestDeclarationMacro' could not be found for macro 'Test'; plugin for module 'TestingMacros' not found`, in 66 s with the cache filled; the first cold run reached the gate's 1800 s deadline in the test build |
| With the variable removed alone | red in 37 to 40 s at the setup, as the first row |

Unconfined, in a scratch package on the same machine (a minimal one, not the fixture, with plain `swift test`), a swift-testing test passes, so the failure is the confinement's. An XCTest target cannot say more: this machine's Command Line Tools have no XCTest, and `swift test` unconfined fails "unable to resolve module dependency: 'XCTest'" too. The sandbox's refusal that stops the macro plugin was not isolated: no deny line could be read from the system log, and no profile bisect was run.

It decides: no Swift line is written. The gate of a Swift package does not pass confined on macOS today, so the rule of "More stacks" (a gate passed confined, a variable passed with and failed without) leaves a note, and the variable is named in it. The variable itself did show as needed for the setup and the build, on macOS alone.

## Not checked

- Linux: no Swift tool chain on this machine, and a Docker rig is a large image and a cold build of about 20 minutes. The module cache path is a clang default there too, and SwiftPM's own sandbox does not exist on Linux, so the lines may pass there.
- Xcode's tool chain, and macOS versions other than 26.6.2: the plugin path of swift-testing may differ.
- Why OWL-628's R1 had the same setup green with no module cache on the same toolchain: its run was before OWL-637, and a warm or writable `~/.cache/clang` then is a guess, not shown.
- That a first confined gate may time out: the cold module cache took 1066 s to build, and a cold test build reached the gate's 1800 s deadline.
- Why the confined run does not find the `TestingMacros` plugin (a sandbox profile bisect).
- A Swift package whose tests are XCTest.

## The line this record corrects

`runtime-and-operations.md`, "More stacks", the table's row for `pubspec.yaml` and `Package.swift`, whose `run_caches` column says "none: a note gives the lines". For Swift the check shows `CLANG_MODULE_CACHE_PATH`, a variable no run cache of `init` carries yet. The sentence after the table, "Swift gets a note giving its lines, not shown to pass confined: ... before OWL-637 `swift build` failed confined on macOS writing to the user's temporary folder", gives a cause this check disproved (the failure is the clang module cache, then the `TestingMacros` plugin). OWL-644 owns that file, so neither is edited here; the follow-up ticket, proposed to Triage with this ticket's PR (no identifier before it is filed), edits both and takes up "Not checked".
