# OWL-659 · Run a conflict rebase's gate once, by the runner, not inside the agent run

Settles: [architecture](../architecture.md) section 5, "Conflicts and the rebase run": *The gate once, by the runner*, and the amended *The run*.

## The case (2026-11-26)

From the daemon's log and the run logs of Locary's LOC-2204 (pitchopp/locary#1796), a conflict rebase of a delivered pull request on `backend/api/urls.py` and `backend/authentication/oidc.py`, a trivial conflict:

- **Attempt 1**, from 13:18 UTC on the fast tier (`claude-haiku-5-5`), ran 22 minutes. Its agent resolved both paths and committed in about 20 tool calls, then ran Locary's gate itself, as `roles/rebase.md` asked (setup, lint, then the test step in the background, waited on with a 240-second sleep and two monitors). It then wrote a `result.json` missing the comma after `summary`, whose summary said the gate was green. The runner refused it (`expected , or } at line 5 column 3`), a failed run, and the retry started the rebase over.
- **Attempt 2**, from 13:42 UTC on the Build routing (`claude-opus-5-5`), resolved the same conflicts in about 10 minutes, then ran the gate itself too. Its test step hit the 20-minute Bash timeout with the backend suite 36 % done, with two Rust gates (OWL-649, OWL-654) sharing the machine. It ran the step again in the background with a 2-hour timeout and slept on a 40-minute wakeup, writing nothing for 30 minutes before the daemon was stopped.

The runner runs the same gate after every rebase run's `done`. The slot was held for more than 90 minutes, and `owlshift stop` waited on it.

## The decisions (2026-11-27)

The orchestrator settled both from the ticket.

- **What the run checks before `done`.** Nothing from the gate: the runner's gate after `done` is the check. The run checks the rebase itself, by reading and with `git status`, `git diff --check` and a search for conflict markers. Rejected: the gate's quick steps, which the gate's configuration has no notion of.
- **The fast tier's refused `result.json`.** Split off to a follow-up: retry a refused result from the refused run's rebased commit, told why, rather than starting the rebase over. Once the run no longer runs the gate, a fast run that writes a refused result costs a few minutes of the fast tier, plus the Build routing's rebase from the last push (about 10 minutes in this case).

## As built (2026-11-27)

- `roles/rebase.md`: the brief's `gate` is data, the commands the runner runs after `done`; "The gate" says the run runs none of them, nor the project's tests, build or linters, and why; `done` asks for nothing left uncommitted, no longer a green gate; a red runner gate is a failed run whose `gate_failure` the next attempt gets, starting again from `head`. The brief's shape is unchanged, so `brief_format` stays 33.
- `Brief::gate`'s documentation (`owlshift-contracts`) says the rebase role runs none of it.
- No runner code changed: the executor already ran `brief.gate` after a rebase run's `done` (`Executor::run`), and the repair's loop already gave a red gate's failure to the next attempt (`OnDemand::repair_runs`).
- Tests: `roles::tests::the_rebase_prompt_leaves_the_gate_to_the_runner` pins the role's text. The scenario `a_rebase_run_runs_no_gate_and_the_runners_red_gate_tells_the_next_attempt` (`owlshift-testkit`, `tests/on_demand.rs`): two agents that rebase and run nothing, the runner's gate red on the fast run's commit, then green on the Build routing's, which is pushed, its brief told the failed command. `a_trivial_conflict_is_rebased_on_the_fast_tier_and_pushed_by_the_runner` already pinned the delivered rebase brief's `gate` and the setup running once, after the run; `base_scenarios.rs`'s held rebase pins an empty `gate`.
