# OWL-657 · Settle a pull request that no check runs on instead of waiting forever for green

Settles: [architecture](../architecture.md) section 5, "What a read decides" (the row *No check at all*), and "Merge on green": *When*, *A pull request no check runs on*, *Kept for a person*, *Waits told*, "As built".

## The case (2026-11-26)

LOC-2193 (pitchopp/locary#1792) changed only `docs/**` and `.claude/rules/**`. Locary's `deploy.yml` runs on a `paths` filter (`backend/**`, `frontend/**`, …) and `claude-code-review.yml` only on `opened`, `reopened` and `ready_for_review`. After its refresh rebase pushed head `90d3a6a` at 12:07:18 UTC, watch recorded `wait_checks` with verdict `no_checks` at 12:07:29 and nothing more. GitHub reported the pull request `MERGEABLE`, `CLEAN`. The ticket kept its zones, and LOC-2194, LOC-2197, LOC-2199 and LOC-2201 waited in `collision` behind it until a person merged it at 12:59.

## The decision (2026-11-26)

The maintainer chose option A of three, relayed by the orchestrator: once watch has read no check on a merge-on-green head for 10 minutes, Owlshift merges it under every other merge-on-green condition. The two rejected options:

- B kept the pull request for a person, with a notification.
- C added a project switch defaulting to B.

The maintainer also set four guardrails:

- A commit that asks CI to skip is a hard stop.
- The window restarts on a new head, and whenever a check appears.
- GitHub's refusal of such a merge is final and notified once.
- The MERGED comment and the `pr_merged` event say plainly that no check ran.

## Live check L1: what GitHub shows for a head no workflow runs on (2026-11-26)

These are read-only calls through the maintainer's `gh` login on head `90d3a6a7093e204bd12b22f804037b979daf6fa7` of pitchopp/locary#1792. The pull request was already merged when they ran.

- **Check runs.** `gh api repos/pitchopp/locary/commits/<sha>/check-runs` lists a single check run, "Delete the closed PR's caches". It started at 12:59:15, after the merge, from a `pull_request: closed` workflow. No check run existed while the pull request was open.
- **Check suites.** `gh api repos/pitchopp/locary/commits/<sha>/check-suites` lists four suites:
  - Three suites of other apps (`cursor`, `claude`, `posthog-eu`) were created at the push (12:07:19). Each stayed `queued`, with `latest_check_runs_count` 0 and conclusion `null`.
  - The `github-actions` suite appeared only at 12:59:13, for the cleanup run.

  GitHub Actions makes no suite for a push that no workflow runs on.
- **Status rollup.** The same commit's GraphQL `statusCheckRollup` lists only check runs. The three queued suites are absent from it, so they never read as running checks. Watch's own reads while the pull request was open found the rollup empty (`verdict` `no_checks` in `events.jsonl`). The fake GitHub of the testkit's new scenarios answers the same: an empty context list.
- **Combined status.** `gh api repos/pitchopp/locary/commits/<sha>/status` answers `state` `pending` with 0 statuses: GitHub's combined status reads pending when no status exists, so it is no signal.
- **Not relied on.** `mergeStateStatus` was not read for an open head with no check. The ticket reports it as `CLEAN`, which is what a head whose checks have not registered yet also shows.

What it decides: an empty rollup is all the forge says of a change no workflow runs on. Time alone tells it from a change whose checks have not registered yet.

## Measure L2: how soon checks register after a push (2026-11-26)

The `tracker_write` push events of the maintainer's data directory give 250 distinct commits Owlshift pushed, from 2026-11-01 to 2026-11-26, on pitchopp/locary and pitchopp/owlshift. For each, `gh api …/commits/<sha>/check-runs` and `…/statuses` (read-only) gave the earliest check or status after the push:

- **237 commits had a check.** The first registered a median 7 s after the push, 10 s at the 90th percentile.
- **The REST outliers are re-runs.** Six commits showed a first check 103 s to 4.5 h after the push. The endpoint defaults to `filter=latest` and lists only a re-run job's newest attempt. Watch's own reads of those heads found checks 10 s after the push (`64a4c46d`, `a55fed34`, `96344142`) or a verdict at their first recorded read.
- **Slowest seen by watch.** 17 heads were read with `no_checks` at least once. All but LOC-2193's got checks. The slowest, LOC-1513's `bce2b8f8`, was read `no_checks` 7 s after its push and `pending` 75 s after it. The longer gaps in the event log are passes that did not read the pull request: GitHub shows those heads' first check runs starting 12 to 16 s after the `no_checks` read (`995aa5d0`, `adf59e81`).
- **Commits with no check at all.** Thirteen commits had none after their push:
  - LOC-2193's two heads;
  - two LOC-2233 commits whose push kept being retried, which watch never read;
  - nine commits pushed onto pull requests that conflicted with their base (L3).

What it decides: 10 minutes (`NO_CHECKS_AFTER`) is eight times the slowest registration watch saw.

## Live check L3: a conflicting pull request gets no check (2026-11-26)

These cases come from the same data:

- Nine pushes (OWL-485, OWL-460, OWL-475, OWL-528, OWL-538, OWL-539, OWL-552, LOC-2063, LOC-2204) went to pull requests whose next read was `conflicting`, and none of them got a check run.
- Locary's #1796 (LOC-2204), open and `CONFLICTING`, answered `statusCheckRollup` `null`.

GitHub runs no `pull_request` workflow while a pull request conflicts, as documented and noted unobserved in section 5's check of 2026-10-10. The table decides a conflict first, so such a read never reaches *no checks*.

## As built (2026-11-26)

- **Core** (`owlshift_core::follow`):
  - **New action.** `Action::NoChecks` is decided for a mergeable head that lists no check; `WaitChecks` now means checks still run.
  - **No-repair reads.** `Decision::asks_no_repair` is the one rule for reads that leave room for a correction, a review loop, a person's steps and merge on green. It replaces five copies of the same pattern in the runner.
  - **Merge decision.** `merge_due` takes `NoChecks` as green once `MergeFacts::first_green` (of the decision's kind) is `NO_CHECKS_AFTER` old. Before that it waits on `NoChecksYet`, right after the green test.
  - **Skip instruction.** Last for such a head comes `MergeFacts::ci_skipped`: `CommitsUnread` until read, then `CiSkipped`, kept for a person as `skip_ci`.
  - **Base checks.** `base_hold` counts nothing, and needs no read, for a head that carries no check.
  - **Matching.** `asks_ci_to_skip` matches `CI_SKIP_STRINGS` in any case, and the `skip-checks:` trailer.
- **Runner:**
  - **Watch's memory.** `Following` keeps the window in the first green read's slot, `(head, no_checks, since)`. `no_checks_settled` and `no_checks_until` read it.
  - **Before the window ends.** Watch calls the merge step for a `NoChecks` read only once the window is over. Before that, `Watch::no_checks_yet` reads only the base head and the switch, and tells `merge_no_checks` with `until` when the switch is not `never`.
  - **The commits read.** The merge step reads the commits (`merge::ci_skipped`, `git log --format=%B <base head>..<pushed>`), fetching the dedicated checkout first when it lacks either commit.
  - **Refusals.** In `merge_now`, a refusal that "may pass" is final for a head no check ran on. A refusal on a moved base still takes the refresh path first.
  - **What is said.** `MergedComment::no_checks` (`Some(true)`, `Some(false)`, `None` for a merge a later read found), the `pr_merged` event's `no_checks`, `merge_waits`' `no_checks` and `merge::standing_words` say what the head stood on.
  - **Refresh step.** The merge refresh step re-reads and accepts `NoChecks` as it accepts `Green`.
- **Tests:**
  - **Core:** `running_checks_wait_none_at_all_is_no_checks_and_every_check_passed_is_green`, `a_message_asks_ci_to_skip_by_github_s_strings_or_its_trailer`, `merge::a_head_no_check_ran_on_merges_after_the_window_unless_a_commit_skips_ci`.
  - **Runner:** `follow::tests::a_head_with_no_check_settles_after_ten_minutes_of_reads_listing_none`, the `NoChecks` line in `only_an_end_an_adoption_or_a_clearing_green_changes_the_ref`, the new cases in `merge::tests::every_wait_told_for_a_blocker_has_its_words`, and the MERGED comment's three wordings in `writer::tests::who_merges_is_said_and_a_merge_is_told_once`.
  - **Testkit** (`merge_scenarios.rs`): `a_pull_request_no_check_runs_on_merges_once_none_has_run_for_ten_minutes` and `a_head_no_check_ran_on_whose_commit_skips_ci_is_kept_for_a_person`.
- **Built otherwise than first planned.**
  - **Holds for a person.** The plan told the window from the merge step, before the switch and the holds for a person. The plan's review found that this would announce a merge on `never` and unlabeled tickets. It also found that moving the window down to *Green twice*'s place would notify a hold for a person at the first read of nearly every head, red ones included, since most heads are first read before their checks register. So watch does not enter the merge step before the window ends.
  - **No second memory.** A second memory for the window was dropped for the first green read's slot.
