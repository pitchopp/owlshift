# OWL-669 · Retry a refused rebase result from the refused run's rebased commit

Settles: [architecture](../architecture.md) section 5, "Conflicts and the rebase run": *A refused result*, and the amended *A red gate*, *Split off* and *Each attempt from Owlshift's last push*. Follows [OWL-659](OWL-659.md), whose second decision split this off.

## The case (2026-11-26)

Locary's LOC-2204: the fast tier's rebase run resolved both conflicting paths and committed, then wrote a `result.json` missing the comma after `summary`. The runner refused it (`expected , or } at line 5 column 3`), a failed run, and the retry on the Build routing reset the branch to Owlshift's last push and redid the rebase, about 10 minutes.

## The decisions (2026-11-27)

The orchestrator settled them from the ticket and section 5.

- **Where the retry runs, and how it counts.** On the Build routing, counted as a failed run as before: section 5 already says a failed fast run is retried once on the Build routing and a second failure parks. Rejected: freeing the refusal as Build's is and retrying on the fast tier, which gives a rebase three runs.
- **What happens when the refused run left no usable commit.** Today's reset to Owlshift's last push, untold: the retry is told only when it starts from the kept commit, so the role says where the branch stands from the brief alone.
- **Where the commit is kept.** In the command's memory, as intake's and the review roles' told retries; not in the ticket ref.
