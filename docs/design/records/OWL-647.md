## Live check R1, macOS (2026-11-24)

macOS 26.6.2 (25G83), Apple silicon; Swift 6.4 (swiftlang-6.4.0.34.1) of the Command Line Tools, without Xcode; SwiftPM's default build system, Swift Build.

**The plugin, unconfined.** Each run used a package with one swift-testing test and started from an empty `.build`.
- Plain `swift test` failed with "plugin for module 'TestingMacros' not found" in 25 of 47 runs: by hand, in `owl-647.sh`'s unconfined runs, in `owl-647-bisect.sh` (0 of its 5), and in four runs in each of two folders.
- None of these changed it: `--disable-sandbox`, `-j 1`, `SWIFT_DETERMINISTIC_HASHING=1`, `--disable-xctest`, or the package's folder (under `/private/tmp` or under the home). `--build-system native` fails sooner, with no module `Testing`.
- In the `-v` logs of a failing run, Swift Build passed the test target no `-external-plugin-path …/host/plugins/testing#…/swift-plugin-server`. A passing run had it.
- Given `-Xswiftc -plugin-path -Xswiftc <runtimeResourcePath>/host/plugins/testing`, none of the more than 40 builds of this record, confined or not, missed the plugin.
- One build that failed so failed again when rerun on the same `.build`.

**The gate, confined.** Script: `owl-647.sh` with `RUNS=3`, its binary a local build whose `stack::swift` writes the note's lines (as OWL-638's check did). The fixture is owl-628.sh's (`Files` 4.2.0 from GitHub, one swift-testing test).

**The link.** The system log (`log stream --predicate 'sender == "Sandbox"'`) showed `swift-driver deny(1) file-write-create /private/tmp/TemporaryDirectory.XXXXXX` at each failure.

`ps -E`, during an unconfined build, showed the environment Swift Build gives its tasks:
- the linker's: `PATH`, `__CF_USER_TEXT_ENCODING` and llbuild's own variables;
- the compiler's: these and `DEVELOPER_DIR`, `SDKROOT` and `TOOLCHAINS`;
- neither has `TMPDIR` or `HOME`.

Swift Build drives the compiles itself, in a process that has `TMPDIR`; the link it hands to a separate `swiftc`. The swift-driver makes a temporary folder as it starts: under the profile that refuses writes in `/private/tmp` and `/private/var/tmp` (below), `swiftc --version` without `TMPDIR` fails the same way.

Without `TMPDIR`, the driver asks the system for the user's temporary folder. The sandbox leaves that question unanswered since OWL-637, so the driver falls back to `/tmp`, closed.

`owl-647-bisect.sh` ran `sandbox-exec` with `(allow default)` and a few denials, the plugin path given, `TMPDIR` set for `swift test`:
- With the two services of OWL-637 closed, the test passed when writes were refused in any one of `/private/tmp`, `/private/var/tmp` and `/private/var/folders`. It also passed with `/private/tmp` and `/private/var/folders` refused together, and with `/private/var/tmp` and `/private/var/folders` refused together.
- It failed, `permissionDenied` at the link, whenever `/private/tmp` and `/private/var/tmp` were both refused.
- The failing link command, replayed alone under that profile with `PATH` alone, failed. With `TMPDIR` added, it passed. Hence the cause: the link's `swiftc` gets no `TMPDIR`. An attempt to hand it one as a build setting, `-Xxcbuild TMPDIR=…`, failed the same way.

The other refusals in the log changed no verdict, the compiles passing:
- swift-frontend writing `/private/var/tmp/swift-generated-sources`;
- swift-package reading its caches in the home;
- `/usr/bin/git`, the Command Line Tools' shim, writing `/private/tmp/xcrun_db`.

**The one rule that passes.** A local, uncommitted change to `seatbelt_profile` added this rule last before the `mach-lookup` denials:

```
(allow file-read-data file-read-xattr file-write* (regex #"^/private/tmp/TemporaryDirectory\.[^/]+(/|$)"))
```

With it, `owl-647.sh` (`RUNS=1`) gave:
- the lines on empty run caches: green in 74 s, 90 MB of module cache; green again in 54 s;
- `CLANG_MODULE_CACHE_PATH` removed: red at the setup in 3 s;
- the plain test line: red, the plugin not found.

## Why Swift stays a note

- **The rule above, refused.** `/private/tmp` is one folder for every confined run on the machine. The rule opens the driver's names there to every confined command, so one project's run could read another's linker temporaries, or rewrite them while that run links. That is the reason section 8 of the architecture gives for refusing the names `mktemp` makes in the user's own temporary folder (OWL-637). The narrower kin of that rule, opening only a run's own name, cannot be written: `mkdtemp` draws the name, and the profile is set before the run starts.
- **Lines written only when `init` runs on Linux, refused.** The project file is committed and shared. A macOS machine running the same project would get a red gate. And `CLANG_MODULE_CACHE_PATH` cannot meet OWL-624's rule for a variable: it never passed confined on macOS.
- **Lines written everywhere, refused.** The macOS gate is red confined, and "More stacks" leaves an ecosystem whose gate does not pass confined a note.
