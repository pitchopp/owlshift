# OWL-625 · Assign the after-merge follow-up of a person's steps to the decider

Settles: [architecture](../architecture.md) section 4, "A person's steps", "At delivery"; follows [OWL-619](OWL-619.md), which files the follow-up.

## As built (2026-11-22)

- `Proposal` (the tracker trait's filing) gains `assignee: Option<&str>`, the tracker's own account id as `Person::id` gives it. `proposals::Filing::assignee` carries the ticket's decider, and `file_owed` passes it to the one follow-up `Filing::exempt` names; every other proposal is filed unassigned.
- The decider is resolved by `on_demand::after_merge_decider`: `pending_decider` and `decide`, the rules of a question. Deviation: the zone owners come from the project file the command loaded (`owlshift watch` files the follow-up and reads none at the base commit, where a question's decider reads them). It is resolved while the follow-up is still to be filed (`proposals::unfiled_after_merge`: not kept, or kept owed after a refusal), so a retry assigns as the first filing would. A follow-up found already filed after a crash is never assigned. A ticket that cannot be read, or owners that cannot be read, is a `warning` event (`after_merge_decider`); one with no decider files the follow-up unassigned.
- Linear: the issue is created as before, then `issueUpdate(assigneeId)` is sent and its answer checked. A refused, failed or mismatched assignment is a `Filed::problems` entry, so the follow-up is never lost and the relation is still written.
- GitHub Issues: the decider is a numeric id, `assignees` takes a login. The adapter reads it with `GET user/<id>` (`account_name`, OWL-552) before the creation and sends `assignees` with it. GitHub drops an assignee it cannot assign without an error, so the answer's assignees are checked; an unreadable or unknown account, or a dropped assignee, is a problem.
- Markdown: no assignment (its assignee is a name in the front matter that no run reads as an account of the tracker). The follow-up's text names the decider: "DEMO-1's decider (name)", and says that where the tracker can assign, the ticket is assigned to them.
- No live tracker write was made: the checks are the adapters' scripted Linear transport, GitHub's canned answers and the bench scenario `the_steps_after_the_merge_are_filed_as_one_follow_up_once_merged`, which asserts the assignee the bench tracker received.
