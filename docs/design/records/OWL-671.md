# OWL-671 · Find why the hard-kill UI test times out under heavy load

With OWL-672, "Make the process and daemon tests hold under a loaded full-workspace run", folded in.

Settles: [build plan](../build-plan.md), "The test bench", "Waits in tests" (applied, not changed); [architecture](../architecture.md) section 5, "The background service", the web UI's ends (a hard kill leaves the UI to the daemon's sentinel).

## The failures

- OWL-671: in [OWL-667](OWL-667.md)'s run of `main` under five full workspace runs at once (load 156 to 222), daemon `a_sigterm_and_a_hard_kill_leave_no_ui` timed out once on "the web UI to be gone and its port free". The wait could not say which half was missing.
- OWL-672: Owlshift's rebase run on OWL-654 (pull request #638, run of 2026-11-27 09:57 UTC, on a base before #646) had 7 of 2697 tests fail in one full run and pass alone. Six were OWL-667's, fixed by #646: child_steps `a_sigterm_during_two_builds_checks_both_and_both_resume`, `a_build_canceled_in_watch_s_own_process_stops_and_parks_the_watch_going_on`, `two_projects_two_in_flight_each_share_two_slots`, and daemon `s11_a_checked_stop_resumes_both_builds_and_a_kill_quarantines`, `a_canceled_build_is_stopped_checked_and_parked_then_resumed_from_its_checkpoint`, `an_upgrade_drain_lets_the_steps_under_way_finish_then_exits_75`. The seventh, owlshift-platform `process::sentinel::tests::a_sentinel_that_stops_nothing_fails_and_leaves_nothing`, is fixed here: `Fails("the test sentinel still ran 300 ms after its input ended")`.

## The cause of the OWL-671 timeout

The sentinel's window between a tree's start and the line that tells the sentinel of it. `register` (`process/signals.rs`) spawns the tree, then writes `+ <group>` to the sentinel. A kill in between leaves that tree running, a limit `stop_trees_when_killed` states, "well under a millisecond". On a loaded machine the window is as long as the daemon waits to run again after the spawn: there, the daemon's web UI started, started its own sentinel, took its socket, wrote its pid and answered the test, all before the daemon had told its sentinel of it. The test then killed the daemon, the sentinel did not know the UI, and the UI outlived the kill, holding its port.

Seen once, at 13:38 UTC on 2026-11-27, in a stress loop of the six UI tests running while five full workspace runs ended (load about 200), with this change's diagnosis (one of 39 runs of the test there): after 120 s, `the UI runs: true; port …: not free`, `ps` showed the UI asleep with parent 1, `lsof` the UI alone listening on the port, and the daemon's output ended before its line `Started the web UI on 127.0.0.1:… (pid …)`, which it says once `register` has returned.

Kept as it is in the product: closing the window changes the sentinel's protocol (the child announcing itself before it executes, the parent confirming or withdrawing), a decision for its own ticket. The two tests that hard-kill the daemon now kill it once the daemon has said it started the process they check, so after the sentinel was told: `a_sigterm_and_a_hard_kill_leave_no_ui` and `a_hard_kill_of_the_daemon_leaves_no_watch_or_step`.

## Measures (2026-11-27)

Round 1 did not reproduce the timeout: none of its 2100 waits, 468 of them in the hard-kill test, came near the bound. What it measured on the path that wait takes:

- **The UI's sentinel held the UI's socket.** Every process starts its sentinel first in `main` (`process::stop_trees_when_killed`), before the `ui` command adopts the socket and the run secret's pipe the daemon handed it, which `adopt_listener` makes close-on-exec. So the sentinel, `/bin/sh`, inherited both, and the port stayed bound until the sentinel too had read the end of its input and ended. A successor daemon's sentinel held the daemon's lock (`daemon --lock-fd`) the same way.
- **`kill -0` reads a zombie as alive on macOS** (checked: exit 0 on a `<defunct>` child). After a hard kill the UI is an orphan, its end read by launchd: 577 orphans killed under the load read gone after 0.038 s at the median, 0.93 s at most.
- **The pid space went round every 20 s or so** (about 4400 new pids a second at a load of 160 to 180), so a pid read alive may be another process's.
- **Ephemeral ports are handed out in order on macOS**, about 15 a second under that load (a round in about 18 minutes): of 4110 ports freed, none was taken by another listener within 5 s. A client connection or a `TIME_WAIT` on the port does not refuse `TcpListener::bind`, which sets `SO_REUSEADDR` (checked).

Each of these made the wait's verdict depend on a process other than the UI; none held it for 120 s by itself. The wait's diagnosis, added for them, named the cause above when the timeout came back.

## As built

- `process::sentinel`: a sentinel, and each process of the sentinel probe, inherits no descriptor of its starter's but its standard streams (`inherit_none`): each descriptor above them open when it starts, as `/dev/fd` lists them, is made close-on-exec in the child just before it executes, never in the starter, whose later children may need one. A descriptor opened after that listing by another thread, not close-on-exec, is still inherited; when `/dev/fd` cannot be read, the sentinel starts inheriting as before. Tests: `a_sentinel_keeps_no_descriptor_handed_to_its_starter` (an inheritable pipe's write end, dropped by the starter once a sentinel runs, reads its end at once), and daemon `a_watch_holds_no_socket_of_the_ui`, which now also checks that no child of the UI holds its socket. Both failed without the change.
- daemon `Bench::ui_gone`: the UI is gone once `ps` shows no process at its pid running as the UI's stand-in (no row, a zombie, or another command); a `ps` that fails otherwise tells nothing, and the wait goes on. A timeout prints which half is missing, `ps` of the pid and `lsof` of the port before the bench's output. Its bound is unchanged, `wait::REACHED`.
- daemon `Bench::told_its_sentinel_of`: waits for the daemon's line saying it started a pid, before a test kills the daemon outright.
- `a_sentinel_that_stops_nothing…`: its case is the probe's bound, 300 ms, and the verdict on the group comes only once the test sentinel ended, so a probe cut before then runs again with twice the bound, `wait::REACHED` at most, as OWL-667 decided for a cut that comes before the state the test checks. The probe's own time is measured in the helper: at least the bound, and less than the bound plus `wait::REACHED`; the former 5 s ceiling on the helper's whole run was a deadline the passing path had to beat. `the_sentinel_stops_a_group_when_its_input_ends` gives the probe `wait::REACHED` instead of 5 s, and the stopped-sentinel tests wait for a status within `wait::REACHED` instead of 5 s. The doctor's own probe keeps its 5 s (`SENTINEL_PROBE_TIMEOUT`, OWL-90): with it, the working-sentinel test passed 1307 of 1307 under round 1's load.
- `the_ui_starts_with_the_daemon_and_starts_again_after_a_kill`: the clock starts before the signal. Started after `kill` had ended, it missed what load added to `kill`'s own time. Reading the delays the daemon chose from what it said was tried and left out: an unrelated end of the UI (below) shifts them.

## Left as they are

- The sentinel's window above, in the product, for every process tree: on a loaded machine a hard kill right after a start can leave that tree running.
- A web UI that starts without its run secret's descriptor: in round 2's stress, one UI stand-in ended at once with `descriptor 14 is not open: nothing was handed over on it`, and the daemon started it again, an end `a_stop_and_an_upgrade_end_the_ui_after_the_watches` counts. The same six tests for 4 minutes each at a load of about 40, at 13:45 UTC: 1 such end in 2157 UI starts with this change, 5 in 2205 without it, always in that test, whose daemon runs a watch beside the UI. It does not come from this change; its cause is not known.
- The UI restart test proves the delay was waited only up to `kill`'s and a start's own time: a daemon that started the UI again at once is caught where those take less than the delay, as on a machine at rest.
- A pid the UI ended with, taken in the same moments by another test's UI stand-in, reads as the UI.
- The other waits of `tests/daemon.rs` read a process through `kill -0`, zombie or reused pid included: launchd reads an orphan's end in 0.04 s at the median, and none of them failed in either round.
