# OWL-631 · Note a toolchain that a version manager in the home installs

Settles: [architecture](../architecture.md) section 8, "Caches a run may write", "Tool chains": the paragraph's rule that a version manager whose installs live in the home stays closed to confined runs until its folder is declared and allowed; `owlshift init` now says so before the first gate. Follow-up of [OWL-624](OWL-624.md), whose poetry check needed `.pyenv` declared.

## As built (2026-11-23)

- **Notes only.** No `caches` and no `run_caches` line is written: the folder is the machine's, not the project's. So the ticket's run-cache method (a variable kept only after a confined live check on macOS and Linux) does not apply, and no confined check was run.
- **Core** (`owlshift_core::stack::home_toolchains`, a source after `ruby` in `detect`'s fixed order, skipped under `.tool-versions`): one notes-only `Found`, source `tool chains in the home`. `.tool-versions` joined `MANIFESTS`, read for the first word of each line that is not blank or a comment.
  - A manager the runner found gives the folder to declare, for a root of its language: pyenv for Python (`pyproject.toml`, `requirements.txt`, `.python-version`, or `python` in `.tool-versions`), rbenv for Ruby (`Gemfile`, `.ruby-version`, or `ruby`), asdf for a `.tool-versions` naming a tool, pipx for a `pyproject.toml` beside `poetry.lock` or `pdm.lock`. The note reads `declare caches = [".pyenv"] under [stack] and allow .pyenv in your personal allow_caches, or install … outside the home`. Only poetry was seen to fail on pyenv's folder (OWL-624), so each manager note says when it applies ("when the gate's Python, or poetry looking for one, goes through pyenv").
  - Each pinning file gives a note naming the managers that install it in the home (pyenv, rbenv, rvm, chruby, asdf, mise), unless a manager found reads that file. `.python-version` beside a `uv.lock` gives none: uv installs the pinned Python into its `UV_PYTHON_INSTALL_DIR` run cache.
  - Tests: `stack::tests::a_pinned_tool_chain_names_the_managers_that_install_it_in_the_home`, `a_manager_in_the_home_names_its_folder_for_its_language_only`, `an_unread_tool_versions_is_skipped`.
- **Runner** (`init::home_managers`): reads `HOME`, `PATH` and the managers' variables. A manager counts when a file of its name is in a `PATH` folder and its installs folder lies under the home, both canonicalized: its variable when set (`PYENV_ROOT`, `RBENV_ROOT`, `ASDF_DATA_DIR`, `PIPX_HOME`), else the first default that exists. An empty or non-UTF-8 relative folder is dropped. Test: `init::tests::a_manager_on_path_counts_with_its_installs_in_the_home`.
- **Otherwise than the ticket's words.** The ticket reads "the manager on PATH resolves into the home". The installs folder decides instead. Homebrew's pyenv lies in `/opt/homebrew` and installs into `~/.pyenv`, which is OWL-624's case. A manager installed in the home has its installs there too, so the literal case is covered.
- **CLI**: `owlshift init` fills `RootFiles.home_managers` before `detect`. The notes show in the detection report (`  Note: …`) and as `# note:` above the gate in `owlshift.toml`, through the existing paths. Tests: `init_notes_a_tool_chain_a_version_manager_may_install_in_the_home` (cli), `init::tests::a_pinned_python_writes_its_note_above_the_gate`.

## Live check R1, Linux (2026-11-23)

pipx 1.18.19 installed with pip into a virtualenv, `HOME` moved to a scratch folder, Python 3.13.18. `pipx environment` gave `PIPX_HOME=~/.local/share/pipx`, `PIPX_BIN_DIR=~/.local/bin`; `pipx install pycowsay` made `~/.local/bin/pycowsay` a link into `~/.local/share/pipx/venvs/pycowsay/bin/`. pipx's `paths.py` takes `PIPX_HOME`, then the legacy `~/.local/pipx` when it exists, then platformdirs' data folder (`~/Library/Application Support/pipx` on macOS, not run): `home_managers` checks them in that order.

It decides: pipx's folder is the note's `.local/share/pipx` or `.local/pipx` on Linux.

## Not checked

- pyenv, rbenv and asdf, whose defaults (`~/.pyenv`, `~/.rbenv`, `~/.asdf`) and variables come from their documentation: cloning them to call `pyenv root` was refused in the session's container. They only feed the notes' text and the folder looked for.
- mise, rvm and chruby are named in the files' notes, not looked for on `PATH`. `XDG_DATA_HOME`, which moves pipx's and mise's folders on Linux, is not read.
- A manager note is written even when the personal `allow_caches` already holds the folder.
