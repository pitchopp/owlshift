# OWL-666 · Keep the nextest gate within its deadline when the host is loaded

Settles: [build plan](../build-plan.md), "The project gate", "Output and deadline"; "`stack.setup`" (the setup's share).

## Why (2026-11-26)

When several Owlshift runs share one machine, this repository's gate takes about the whole of the runner's gate deadline, then 30 minutes (`DEFAULT_GATE_TIMEOUT`, `crates/owlshift-runner/src/executor/gate.rs`), and a correct branch fails on load alone. OWL-654's gate was stopped at 1800 s with 2621 of 2622 tests passed, the last one (`waits_scenarios::a_build_waiting_on_a_zone_names_its_holder_and_the_zone`) passing alone in 19.7 s. The same day, `cargo nextest run -p owlshift-testkit --test on_demand` took 1825 s for 435 tests at a load average of 34 to 96 on 18 cores, single scenarios 200 to 400 s.

## As built (2026-11-27)

- `DEFAULT_GATE_TIMEOUT` is 60 minutes, for every project: the worst gate seen under load ran past 1800 s, and the hour leaves it about twice that. The setup's share, a third (`SETUP_SHARE`), follows to 20 minutes, so a setup stalled on a slow network (as OWL-624's and OWL-627's checks saw) now holds its run 20 minutes before it fails. The share is kept as it is.
- What else the change reaches: `owlshift gate` builds the same executor and gets the hour too. Nothing else is bound to the gate's deadline: a Build's harness keeps its own 2 hours (`DEFAULT_RUN_TIMEOUT`), the gate running after its `done`; a claim's lease is 24 hours; the resolver's, the clone's and the usage probe's 30 minutes are their own. No test states the constant, so none changes. The failure's reason already gives the deadline in seconds.
- A gate that truly hangs (nextest has no `slow-timeout` here) now holds its run, its slot and its claim an hour instead of 30 minutes, on every project. Accepted: a false red under load is what happened, a hang is not.
- No CI setting changed: `.config/nextest.toml` and `ci.yml` are as they were, so the decider's approval of architecture section 8's floor is not needed.
- The records written before this one (OWL-624, OWL-627, OWL-638, OWL-647) and `docs/design/live-checks/owl-624.sh` keep their 30 minutes or 1800 s: they are dated.
- Rejected: a key of the project file setting the deadline (`stack`), which `owlshift.toml` would set to an hour: the configuration, its schema, the `init` example, `config show` and the run's specification to change, for one project that needs it. It becomes worth it when a project needs more than the hour, or when an hour-long hang costs a project more than a false red. A cap on nextest's threads for the on_demand binary, measured below: slower, and a CI setting. More threads than cores: not measured, more load for the other runs, and a CI setting too.

## Measures (2026-11-27)

On the maintainer's machine (macOS, Apple silicon, 18 cores, 48 GB), cargo-nextest 0.9.146, while three other agents' builds and gates of this repository shared it, so the load is theirs as much as these runs'. Not an idle machine, and not the same load from one run to the next.

- `cargo nextest run --locked --no-fail-fast -p owlshift-testkit --test on_demand`, nextest's default 18 threads: 440 tests passed in 713 s; load average (one minute, sampled every 15 s) 29 to 66, median 47; the slowest test 133 s (`pipeline_scenarios::scenario_a_risky_plan_refused_approved_and_replanned`), 20 tests over 60 s.
- The same with `--test-threads 6`: stopped after 938 s with 225 tests passed; load average 26 to 100, median 60. The load was higher than in the first run, so the two are not a clean comparison, but the cap's cost does not hang on it: a test's mean time fell only from 22.0 s to 17.4 s (the first 170 tests of each run), so six threads pass about 0.34 tests a second against 0.82 for eighteen. The tests wait on the processes they start more than they compute, and fewer at once means a longer run.
- Building every test binary (`cargo nextest run --workspace --locked --no-run`) on a target that had not built this branch: 2 min 36 s.
- The whole gate, the five commands of `owlshift.toml` in order, on this change's branch, on the target the runs above had built, which recompiled the runner and what depends on it: passed in 1683 s, 28 minutes, at a load average of 73 to 261, median 130, the heaviest of the day. `cargo fmt --check` 32 s, clippy 200 s, rustdoc 161 s, nextest 1274 s (2683 tests passed, 102 skipped, 89 slow, the slowest 201 s), the doctests 16 s. That is 47 % of the hour, and 117 s short of the old 30 minutes.

The full gate's time is a check that the hour holds on such a day, not a measure of the margin: the margin is reckoned from 2026-11-26's gate, the worst one seen.
