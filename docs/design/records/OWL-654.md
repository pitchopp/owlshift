# OWL-654 · Refresh an overlapping pull request once, when it could otherwise merge

Settles: [architecture](../architecture.md) section 5, "Tolerated overlap", *The refresh* and *The merge*; "Merge on green", *The guarantee given up*.

## Designed (2026-11-26)

Under `policy.overlap = "rebase"`, watch scheduled a refresh rebase each time a new base head changed a path one of the ticket's overlaps names, whatever the pull request waited for. On Locary, LOC-2200 (pitchopp/locary#1783) refreshed onto 84072d47 (2026-11-25 20:22 UTC), 2378077c (21:47) and b7f0608f (23:52), and a fourth was due on 2026-11-26 08:35, while it waited for its decider from 02:22 to 08:29. Each refresh costs a rebase run (median 15 minutes, mostly the gate) and the pull request's CI again (Locary median 43 minutes).

The refresh is now owed, recomputed at each pass, and runs once the pull request could otherwise merge, onto the base head of that moment. Two points the ticket left open were decided by the resolver on 2026-11-26:

- **Q1, a person's merge.** Under `[forge] merge = "never"`, or `labeled` without the label, an owed refresh runs once the pull request is otherwise ready for the person: green, no question, correction, review loop or person's step pending. A later sibling merge on a shared path while it waits for the person makes it owed again. Waiting for an approving review was rejected: a person who merges right after approving merges checks that were not refreshed.
- **Q2, the checks.** An owed refresh waits for a green read of the pull request's own checks. While they run it stays owed; a red read gets its fix run, whose push records its `base_at_push` and clears the refresh when that base holds the sibling's change. The cost: when the checks were the only thing left, the refresh waits one more CI run.

Two readings follow from Q1 and are written in the design: a question its decider answered (a `security` one included) or one the resolver decided holds no refresh, though it holds the runner's merge; and the forge's review decision (a required approval missing, changes requested) holds none either, since under `all` the runner merges as soon as the approval comes.

What the Locary case gives under the rule is not settled by the ticket's timestamps. The refreshes are 85 and 125 minutes apart, against a median rebase run plus Locary's median CI of 15 + 43 = 58 minutes, so the pull request may have been green with nothing pending between two sibling merges; and watch does not follow a ticket whose round waits for its decider, so the decider's wait ran no refresh by itself. Under Q2 the replay can give anywhere from 1 to 4. The replay on `events.jsonl` decides (below).

## As built (2026-11-26)

- **Where it is decided.** The core's table (`follow::decide`) no longer returns a refresh rebase for an overlap: `Followed::overlap` is gone, and a mergeable read goes on to the checks; a conflict still gets its rebase at once. Merge on green's `blocker` is split, in its order, into `not_green` and `otherwise_ready(gate, facts, QuestionHold)`; `MergeFacts::overlap` names the base head an owed refresh would rebase onto, and `merge_due` waits on `MergeBlocker::OverlapOwed` while it is set, after `SomethingDue` and before `BaseUnknown` and `BaseMoved` (rows in `merge_due`'s existing table). `overlap_refresh(gate, facts, read)` returns the owed refresh and what it waits for: `not_green`, then `otherwise_ready` with `QuestionHold::Refresh`, which calls `held_question` on the questions still `Open` only, so one predicate decides which questions hold. It never reads the switch or the labels. `OverlapOwed` is reached by `continue`'s merge note; watch decides the refresh before `merge_due`.
- **Watch.** `Watch::merge` reads on under `merge = "never"` when a refresh is owed (`Refreshes::due`), and a refusal it holds for the head and base holds no owed refresh. It asks `overlap_refresh` first: with no wait it runs `Watch::refresh`, merge on green's refresh rebase, whose repair (`OnDemand::repair_due`) names its cause `overlap` when its own fetch reads the base changing a path an overlap names (`overlap_base`), else `merge`; with a wait it tells it. `needs_draft` takes the blocker, `None` when everything else held, and `OverlapOwed` among those that read the draft. `follow()` tells an owed refresh on a running or base-red read (`until` `checks`) and, on a green read, for a pending correction, review loop or person's steps (`correction`, `review`, `person_steps`), in place of `merge_due_first`. The waiting loop tells it for a ticket watch reads only for an end, once `close_outlived` found its pull request open (`tell_held_refresh`, `merge::held_until`: `question`, `park`, `review`), with no forge read of its own.
- **Telling.** Every `refresh_owed` goes through `Watch::tell_refresh`, which keeps its own memory (`Refreshes::told`, the last event per ticket, dropped once no refresh is due): `look_ending` forgets merge on green's memory at each look, so `tell_wait` would have told a waiting ticket at every pass. The event is `watch` `waits`, reason `refresh_owed`, with `onto`, `until` and, for a question, its `category` (`merge::refresh_owed`, `merge::refresh_wait`); `merge::wait_words` words it for watch's line and `owlshift why`.
- **The guard on a head already rebased onto** moved from the table to `Watch::overlap_refreshes` and `OnDemand::overlap_base` alike (`watch::refresh::rebased_onto`, unit-tested). It is close to redundant: `rebased_onto` is set only when a rebase's push lands (`follow::landed`), with `base_at_push`, and the pushed head then contains that base, which `held::base_moved_on` reads as no move.
- **`owlshift continue`** never runs an owed refresh: `look_once` reads the pull request green and its merge note says a refresh comes first (`continue_names_an_owed_refresh_and_runs_none`); watch's next pass runs it. Under `merge = "never"` the note is not shown, as before.
- **The forge's review decision** (a required approval missing, changes requested) holds no refresh: it is read only in `confirm_merge`, after the refresh is decided, as the design says.
- **Scenarios** (`crates/owlshift-testkit/tests/on_demand/overlap_scenarios.rs`): `two_siblings_merging_while_the_decider_is_asked_get_one_refresh_after_the_answer` puts DEMO-1 at `NeedsInput { return_to: Watch }` through a fix run that asks, then merges two siblings' changes to `AGENTS.md`: the refresh is told owed onto each new head, waiting for the answer, and `why` shows it; after the answer exactly one `overlap` refresh runs, onto `main`'s latest head, and the rebased head merges on green. Before OWL-654 that wait ran no refresh either (watch does not follow a ticket whose round waits); what the rule saves is a refresh per sibling merge while the pull request is followed and not ready. `under_never_an_owed_refresh_waits_for_the_checks_and_is_owed_again_after_a_later_sibling`, `labeled_without_its_label_gets_one_refresh_once_ready` and `a_fix_push_onto_a_base_holding_the_siblings_change_clears_the_owed_refresh` hold Q1 and Q2. The earlier overlap scenarios pass unchanged: each read its pull request green with nothing due. The fake GitHub's single pending read became a range (`pending_follow_reads`), which a scenario keeps open until it clears it; `later`, `merged_comments` and `github_merges` are shared from `merge_scenarios.rs` rather than copied (`person_scenarios.rs` keeps its own `later`).
- **The replay**: [`live-checks/overlap-refresh-replay.py`](../live-checks/overlap-refresh-replay.py), with its fixture: DEMO-1 (four refreshes, a decider round from the second to the fourth) gives 4 and 1; DEMO-2 (green with nothing pending between two sibling merges) 2 and 2. It reads readiness from the events of each pass and replays the old rule's history after each refresh, so its count is approximate.
