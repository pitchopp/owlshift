# OWL-654 · Refresh an overlapping pull request once, when it could otherwise merge

Settles: [architecture](../architecture.md) section 5, "Tolerated overlap", *The refresh* and *The merge*; "Merge on green", *The guarantee given up*.

## Designed (2026-11-26)

Under `policy.overlap = "rebase"`, watch scheduled a refresh rebase each time a new base head changed a path one of the ticket's overlaps names, whatever the pull request waited for. On Locary, LOC-2200 (pitchopp/locary#1783) refreshed onto 84072d47 (2026-11-25 20:22 UTC), 2378077c (21:47) and b7f0608f (23:52), and a fourth was due on 2026-11-26 08:35, while it waited for its decider from 02:22 to 08:29. Each refresh costs a rebase run (median 15 minutes, mostly the gate) and the pull request's CI again (Locary median 43 minutes).

The refresh is now owed, recomputed at each pass, and runs once the pull request could otherwise merge, onto the base head of that moment. Two points the ticket left open were decided by the resolver on 2026-11-26:

- **Q1, a person's merge.** Under `[forge] merge = "never"`, or `labeled` without the label, an owed refresh runs once the pull request is otherwise ready for the person: green, no question, correction, review loop or person's step pending. A later sibling merge on a shared path while it waits for the person makes it owed again. Waiting for an approving review was rejected: a person who merges right after approving merges checks that were not refreshed.
- **Q2, the checks.** An owed refresh waits for a green read of the pull request's own checks. While they run it stays owed; a red read gets its fix run, whose push records its `base_at_push` and clears the refresh when that base holds the sibling's change. The cost: when the checks were the only thing left, the refresh waits one more CI run.

Two readings follow from Q1 and are written in the design: a question its decider answered (a `security` one included) or one the resolver decided holds no refresh, though it holds the runner's merge; and the forge's review decision (a required approval missing, changes requested) holds none either, since under `all` the runner merges as soon as the approval comes.

What the Locary case gives under the rule is not settled by the ticket's timestamps. The refreshes are 85 and 125 minutes apart, against a median rebase run plus Locary's median CI of 15 + 43 = 58 minutes, so the pull request may have been green with nothing pending between two sibling merges; and watch does not follow a ticket whose round waits for its decider, so the decider's wait ran no refresh by itself. Under Q2 the replay can give anywhere from 1 to 4. The replay on `events.jsonl` decides (below).
