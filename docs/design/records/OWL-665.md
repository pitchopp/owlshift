# OWL-665 · Publish the gate verdict of a delivered commit as a commit status the project's CI can read

Settles: [architecture](../architecture.md) section 5, "The gate's status", and watch's check read ("What a read decides"); section 8, "GitHub credentials"; section 12, D13.

## Decisions (2026-11-27)

The ticket left three points to the design, settled from the code and the live check, and two to its decider, answered on 2026-11-27:

- *A red gate* sets nothing. Owlshift never pushes a commit whose gate failed, GitHub refuses a status on a commit it does not have (HTTP 422), and watch reads a failed commit status as a code failure, which would start a fix run.
- *The identity to trust* is the status's `creator.login`: the GitHub account that ran `owlshift init`, or the personal token's owner. A status records no app (R1); the App's user token acts as its user, so its statuses are expected to show that user, which R2 settles.
- *Only a gated SHA*: the status is set in the two places that push a ticket's branch, `deliver` and `push_repair`, from the gate the push carries; see "As built".
- *Q1, the live check's credentials:* the maintainer adds Commit statuses (read and write) to the `owl-shift` App, installs it on the sandbox, makes the fine-grained token and runs `live-checks/owl-665.sh` twice; R2 and R3 below are filled from those reports.
- *Q2, the gate's time in the description:* kept on disk, `gate_elapsed_s`, with `review.json` at format 3 and `delivery.json` at format 11, since the Build's gate and its delivery can fall in different steps.

## As built (2026-11-27)

- *The switch.* `[forge] publish_gate_status` (`config::Forge::publish_gate_status`, off when absent), read at the fetched base's project file (`project::gate_status_at`), as `merge` is. A `[forge]` table that sets only it is valid; `owlshift init`'s file lists it, commented, and the configuration reference is generated from that file.
- *The write.* `GitHubForge::set_gate_status` posts `{state: "success", context: "owlshift/gate", description}` to `repos/<owner>/<name>/statuses/<sha>` through the token's channel (a 401 on the App's token refreshes it and retries once), and `gate_status_answer` reads any answer but a 2xx as an error. The Writer's `set_gate_status` asks the floor first: `Action::SetGateStatus`, the runner's, refused from the UI. `on_demand::gate_status::description` writes "Owlshift's gate passed in 4 min 23 s: <commands joined by `; `>", cut to 140 characters with an ellipsis (R1: 141 is refused).
- *Where.* `OnDemand::publish_gate_status`, called right after a push lands and its event: in `deliver`, before the pull request is opened, from the kept Build (`KeptBuild::gate`, `gate_elapsed_s`); in `push_repair`, before the pull request's head is read, from `Repaired::gate` and `gate_elapsed`. `Repaired::gate` is `Passed` only when it was built from a gate run that passed on `Repaired::commit` (`repair_runs`, `kept_build`), or kept with that commit in one `pushing` record (`Repaired::again`, through `told`). A refresh rebase is `Gate::NotRecorded` and sets nothing, silently; a gate with no command sets nothing, with a warning.
- *The tree.* The pushed commit is the neutral image of the gated one (OWL-558), which keeps its tree header verbatim (`neutral_commits`), so no second tree check was added: a review of the plan weighed it and found the invariant already held by the only type the pushes take (`NeutralHead`).
- *Never in the way.* A switch that cannot be read, a floor refusal, a refusal or no answer from GitHub is a `warning` event `gate_status_unset` with `commit` and `reason`; a status set is a `tracker_write` event with `action` `gate_status`, `commit`, `context` and `description`. The push, the pull request and the report go on.
- *Watch's reads.* `Check::is_gate_status` and the adapter's `without_gate_status` leave every commit status of context `owlshift/gate` out of `checks`, `follow` and `base_checks` (and their extra pages), after the count against GitHub's total. This was not in the ticket's acceptance: without it a pull request whose only check is Owlshift's own status would read green before any workflow registered, and merge on green would merge it untested. A failure set under that context by anyone else is dropped too.
- *Doctor.* `Installation::statuses_write` and `AppGrants::Installed::statuses_write` read the installation's `statuses` permission; with the switch on, a `gate status` line says ok, warns (blocking nothing) with the installation's settings as its fix, or informs for a personal token or no installation. `GITHUB_TOKEN_HELP` names commit statuses (write) for the switch.
- *Formats.* `KeptBuild::gate_elapsed_s` (`review.json` format 3; formats 1 and 2 read, a format-2 one refused when its Build keeps a time) and `KeptReport::gate_elapsed_s` (`delivery.json` format 11; formats 1 to 10 read, a format-10 one refused when a report keeps a time). The time is `GateReport::elapsed`, the setup's and the commands' `elapsed` summed, awake time.
- *Tests.* Adapter: `the_gate_status_is_posted_on_the_commit`, `the_gate_status_is_no_check`, `the_apps_installation_is_found_by_slug_then_by_repository`. Contracts: the delivery and review format cases in `contracts.rs` and `quality_pipeline.rs`. Runner: `the_description_names_the_time_and_the_commands`, `a_long_description_is_cut_to_githubs_bound`, `the_gate_status_line_names_a_missing_statuses_write`, the floor and UI-writer tables. Bench: `each_gated_push_gets_the_gate_status_on_its_commit` (the delivery's status before its pull request, a fix's refused as a warning with the fix pushed, the next fix's set on its own head); every other bench test, the switch off, would panic on a status post.
- *Docs.* [Recipes](../../recipes.md), "Skip the suite Owlshift already ran": the CI step that reads the head's statuses, keeps context `owlshift/gate` from the listed logins, takes the newest and requires `success`, waiting up to 30 s on Owlshift's own pull requests; and what it does not cover.

## Built otherwise than designed

- *A crash* between the push and the status may leave none: a later read that adopts the push sets none, and the CI then runs its suite; a push made again from the kept `pushing` sets it.
- *A push made again* that finds the branch already at its commit (`up_to_date`) sets the status again: GitHub keeps one more status of the same context.

## Live check R1 (2026-11-27): the gh CLI's OAuth token

On `pitchopp/owlshift-live-sandbox`, the head of `main`, with the gh CLI's OAuth token (scopes `repo`, `workflow` among others):

- `POST /repos/{owner}/{repo}/statuses/{sha}` with `state` `success`, `context` `owlshift/gate`: HTTP 201.
- Read back through `GET /repos/{owner}/{repo}/commits/{sha}/statuses`: `state` `success`, `context` `owlshift/gate`, and `creator` the token's own account, `type` `User`. The status's fields are `avatar_url`, `context`, `created_at`, `creator`, `description`, `id`, `node_id`, `state`, `target_url`, `updated_at`, `url`: no app is named.
- The same post on a commit GitHub does not have: HTTP 422 "No commit found for SHA".
- A description of 141 characters: HTTP 422 "Description is too long (maximum is 140 characters)".

It decides the 140-character cut, the 422 that rules out a status on an unpushed red commit, and that a CI can trust a status by its `creator` alone, no app field being there to read.

## Live check R2: the GitHub App's user token (2026-11-27)

`owl-shift` asks Commit statuses (read and write); the maintainer's installation, which covers the sandbox, accepted it on 2026-11-27. Run with the `access_token` of a project's `github-app` keychain entry:

```
OWL-665 live check, 2026-11-27T23:39:58Z, token kind: app
commit: the default branch's head (main)
POST /repos/{repo}/statuses/{sha}: HTTP 201
  x-accepted-github-permissions: statuses=write
GET /repos/{repo}/commits/{sha}/statuses: HTTP 200
  state: success, context: owlshift/gate, description: OWL-665 live check, app token
  creator: type User, the token's own account: yes
  creator is a bot (login ends with [bot]): false
  fields: avatar_url, context, created_at, creator, description, id, node_id, state, target_url, updated_at, url
```

As expected: the App's user token sets the status as its user, whose login is the `creator` a project's CI trusts; no app or bot appears, and the permission GitHub checks is `statuses=write`. An entry whose token has expired (8 hours) is refused with HTTP 401 at `GET /user`.

## Live check R3: a fine-grained personal token (2026-11-27)

A fine-grained token on the sandbox only, with Commit statuses (read and write); the first run, without Contents, got HTTP 403 at `GET /repos/{repo}/commits/{branch}`, the script's own read of the head, before any status was set. With Contents (read) added:

```
OWL-665 live check, 2026-11-27T23:44:20Z, token kind: fine-grained
commit: the default branch's head (main)
POST /repos/{repo}/statuses/{sha}: HTTP 201
  x-accepted-github-permissions: statuses=write
GET /repos/{repo}/commits/{sha}/statuses: HTTP 200
  the status set is not listed
```

The read-back right after the write missed the new status. Read again a minute later, with another credential, the commit's statuses held it: `creator` type `User`, the token's owner, not a bot. As expected: a personal token sets the status as its owner, the login a project's CI trusts, with `statuses=write` the permission GitHub checks. The script now retries its read-back for a few seconds. Owlshift itself does not read the status back, so the lag changes nothing in the product; the personal token Owlshift uses already holds Contents (write) to push.
