# OWL-646 · Make plain cargo test robust to file descriptors that other tests' children inherit

Settles: [architecture](../architecture.md) section 5, "A lock just released"; [OWL-645's record](OWL-645.md), "Not met: three full runs in a row", whose two kinds of failure this ticket removes.

## The cause (2026-11-24)

Under `cargo test` the tests of a binary share one process. A child that one test forks gets a copy of every descriptor open in the process at that moment, and keeps it until it starts its own program. The standard library opens every descriptor close-on-exec, so setting close-on-exec everywhere changes nothing: the copy lives from the fork to the exec. Two kinds of failure follow:

- **A program just written is refused (`ETXTBSY`).** Linux refuses to run a file that some descriptor still holds open for writing. If the test that wrote the file has closed it, a child that another test forked meanwhile still holds the write.
- **A lock just released is read as held.** An `flock` belongs to the open file description. A lock that is released only by closing its descriptor stays held while the child's copy of that descriptor lives.

**Probe.** A Python script forks a child that sleeps 1 s without exec. It was run in OWL-645's rig (Linux 6.12.76-linuxkit) and on macOS 26.6 (Darwin 25.6.0):

| Case | Linux | macOS |
| --- | --- | --- |
| File written in the process, child alive, file run | `ETXTBSY` | runs |
| Same file written by `cp`, child alive, file run | runs | runs |
| `flock` released by close, child alive, lock tried | held | held |
| `flock` released by `LOCK_UN`, child alive, lock tried | free | free |

## As built (2026-11-24)

Two mechanisms, one for each kind of failure. Neither fixes tests one by one.

### Executables are written by a child process

`owlshift-testkit`'s `stand_in.rs` gains `write_executable` and `copy_executable`. On Unix they write through a child process: `cat`, fed on its input, for written contents, and `cp` for a copy. They then set mode 0o755 by path. The test's process therefore never holds a descriptor open for writing on a file it will run. Each helper checks the child's exit status and panics with the path; it never sets the mode after a failure. On other systems they do a plain write or copy.

`stand_in::write` uses `write_executable`. The places converted to the helpers:

- the platform's `process.rs` tests: the copy of `/bin/sh` that OWL-645 saw refused, and three scripts;
- the runner's `install.rs` and `executor/git.rs` tests;
- the testkit's `step_child.rs` (the ssh command and `holding_harness`) and `bin_copy.rs` (the copy of each binary under test);
- the testkit's tests `child_steps.rs`, `confinement.rs`, `daemon.rs` (the copy of the daemon bench, the failing script), `executor.rs`, `on_demand.rs` and its `cli_restart_scenarios.rs` and `drain_scenarios.rs`, and `self_update.rs` (the copy made where a hard link fails);
- the CLI's `release.rs` tests.

The platform's and the runner's unit tests include `stand_in.rs` with `#[path]`, as the CLI's and the runner's integration tests already did. The testkit depends on both crates, so neither can depend on the testkit.

**One case left to a retry.** An executable that production code writes in the test's own process is not written by the helpers. The case is `process::pin_copy`'s copy in the platform's two pin tests. Its first start goes through `stand_in::start_once`, which since OWL-645 retries a start refused as busy, for 10 s at most.

**Guard.** `owlshift-testkit`'s `every_executable_a_test_writes_goes_through_stand_in` scans the workspace's sources. It refuses a `mode(0o…)` literal with an execute bit for the group or others outside `stand_in.rs`, unless the line before says why it is not an executable a test writes. Three lines say so: two folder modes and the staged binary of `owlshift self-update`. Owner-only modes (0o700, 0o500) are folders' modes and are not looked at.

A copy of an executable names no mode in the source, so the guard cannot see it. The copies were audited instead. These ones copy no executable that is run:

- `on_demand.rs`'s `copy_dir`, a git directory whose only executables are `*.sample` hooks;
- the testkit's `git.rs` `copy_tree`, fixtures, none of them executable in the repository;
- `confined_setup.rs`, package archives;
- `session_live.rs`, session files;
- `ui_server.rs`, a registry file.

### Locks are released explicitly

The runner's `project::FileLock` owns the `File` whose lock this process took. Its drop calls `File::unlock` before the descriptor closes. If the unlock fails, the close that follows releases the lock, as before; the drop never panics. Every lock the runner takes goes through its constructors (`try_exclusive`, `try_shared`, `exclusive`), and so do the probes, a try let go at once:

- `held_alone`;
- the run slots' count;
- `watch::presence::watching`;
- `uninstall`'s `is_held`.

The holders that now keep a `FileLock`:

- the project lock and the ticket lock;
- `under_lock`;
- the served lock and the claim lock;
- the account lock and the usage file's lock;
- the run slot;
- watch's presence and its holder record;
- the event log's append.

The runner's own `clippy.toml` refuses the standard library's four lock methods anywhere else in the crate. It is not a workspace file, so the testkit and the CLI's tests, which hold a lock for a whole test as "another holder", are not affected. The testkit's `bin_copy.rs` uses the standard library only. It releases cargo's lock, the `copying` lock and its probe explicitly through a small wrapper of its own.

**The one exception: the daemon's lock.** The daemon hands its lock to the daemon of a newer binary on a copy of its descriptor (OWL-616). An explicit unlock would take the lock from that daemon too. `daemon::instance::lock` and `adopt` keep a plain `File` (`FileLock::into_file`), released by the close alone, as before. Its tests already run alone (OWL-645).

**Audit.** No other lock is meant to outlive its descriptor into a child. The grep of 2026-11-24 found that `hand_over_file` is called only by `daemon::successor`. No `pre_exec`, `Stdio::from(File)`, `into_raw_fd` or `mem::forget` carries a lock's descriptor, and every lock file is opened close-on-exec. A step's child takes its own locks. The `Mutex::try_lock` calls (`ui/server.rs`, `executor/gate.rs`) lock no file.

**Tests.**

- `project::tests::a_released_lock_is_free_while_a_child_holds_its_descriptor`. A `sleep` child inherits copies of two locks' descriptors (`process::hand_over_file`). The lock released through `FileLock` reads free at once. The lock released by the close alone reads held while the child runs.
- The close-on-exec check in `helper_one_do_at_a_time_per_project` now releases its lock by the close alone. An explicit release would hide a descriptor that a child inherited.

**What stays.** The 250 ms bound, the waits, and the tests that run alone stay. They still cover a holder that ended without its release, and the daemon's lock. Architecture section 5, "A lock just released", says so.

## Live check R1, Linux (2026-11-24)

**The rig.** OWL-645's, unchanged, with this ticket's own volumes:

- Ubuntu 24.04 aarch64 in Docker 29.4.0, kernel 6.12.76-linuxkit, 18 cores, Rust 1.98.1, on a Mac that other agents loaded (load average up to about 80 over the runs).
- The image's zoneinfo mount and `python3`, as in OWL-645.
- Each run is started with `setsid --wait` under `docker run --init`.

**Before, on `main` at `91e0e56a`.**

- One full plain `cargo test --workspace --locked --no-fail-fast` passed: 77 binaries, 2598 tests. These failures come and go, so one green run proves nothing.
- A stress of the three binaries where OWL-645 saw them, each run 8 times as a plain `cargo test` (`-p owlshift-platform --lib`, `-p owlshift-runner --lib`, `-p owlshift-testkit --test daemon`), failed 4 runs of 24:
  - `ETXTBSY` 3 times: `own_program_spawns_the_binary_this_process_started_from` twice, and `a_session_daemon_moves_onto_a_newer_binary_with_no_gap`.
  - A lock just released read as held, 3 tests in one runner run: `a_commands_ticket_lock_names_its_holder_until_it_ends`, `a_watch_is_seen_while_it_holds_its_project_and_not_after`, and `a_persons_pause_replaces_the_daemons_and_the_machines_stands_first`.
  - Two more daemon tests failed in the same run as the `ETXTBSY`: `a_watch_that_cannot_serve_pauses_its_project_until_one_serves` and `a_killed_watch_starts_again_with_a_doubling_delay_told_at_the_third_end`.

**With the change.**

- The same stress passed 24 runs of 24.
- Three full plain `cargo test --workspace --locked` runs, one after another, all passed. Each ran 77 binaries: 2600 tests passed (the 2598 plus this ticket's two), none failed, 100 ignored. They took 1121 s, 589 s and 287 s.
