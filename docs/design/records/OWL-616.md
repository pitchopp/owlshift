# OWL-616 · Move the daemon onto an upgraded binary without a command

Settles: [architecture](../architecture.md) section 5, "An upgrade", "Without a command"; [runtime and operations](../runtime-and-operations.md), "Updates & versions".

## As built (2026-11-21)

As designed. The daemon's look at its binary is `Daemon::run`'s `look_at_binary` and `probed` (`crates/owlshift-runner/src/daemon/supervise.rs`), its stamp and probe `daemon::upgrade` (`Stamp`, `probe`, `parse_version`, `end_of_drain`, `started_by_service`, `moves_onto`), the handover `daemon::successor` and `Daemon::serve`, the adoption of the lock `daemon::instance::adopt` with `owlshift_platform::process::{hand_over_file, adopt_file}`, and the record's format 3 `DaemonRecord::watches`. `owlshift daemon --lock-fd <n>` is hidden. `owlshift start` launches the session's daemon by the path it was run by when that is its own file (`binary_for_service`), as `start --at-login` names it to the service. The pin check and the look share one parser of `--version` (`upgrade::parse_version`, `BuildIdentity::parse_shown`).

Tests: on the bench (`crates/owlshift-testkit/tests/daemon.rs`), `a_session_daemon_moves_onto_a_newer_binary_with_no_gap`, `a_service_daemon_drains_then_exits_75_and_its_launcher_starts_the_new_binary` and `a_replaced_binary_not_newer_failing_or_stopped_leaves_the_daemon_as_it_was`; unit tests of the stamp, the parser, the end's decision, the wait's decision, the adoption, the record's formats and `decide`'s `MovesItself`; doctor's running builds line for a daemon that moves itself.

Not tested on the bench: a replacement written in place rather than renamed. Every installer this ticket names renames or relinks (below), and on Linux writing over a running executable fails with `ETXTBSY`; the stamp's size and modification time would still tell one.

## Live check R1: the lock across a handover (2026-11-21)

`flock` semantics the handover rests on, with a Python script: a parent takes `LOCK_EX`, hands a `dup` of the descriptor to a child it starts (`pass_fds`), and exits without unlocking; a third process probes with a fresh open and `LOCK_SH | LOCK_NB`, as `owlshift`'s instant probe does. On macOS 26.6.2 (Python 3.9.6) and in Linux 6.12.76 (rust:1-bookworm, Python 3.11.2), alike: the child's own `LOCK_EX | LOCK_NB` on the copy succeeded at once; the probe read "held" before the parent's exit and five times after it while the child lived, and "free" once the child ended. Decides that one open file description shared by the two daemons keeps the lock held through the handover.

## Live check R2: how the installers replace the binary (2026-11-21)

- Homebrew: `/opt/homebrew/bin/owlshift` is a symlink, `../Cellar/owlshift/0.2.0/bin/owlshift` (read only; nothing of the Homebrew install was touched). An upgrade relinks it to the new version's folder, so the stamp read through the link changes.
- `cargo install` (cargo 1.98.1): a crate installed into a scratch root, then installed again with `--force` after a change, left a file of another inode (494005706, then 494005999), the same size and, to the second, the same modification time. So cargo renames a new file over the binary, and the inode in the stamp is what tells it.
- `owlshift self-update` renames its staged copy over the binary (`self_update_cmd.rs`, read in the code).

## Live check R3: the real binary, without a service (2026-11-21)

macOS 26.6.2, two debug builds of this branch's `owlshift` 0.2.0: A, the design commit with this ticket's code uncommitted (a dirty build), built 18:08:00Z; B, the code commit, clean, built 18:25:34Z, so B supersedes A by "Newer" (the branch was rebased afterwards, so their commit ids are not the merged ones). Each in a Cellar-like folder of a scratch directory, `bin/owlshift` a symlink to A's, with a data and a configuration directory of the run's own (the UI on a port of its own, notifications and the digest off); nothing of the maintainer's daemon, service or Homebrew install was touched. The daemon was started from the link as `owlshift start` starts one, in a process group of its own, its output in `<data>/service/daemon.log`, serving no project. Then the link was renamed over by one to B's, as Homebrew relinks, at 18:25:49Z, and nothing was typed until B's record stood. A Python prober opened the lock afresh and tried `LOCK_SH | LOCK_NB` every 10 ms from before the relink to after B's record.

- A's record was format 3, `watches` the link. At its next pass, about 56 s later, it logged the binary at its path as newer, drained (no watch), and handed its lock to B's daemon (pid 69272); "took over" once B's record stood at 18:27:10Z, then A ended. B's record named B's commit, clean, and the same `watches`.
- The prober made 6,722 probes and found the lock free 0 times. B's record came about 20 s after its start, the time of its pin and the macOS scan of its new copy; during that window a probe read the lock held and no record, as during any pin.
- `owlshift stop` then drained B, which ended 0.

## Live check R4: the real binary under launchd (2026-11-21)

The same builds and layout, with a launcher copied from `install/units.rs` and an install manifest in the run's data directory naming it. A property list with the test label `dev.owlshift.owl616-check`, never `dev.owlshift.daemon`, sat in the scratch directory and not in `~/Library/LaunchAgents`, with `install`'s values (`RunAtLoad`, `KeepAlive` `{SuccessfulExit: false}`, `ThrottleInterval` 30, `ExitTimeOut` 60). It was loaded with `launchctl bootstrap gui/501 <plist>` at 18:27:36Z.

- The launcher started A (pid 7897, `launched` 7897).
- 31 s later the link was relinked to B at 18:28:15Z, and nothing was typed. A found B newer, drained, and logged that it exits 75 rather than handing over, the service's launcher having started it.
- launchd started the launcher again: `launchctl print` showed `runs = 2` and `last exit code = 75: EX_TEMPFAIL`. B's daemon (pid 66003, `launched` 66003) recorded B's commit at 18:28:52Z.
- `owlshift stop` ended it with 0, and launchd left it stopped (`state = not running`, `last exit code = 0`).
- `launchctl bootout gui/501/dev.owlshift.owl616-check` then unloaded it. `launchctl print gui/501/dev.owlshift.owl616-check` failed afterwards (exit 113): the label is gone. No process of either run was left (`pgrep`).
