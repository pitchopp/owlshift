# OWL-637 · Give confined runs on macOS a writable folder for mktemp without a template

Settles: [architecture](../architecture.md) section 8, "The user's temporary folder on macOS"; [runtime and operations](../runtime-and-operations.md), "More stacks (OWL-624, OWL-627)", the Maven line. Corrects [OWL-627](OWL-627.md), whose `init` wrote the machine's `mvn` rather than the wrapper `mvnw` (its R1, the row "Maven with `mvnw`").

## As built (2026-11-22)

- **Sandbox.** `seatbelt_profile` (`owlshift-platform`, `sandbox.rs`) ends with a second `mach-lookup` denial, of `USER_FOLDER_SERVICES`: `com.apple.bsd.dirhelper` and `com.apple.system.opendirectoryd.membership`. Every confined command on macOS gets it: the harness, the setup, the gate and the credential probes. Linux is unchanged: its `mktemp` follows `TMPDIR`.
- **`init`.** With `mvnw` beside `pom.xml`, the gate is `./mvnw -B -Dmaven.repo.local="$MAVEN_USER_HOME/repository" verify`, read from "mvnw, the Maven wrapper", and OWL-627's note that the wrapper is not run is gone; without it the `mvn` line is unchanged. The wrapper keeps the Maven it pins in `$MAVEN_USER_HOME/wrapper/dists`, in the same run cache. As with `./gradlew`, the line assumes the wrapper's executable bit, which `init` does not read.
- **Held by** `executor::gate::tests::mktemp_without_a_template_writes_in_the_runs_own_temporary_folder` (`mktemp -d`, `mktemp` and `mktemp -t` confined land in the run's temporary folder, and a confined write to the runner's temporary folder does not reach it; red on the profile before the change, with `mkdtemp failed on /var/folders/…/T/tmp.…: Operation not permitted`), `sandbox::tests::the_seatbelt_profile_closes_the_home_the_writes_and_the_keychain`, and `stack::tests::a_maven_build_runs_verify_with_its_repository_in_a_run_cache`.

## Finding the mechanism (2026-11-22)

macOS 26.6.2 (25G83), Apple silicon, `sandbox-exec` with profiles shaped like Owlshift's (no write but to the run's folder and `/dev`, the user's `T` closed), one rule added at a time, `TMPDIR` the run's folder.

- `man mktemp`: with `-t` or no template, `mktemp` takes `_CS_DARWIN_USER_TEMP_DIR`, and `TMPDIR` only when that is "not available".
- Denied without effect, `mktemp -d` still failing on `T`: `file-read-metadata` of `T`, of the user's folder `/var/folders/<xx>/<yyy>` or of `/private/var/folders`; `sysctl-read`; `ipc-posix*`; `user-preference-read`; `system-info`.
- Every `mach-lookup` denied: `mktemp` falls back to `TMPDIR`. Bisected with `global-name-regex`: `com.apple.bsd.dirhelper` with `com.apple.system.opendirectoryd.membership` falls back; either alone does not, nor opendirectoryd's `libinfo` or `api` alone. With the pair, `mktemp -d`, `mktemp -t x` and `getconf DARWIN_USER_TEMP_DIR` give the run's folder, and Java's `java.io.tmpdir` is it too.
- Tools confined, without and with the pair. Unchanged: `id`, `id -Gn`, the names of `ls -l` and `stat`, `xcrun --show-sdk-path`, `cc` compile and link, `git init` and `commit`, Python's `tempfile` and `venv`, `java -version`, `mvn -v`, node's `os.tmpdir()`, `claude --version`, `codex --version`, `brew --version` and `--prefix`, `cargo new` and `cargo build --offline`, `rustc`, `uv` and `uv cache dir`, `npm` and its cache, `go env GOCACHE`, `dotnet --version`, `php`, `pdm`, `make`. Changed: `dseditgroup -o checkmember` answers "NOT a member" (exit 67) where it answered yes, so `mbr_check_membership` answers no rather than fail; `getconf DARWIN_USER_DIR` and `DARWIN_USER_CACHE_DIR` exit 71, "Input/output error". Better: `cc` and `swift` no longer print `couldn't create cache file '/var/folders/…/T/xcrun_db-…'`, and `swift -version` exits 0 where it failed.
- `DIRHELPER_USER_DIR_SUFFIX=<s>`, a variable libSystem reads: `confstr` then answers `T/<s>/` to a program built here, but `/usr/bin/mktemp` and `/usr/bin/getconf` ignore it, and the system makes `T/<s>` with SIP's `sunlnk` flag and `com.apple.rootless`, so `rmdir` is refused ("Operation not permitted"). The probe left one such folder, `T/owl637probe`, empty, in this machine's temporary folder; it stays until the system removes it.

It decides: the pair is closed in every confined command's profile. The order it rests on is not documented by Apple and was found on macOS 26.6.2 alone; CI's macOS leg (`macos-26-arm64`) runs the gate test above with confinement required, a second check. Should the order change, `mktemp` is given the user's folder again and refused there, today's failure, never a leak: the folder stays closed by its own rule.

## Live check R1, macOS (2026-11-22)

Script: [`owl-637.sh`](../live-checks/owl-637.sh), a reduced copy of OWL-627's harness: a Maven fixture (`commons-lang3` 3.17.0, `junit` 4.13.2) with its wrapper made by `mvn wrapper:wrapper` (wrapper 3.3.4, only-script, pinning Maven 3.10.1), served on a local bare remote; `owlshift init --tracker markdown --skip-secrets` of this branch, its `owlshift.toml` committed unedited; then the real `owlshift gate` by a binary of `main` without the change (0d70f0f9), and by this branch's. Before each gate the run cache `maven` holds the repository the machine's `mvn` filled unconfined (40 MB, 2189 s at this machine's rate), and no `wrapper/dists`, so each wrapper makes its download folder.

macOS 26.6.2 (25G83), Apple silicon; Maven 3.10.1 and openjdk 27.0.1.1 from Homebrew.

| | `owlshift gate` |
| --- | --- |
| `init`'s `[stack]` | `./mvnw -B -Dmaven.repo.local="$MAVEN_USER_HOME/repository" verify`, read from "mvnw, the Maven wrapper"; `run_caches.MAVEN_USER_HOME = "maven"` |

- The wrapper's jar flavour (`type=script`, `.mvn/wrapper/maven-wrapper.jar`), and wrapper versions other than R1's.
- A real harness turn on the new profile: `executor_live` (`OWLSHIFT_LIVE_CLAUDE=1`) reads the agent-run token from the keychain, which no automated run on the maintainer's machine may risk a dialog for; `claude --version` and `codex --version` ran confined.
- macOS versions other than 26.6.2 and CI's image.
- A `mvnw` without its executable bit.
