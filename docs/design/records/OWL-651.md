# OWL-651 · Lift a paused project once its retried watch is past its start

Settles: [architecture](../architecture.md) section 5, "Pause" (the *Revised* OWL-651 sentence) and "Restarts"; the open point "Within a minute is not exact" of [OWL-650](OWL-650.md).

## Why it took two minutes (2026-11-26)

The OWL-650 notice promises a project is picked up again within a minute of its fix. Before this ticket, three waits added up:

- The daemon tried the project again at its next pass (up to 60 s).
- It lifted its pause 60 s after that watch started (`lift_at = now + pass`).
- The watch had read the pause at its first pass and dispatched nothing. It then slept its 60 s interval, which a lift does not wake (`watch.rs`, `POLL_INTERVAL`), so it dispatched only at its second pass.

Lifting sooner in the daemon alone could not fix this. The watch's first pass reads the pause before any signal reaches the daemon.

## As built (2026-11-26)

- The daemon's own pause holds no watch. `requests::operator_pause`, the pause a watch reads, skips a project pause whose request is `by` `owlshift daemon`. A pause that does not read still holds, and so do a person's and the machine's. A retried watch therefore dispatches at its first pass, within a pass and the watch's start of the fix.
- The daemon keeps its pause file, so `status`, the UI and doctor still say the project waits for you, until the retried watch is past its start. That moment is read from the watch's record `watches/<pid>.json` (`supervise::past_start`, through `watch::presence::running`), at each tick while such a watch runs. The fallback stays the old rule: a watch still running a pass later, as one waiting for the network (OWL-479), is lifted then. For that one, until the lift, the pause is a report only.
- A daemon started while its own pause stands takes it up silently in `Slot::new`. Its first watch is then a quiet retry and lifts the pause once it serves. Before, a new slot started with no pause in mind, so a daemon restarted (a crash, an upgrade's hand-over) after the fix never lifted it.
- Tests:
  - `requests` unit test: a daemon's own pause holds no watch.
  - `supervise` unit test: the take-up, the daemon's own pause alone.
  - Bench (`a_refused_token_at_a_watchs_start_still_pauses_its_project`, extended): the real drain watch, its credentials mended, is never held. The pause is lifted under a bench pass after the watch's start (measured from the events' times), and the pause is notified once. The test fails with the old reading: the watch says "this project is paused" and the lift comes a pass later.
  - The stand-in watch writes no record, so the existing stand-in test still holds the fallback.

## What differs from the plan, or is left open

- **Tripwire.** The lift on time rests on `owlshift watch` writing its record after every check that can refuse it and before its first pass (`do_cmd.rs`, the `WatchRecord` before `Watch`). The bench writes its own copy of that order, so a change that moves or drops the record in `do_cmd.rs` falls back to the lift a pass later, and no test notices. Ticket dispatch would still come at the first pass: only status lags.
- A refusal after the record, `step_program` failing to pin the binary for a served watch, would lift the pause, then pause again. Each retry would repeat the "served again" and "Paused" lines and the notification. It needs an unreadable binary copy, so it was left as is.
- A watch typed in a terminal after `owlshift stop` is no longer held by a leftover daemon pause. It meets the same refusal at its start by itself.
