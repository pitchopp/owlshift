# OWL-673 · Close the gap between starting a process tree and its sentinel knowing it

Settles: [runtime and operations](../runtime-and-operations.md) item 2, "No start escapes the sentinel". Corrects [OWL-671](OWL-671.md): the window "Kept as it is" and first under "Left as they are" is closed, and `Bench::told_its_sentinel_of`, under "As built", is gone.

## As built (2026-11-28)

- `process::sentinel`: two new lines. A tree's root writes `? <group>`, its own pid, from a `pre_exec` closure between fork and exec. Owlshift then writes `+ <group>` when the spawn succeeded, or `!` when it failed, which forgets the group of that unconfirmed `?`. `SCRIPT` keeps a `?` group as live and pending until the next line. A `+` of the same group confirms it without listing it twice; every line but a `?` ends the pending. The `?` and `!` patterns are quoted, since an unquoted `?` matches any one character.
- `Sentinel::arm` adds the closure, last, while the sentinel runs and has lost no line. A flag made for that start alone (`Arc<AtomicBool>`) lets the root write, and is cleared once the start is confirmed or withdrawn, so a command started again writes nothing. `Start::confirm` writes `+`; a `Start` dropped unconfirmed writes `!`, on a failed spawn or a panic in it.
- The closure calls `getpid`, `sigaction` to ignore SIGPIPE around the write, `write` and `sigaction` again, on a `Line` built on the stack without a panic path. Owlshift's own lines are built the same way. std sets SIGPIPE back to its default before the closures, so a write to a sentinel that is gone would otherwise kill the root before its program runs, while std reported a start. `libc` is now a dependency of `owlshift-platform` on every Unix, for `sigaction`.
- `signals::register` takes the command, arms it under the live trees' lock, held across the spawn as before, then confirms the start or drops it.
- Tests:
  - `a_line_names_its_group_in_full`.
  - `the_script_keeps_a_started_tree_and_forgets_a_failed_start`: the script's list after `?`, `!`, `+`, `-`, a `!` with nothing pending, and a `?` left unanswered.
  - `a_start_is_announced_by_its_root_then_confirmed_or_withdrawn`: the exact lines of a start whose program is missing, then of one that runs, then of that command started again, which writes nothing.
  - `a_hard_kill_during_a_start_leaves_no_tree`: a helper starts the sentinel and a tree whose root SIGKILLs the helper from its own `pre_exec`, before it announces itself. The tree must be gone within `wait::REACHED`. A control start of the same command first shows it runs, so a tree found gone is not one that never started.
- daemon `a_sigterm_and_a_hard_kill_leave_no_ui` and `a_hard_kill_of_the_daemon_leaves_no_watch_or_step` kill the daemon as soon as the UI answers or the watches and steps run, no longer once the daemon has said it started them.

Built otherwise than planned: the window test's helper keeps the tree's handle after the spawn. The measure below found the plan's `let _ =` withdrew the tree whenever the helper outlived the kill for a moment.

## The cost of a start

Any `pre_exec` closure makes std fork the root instead of using `posix_spawn`. On the maintainer's machine (macOS, Apple silicon, 18 cores), 300 spawns of `/usr/bin/true` in a group of their own, from a process with 8 idle threads:

| Process memory | Without the closure, median / p90 | With it, median / p90 |
| --- | --- | --- |
| at rest | 0.106 to 0.108 / 0.120 to 0.142 ms | 0.577 to 0.617 / 0.696 to 0.733 ms |
| 300 MB more, touched | 0.090 to 0.098 / 0.104 to 0.112 ms | 0.561 to 0.577 / 0.679 to 0.697 ms |

So about half a millisecond more per tree, under the live trees' lock: for a step's few hundred git calls, about a tenth of a second. Processes without a sentinel, as most test binaries, keep `posix_spawn`.

Not measured on Linux: the local Linux images hold no Rust toolchain or compiler, and nothing was downloaded. There glibc's `posix_spawn` clones without copying the address space, and a fork copies its page tables, so the difference grows with the process's mapped memory.

## Under load (2026-11-28)

On the maintainer's machine (macOS, Apple silicon, 18 cores, 48 GB), cargo-nextest 0.9.146, another agent's builds sharing it. The setup:
- five lanes, each running full workspace runs one after another;
- after a minute, nextest stress loops of the window test and of the two daemon hard-kill tests, 25 min each;
- the load read every 15 s;
- the sentinel's script writing each line it read and each kill to a log of its own (a measuring build, reverted).

**Round 1, from 02:09 UTC, stopped at 02:29.** The window test failed 3 times in 40, each time with its tree still running after 120 s. The sentinel's log of one failure read `? 77671`, `+ 77671`, `- 77671`: the helper had outlived the root's SIGKILL long enough to confirm the start and then drop the tree's handle, which the test's `let _ =` did at once, and the sentinel rightly spared a withdrawn tree.

On a loaded machine a SIGKILL sent to a process does not stop its other threads at once. The thread blocked in the spawn returned, and ran on, before the process ended. The helper now keeps the handle, as every caller of `ProcessTree` does while its run lasts. The daemon loops passed 408 of 408.

## Left as it is

- A start whose program cannot be executed is withdrawn only after std has reaped its root, inside the spawn. A hard kill between that reap and the `!` leaves the freed pid in the sentinel's list, which it kills at the end should another group have taken that id meanwhile. That needs a failed exec, a kill within that span and a reuse of the pid as a group's id.
- The cost of a start on Linux, above.
