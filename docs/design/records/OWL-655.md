# OWL-655 · Rebase a clean refresh without an agent run

Settles: [architecture](../architecture.md) section 5, "Conflicts and the rebase run": *A clean refresh*, and the amended *Trivial or not, as run*, *The push guard* and *Owlshift's own pushes*. Also "Merge on green": the revision of its *Rejected.* bullet and *The guarantee given up*. Also "Tolerated overlap": *The refresh*, *A review after a resolution* and *Recorded per day*. Also "Leaving a broken commit": its *Rejected.* bullet.

## The case (2026-11-26)

On Locary, from 2026-11-10 to 2026-11-26 (`events.jsonl`), there were 6 overlap refreshes, and all 6 were clean. A run took a median 15 minutes from dispatch to push, of which the model took 0 to 9 minutes. The rest was mostly the project's gate, about 12 minutes. LOC-2198's refresh (2026-11-26 00:39 UTC) is one example: Haiku took 1.4 s and the run took 16 minutes. LOC-2200 (pitchopp/locary#1783) was refreshed by hand the same day with GitHub's update-branch: a merge commit, done in seconds. The pull request's CI then ran on the pushed head anyway: a median 43 minutes on Locary, 70 at p75.

## The decisions (2026-11-26)

The runner's resolver decided four questions from the ticket, the design and the code. The decider then approved the plan that carries them.

- **Q1, how.** The runner makes a merge commit itself. Its parents are the last push and the base head, and its tree is `git merge-tree`'s. It is checked by `rebase_keeps_delivery` and pushed as a fast-forward leased on `pushed`. The delivery's commits stay as they are. Rejected:
  - the runner's `git rebase`, which needs a worktree, can stop mid-replay and rewrites an agent's commits;
  - a squash, which flattens the delivery and needs a force push;
  - GitHub's update-branch (below).
- **Q2, the gate.** A clean refresh runs no local gate. The pull request's CI checks the combined code, and merge on green waits for it. The design states that a project's CI must not skip a step on a commit whose DELIVERY report says the gate was not run by Owlshift. That is the coverage Locary's LOC-2092 (Backlog) would drop: it skips a CI step on a commit Owlshift gated green. So the two never drop the same check.
- **Q3, the count.** A clean refresh is one of the delivery's six repairs, through the same `RebaseDue` and `RebasePushed` as a rebase run's push. Each refresh still restarts CI.
- **Q4, the report.** It gets a lead line of its own: "Refreshed onto `main` at `abc1234` after delivery, repair 1 of 6: Owlshift merged the base itself, git finding no conflict; no agent ran." A rebase's line says the branch's history was replaced, which a fast-forward merge commit does not do.

## GitHub's update-branch (read on 2026-11-26)

[`PUT /repos/{owner}/{repo}/pulls/{pull_number}/update-branch`](https://docs.github.com/en/rest/pulls/pulls#update-a-pull-request-branch) "Updates the pull request branch with the latest upstream changes by merging HEAD from the base branch into the pull request branch". It takes an optional `expected_head_sha` (422 when it does not match) and answers 202 with a `message` and a `url`, never the commit it will make. So no push can be kept under way (`pushing`), and the head it moves to is one Owlshift did not push, which would end the following. The runner's own merge gives the same result with the push guard and the lease.

## Live check R1 (2026-11-26)

`docs/design/live-checks/owl-655.sh`, run first in the Build, before any code that rests on it, with git 2.54.0 (Apple Git-157) on Darwin arm64. A delivered branch `b` changes line 1 of a shared file, and `main` then changes its line 3:

- `git merge-tree --write-tree -z --end-of-options main b` exited 0. Its whole output was the tree's id and a NUL, 41 bytes (`f79423259340914c6146bc0723f34368544ce4b0`, an object of type `tree`). That id is the fixture `TREE` of `rebase.rs`'s tests.
- `git -c user.name=Owlshift -c user.email=owlshift@localhost commit-tree --no-gpg-sign <tree> -p <b> -p <main> -m …` exited 0 with a 40-character commit. `git cat-file -p` showed two `parent` lines, `b` then `main`, the author `Owlshift <owlshift@localhost>`, and that tree. The merged file held both changes.
- `git push --porcelain --no-verify --force-with-lease=refs/heads/b:<b> origin <merge>:refs/heads/b` exited 0, its line flagged ` `, a fast-forward, which `read_forced_push_parts` reads as `Pushed::FastForward`. The same push leased on the old head then was rejected, flag `!`.

The script checks each of these and exits 0 when all hold. Owlshift's floor is git 2.39. `--write-tree` and `-z` are documented from 2.38.0 ("Trivial or not"), and `commit-tree` with several `-p` is far older. No older git was at hand to run it on.

## A head with a merge commit under `merge_method = "rebase"` (read on 2026-11-26)

GitHub's documentation does not say how rebase-and-merge treats a pull request whose head holds a merge commit. The current pages say only that the commits "are added onto the base branch individually without a merge commit" ([about merge methods](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github)). An older page lists when GitHub "can't automatically rebase and merge", among them a rebase "considered 'unsafe', such as when a rebase is possible without merge conflicts but would produce a different result than a merge would" ([about pull request merges, Enterprise Server 3.8](https://docs.github.com/en/enterprise-server@3.8/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/about-pull-request-merges)). One user's report on GitHub's community forum ties "This branch cannot be rebased safely" to a merge commit in the pull request ([discussion 22403](https://github.com/orgs/community/discussions/22403)). This was not observed here.

What follows from it: under `squash` (the default) and `merge`, the runner's merge commit changes nothing for the merge. Under `rebase`, GitHub may refuse to merge such a head. That refusal takes merge on green's existing path ("Its answers", *A refusal that will not*): one `merge_refused` event and one notification, and a person merges. No fallback to the rebase run was built for that method; it is proposed as a follow-up.

## As built (2026-11-26)

- `rebase::Classified` keeps `tree`, the merged tree of a clean `merge-tree` whose first field is a full object id (`CommitId::new`'s rule). It is `None` on any conflict, other exit or unreadable output.
- `OnDemand::repair_rebase`, after `classify`, gives a refresh with a tree to `OnDemand::refresh_merge`. That writes the merge commit and checks it with `rebase_keeps_delivery`, and does nothing else. A refusal is a `warning` event (`refresh_merge_refused`, with the reason), and the rebase run follows as before. A merge the guard takes goes to `OnDemand::push_refresh`, in this order:
  - the step's one `dispatch` (command `rebase`);
  - `base::remove_wait`;
  - `reset_worktree` to the merge;
  - a `decision` event (`watch` = `refresh_merged`: `pull_request`, `cause`, `onto`, `tree`, `commit`);
  - `push_repair` with `Gate::NotRecorded` and `RepairKind::Rebase { refreshed: true, .. }`.

  `Writer::push_rebased` checks the merge again and reads its fast-forward as landed.
- `delivery.json` format 10: a kept or owed report's `refreshed`, valid only on a rebase's. Formats 1 to 9 are still read, and a format-9 document that holds it is refused. A push pushed again without a run keeps it from `pushing.report`, and the owed report's lead line follows it (`REFRESHED_LEAD`, one of `LEADS`).
- `roles/rebase.md` tells the rebase run when a refresh still reaches it: `git merge-tree` found conflicts, or the runner's own merge was refused. Merges the runner made earlier are dropped by `git rebase <onto>`.
- Tests:
  - `rebase.rs` unit tests on the tree;
  - `writer.rs`'s `a_refresh_the_runner_merged_says_no_agent_ran`;
  - the contracts' format-10 checks;
  - on_demand scenarios. The acceptance scenario is `refresh_then_merge` (merge_scenarios.rs): a clean refresh pushed with no run, then merged on green. One shared check, `assert_runner_merged`, covers what the merge leaves, and five edge scenarios in `overlap_scenarios.rs` cover a conflicting refresh, a remote refusing the merge's push (played by a lock held on the remote's ref, since the bench runs git with hooks off), a push cut short, a guard refusal and a failing gate on the base.
  - Scenarios that test the rebase run on a refresh, such as OWL-558's closing keyword, now get a base change git finds conflicting while the fake GitHub reports the pull request mergeable.

## Owed: the measure

Once a release with this change runs on Locary, a person reads Locary's `events.jsonl` from that release on. For each `refresh_merged` event, they measure from the step's `dispatch` (command `rebase`) to its forge `push`. They compare that with the 15-minute median of 2026-11-26, and note whether each pull request then merged on green.
