**The rigs, fixed before they could run.** Each fix changes how a tool chain is installed or where the harness starts, never the `[stack]` checked:

- The three wrappers start the harness from the home, not from `/src`. When the checkout mounted as `/src` is a git worktree, its `.git` names a folder of the host, so the harness's `git config --global` failed in `/src`. Without the settings the fixtures could not be pushed and every gate stopped at its clone ("cannot run ssh"). From a plain checkout this would not have arisen.
- `owl-628-linux.sh` takes Erlang/OTP from Hex's builds for Ubuntu 24.04 (`builds.hex.pm`). The Erlang Ecosystem Foundation's `otp_builds`, which the rig named, publish macOS builds only, and the URL answered 404.
- `owl-627-linux.sh` takes Maven 3.10.1 from Apache's archive, the version macOS's check ran, instead of the distribution's 3.8.7. Maven 3.8.7 binds `maven-compiler-plugin` 3.1, which ignores the fixture's `maven.compiler.release` and compiles for Java 5. JDK 21 refuses that ("Source option 5 is no longer supported"), confined or not. That red run, at 08:59Z, says nothing about the sandbox.
- The wrappers pass `TAIL`, `CONCURRENT` and the harness's other options into the container, and the harnesses gained `CONCURRENT=1` (below).

**Two runs at once** (`CONCURRENT=1`, the harnesses' `pair`). For each ecosystem with a run cache, after the rows above: the `[stack]` as written, the ecosystem's run cache tree emptied, then two `owlshift gate` started together. Each has its own `OWLSHIFT_DATA_DIR`, because a gate takes the project's lock in its data folder ([`gate_once.rs`](../../../crates/owlshift-runner/src/gate_once.rs), `GateOnce::run`). Both share the one `OWLSHIFT_CACHE_DIR`, as two steps of one project, each holding its own ticket's lock, share its run caches. A third gate then runs alone on what they left.

pip and Composer, which write no run cache, were not paired. The .NET rows ran from 09:19Z to 09:39Z, one pair after another, each pair from an emptied tree. NuGet extracts a package into the global packages folder, `DOTNET_CLI_HOME`'s `.nuget/packages` here, under a lock file it keeps in its scratch folder. By default that folder is under the temporary folder, and each confined command has its own (`TMPDIR`). So two restores at once do not see each other's lock, and one moves a file away while the other still reads it. `NUGET_SCRATCH`, the variable NuGet reads for that folder, set to one run cache gives both runs the one lock. A single run with the variable removed stays green (6 of 6): one run alone cannot show the race, so the rule's fail-without half, a single run, does not either.

It decides:

- **Every variable `init` writes for OWL-624, OWL-627 and OWL-628 is kept.** Each is green on Linux with it set. `POETRY_CACHE_DIR`, `BUNDLE_PATH`, `MIX_HOME` and `MAVEN_USER_HOME` also fail on Linux when removed. The others are green there without them, which the rule expects. `crates/owlshift-core/src/stack.rs` does not change.
- **GEM_HOME is not needed for a lock that pins a newer bundler.** Bundler 2.4.20 installed the pinned 2.5.23 into `BUNDLE_PATH`, the run cache, not into the home, and the gate's later command used it from there.
- **`./mvnw` runs confined on Linux**, as OWL-637 expected: `mktemp` follows `TMPDIR` there.
- **Elixir's setup holds on a Linux without `/etc/ssl/cert.pem`.**
- **Two runs at once:** one run cache serves two gates installing at once for every ecosystem paired except .NET. Two .NET setups that restore into an empty `DOTNET_CLI_HOME` at once fail about half the time on Linux, and a third run alone after them passes. `init`'s .NET lines are left as they are. `NUGET_SCRATCH` in a run cache cured it in 6 of 6 pairs, but the rule writes a variable on a single run's fail-without, on macOS first, and neither macOS nor that kind of evidence was checked here. Whether `init` writes it is left to a follow-up ticket.
