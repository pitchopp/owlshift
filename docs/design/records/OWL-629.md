# OWL-629 · Detect yarn 4 and pnpm versions other than 10 in owlshift init

Settles: [runtime and operations](../runtime-and-operations.md), "Stack detection (P9)", "Caches a run may write (OWL-617)" and "More stacks"; [architecture](../architecture.md) section 8, "Caches a run may write", "The folders" and "Tool chains". A follow-up of [OWL-624](OWL-624.md), whose method it keeps: a run cache is written only when the real `owlshift gate`, confined, passed with it and failed with it alone removed.

## As built (2026-11-23)

- **pnpm** (`pnpm-lock.yaml`), every major: setup `pnpm install --frozen-lockfile` as before; `run_caches.PNPM_HOME = "pnpm"`, which replaces OWL-617's `npm_config_store_dir = "pnpm-store"`; `run_caches.XDG_RUNTIME_DIR = "pnpm-locks"` unless `package.json`'s `packageManager` pins a pnpm below 12, with a `# note:` saying why; `run_caches.COREPACK_HOME = "corepack"`. The note OWL-617 wrote for a pin other than pnpm 10 is gone. A `packageManager` that names another manager, or a version not starting with a number (`pnpm@latest`), counts as no pin.
- **yarn 2 and later** (`yarn.lock` with `.yarnrc.yml`, or a `packageManager` pinning yarn 2 or later): setup `yarn install --immutable`, `run_caches.YARN_GLOBAL_FOLDER = "yarn"` and `run_caches.COREPACK_HOME = "corepack"`. This replaces OWL-593's `caches = [".yarn/berry"]`, the person's global cache read-only, which every machine had to allow in `allow_caches` and keep holding the project's packages, and the reading of `.yarnrc.yml`'s settings that decided it. Without `.yarnrc.yml` a yarn 4 project was taken for yarn 1 before. yarn 1 and bun are unchanged.
- **Removed with it**, nothing else using them: `stack::SETTINGS` and the reading of `.yarnrc.yml`'s text by `init::read_root_files`, `Found::caches` and `Detection::caches`, the `caches` lines `init` wrote from them, and `init`'s advice and offer for them on a new file. A project file that declares `stack.caches`, by hand or as `init` wrote yarn 4's before, still gets that advice from `init`, `doctor` and `gate`. The template's commented example is now `caches = [".pyenv"]`, the case OWL-624 found.
- **Decided with the maintainer** (2026-11-23): corepack gets a run cache of its own, since it installs the version the project pins (architecture section 8, "Tool chains"); `XDG_RUNTIME_DIR` may name a run cache, the person's own value still never inherited (section 8, "The folders"; `agent_env::INHERITED`'s comment).
- **Held by** `stack::tests::each_node_manager_gives_its_install_and_its_scripts`, `pnpm_writes_its_lock_folder_unless_pinned_below_12`, `yarn_2_or_later_writes_its_global_folder`, `the_lock_folder_is_a_run_cache_and_the_real_one_is_never_inherited`, `every_run_cache_detected_passes_the_names_check`; `agent_env::tests::the_run_caches_are_written_and_named_on_the_command_alone` (runner: the command gets the run cache's folder for `XDG_RUNTIME_DIR`, not the runner's value); `init::tests::a_gate_given_by_hand_wins_and_the_detected_setup_stays`, which loads the three pnpm variables back from the file; the CLI's `a_gate_given_with_init_wins_over_the_detected_one`, a yarn 4 root end to end, then a kept file declaring `.yarn/berry`.

## Before the code (2026-11-23)

The same harness with `main`'s binary and `STACK_EDIT`, on macOS, found what the lines above rest on: pnpm 11 and 12 read `pnpm_config_store_dir` and not `npm_config_store_dir`, so OWL-617's variable leaves their store in the worktree; `PNPM_HOME` moves the store of pnpm 9 to 12 alike (`pnpm store path`); pnpm 10 and later switch to the version `packageManager` pins, downloading it under `PNPM_HOME` (`.tools` for pnpm 10, `package-manager-store` for 11 and 12), and pnpm 9 does not; pnpm 12, a native build, takes its store's locks in `$XDG_RUNTIME_DIR/pnpm-store-operation-locks-<uid>`, otherwise in the shared `/tmp`, which the sandbox closes: the cause of OWL-598's `ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK`; yarn's `YARN_GLOBAL_FOLDER` wins over a project's `globalFolder`. A machine's pnpm 10 on a project pinning pnpm 12 fails unconfined too, `ENOEXEC` running pnpm 12's native binary.

## Live check R2, Linux (2026-11-23)

Script: [`owl-629-linux.sh`](../live-checks/owl-629-linux.sh): the same runs in Docker on the same machine, Ubuntu 24.04 (aarch64), bubblewrap 0.9.0, a non-root user, a Linux build of this branch, node 24.22.3 with pnpm 10.33.2 in `/opt/node`, the same tools under `/opt/owl629-tools`. A first run on node 22.11.0 could not lock the pnpm 11 fixture, unconfined: pnpm 11 needs node 22.13 or later.

All 15 fixtures green as written, pnpm 12.20.0 (61 MB) and pnpm 9 (22 MB) downloaded into `pnpm` by the switches, pnpm 9 into `corepack` (20 MB). With one variable removed, every run green, the tool writing into bwrap's private home or `/tmp` instead, lost with the command, as OWL-617 found, but two: yarn 4 with Plug'n'Play, with or without `.yarnrc.yml`, red without `YARN_GLOBAL_FOLDER` at `yarn run test`, `Cannot find module`: the setup's cache was in the setup's private home, and Plug'n'Play resolves the packages from the cache itself, not from a `node_modules` in the worktree. So on Linux too, yarn 4's default linker needs the variable.

## Not checked

- Two confined runs at once switching pnpm, or corepack, into one empty folder.
- A Build agent's `pnpm add -g`, whose global folder is now in the run cache, which no `PATH` names; it failed before on the closed home.
- A project `.npmrc` setting `store-dir`, which wins over `PNPM_HOME`'s default store: inside the worktree and not ignored, the gate names the files.
- yarn 1 through corepack; a yarn 2 or later project whose zero-install cache is committed; Plug'n'Play's `.pnp.cjs` committed, which the install rewrites with the run cache's path.
- The folder `XDG_RUNTIME_DIR` names is made with the run cache's mode, not `0700`; the cache directory above it is the user's own. A tool that checks the mode may warn.
